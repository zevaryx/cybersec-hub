// WHY THIS TALK

The maths holds. The calls around it don't

Real incidents rarely break AES. They break the call: a weak random seed, a check switched off, a comparison that gives itself away.

  • You will call crypto far more often than you'll write it. The skill is choosing and holding it correctly.
  • Prefer the highest-level API that does the job: every knob is a mistake you can make.
  • Test the failure paths: tampered data, wrong key, expired token.

Sources: Android · Georgiev et al. · Keyczar · Böck et al.

Android, 2013Java's SecureRandom could return weak values on some devices. A compromised bitcoin transaction led to wallet-app updates on 11 August.
Certificate checks, 2012Certificate validation was broken in many non-browser programs: logic errors, or checks switched off.
A comparison, 2009Keyczar's HMAC check stopped at the first wrong byte, so timing leaked information. Fixed in May 2009.
Repeated nonces, 2016184 HTTPS servers reused AES-GCM nonces, which breaks the authenticity of their connections.

  • TipAndroid: the post says apps that set up TLS through HttpClient or java.net weren't affected, and apps running only on Android 4.4 or later needed no workaround. Don't overstate it as "all Android crypto was broken".

Choosing a library

  • Platform first: Web Crypto in browsers, the OS keychain for stored secrets, your language's standard library.
  • Mainstream and maintained: libsodium, Google's Tink, Python's cryptography. Many eyes, regular releases, security contacts.
  • Safe defaults: the easy path should be the safe path. Be wary of APIs that make you pick modes, padding or IV lengths.
  • Boring wins: a library everyone uses beats a clever one nobody has reviewed.

Sources: Tink · libsodium secretbox · Python cryptography (its "hazmat" layer is labelled for experts)

~4 min

  • SayLibraries come in layers. The lower you go, the more you must know, and the more ways there are to hold it wrong. The Python cryptography package even names its low-level section "hazmat" and warns you to be 100% sure before using it. Start at the top layer and only drop down when you have a reason.

    // CHECKPOINT 1 · 5 MIN

    Pause and discuss

    Talk with a neighbour for a couple of minutes, then we share answers.

    1. You need to store users' passwords. Which function do you reach for, and what do you not do?

      Hint

      Which layer of the library, and is speed a virtue here?

      Answer

      The library's password-hashing function (Argon2id, or scrypt, bcrypt or PBKDF2 where required) with its verify function. Don't use a plain SHA-256 or MD5, and don't write your own loop.

    2. A package's README says "military-grade, proprietary algorithm, never broken". What do you do?

      Hint

      Who has reviewed it?

      Answer

      Walk away. Home-made algorithms and marketing claims are red flags. Use a mainstream library with a standard algorithm that has survived public attack.

    3. Why prefer a recipe like secretbox over calling AES directly?

      Hint

      How many choices does each one leave you?

      Answer

      A recipe has safe defaults and fewer choices to get wrong (mode, padding, tag). Every knob you can turn is a mistake you can make.

    // ENCRYPTION WITHOUT FOOTGUNS 01

    Authenticated encryption only: why the tag matters

    CIPHERTEXT (the attacker can change any byte)

    No tag (a stream mode alone)Decryption "works". The change goes through, and nothing says so.
    With a tag (AES-GCM)The tag no longer matches, so the message is rejected before anyone reads it.
    • Use AES-GCM or ChaCha20-Poly1305, or a recipe built on them.
    • Plain CBC or CTR need a separate MAC, applied encrypt-then-MAC. Easier to avoid them.
    • Decrypt fails closed: on a bad tag, throw. Never use the plaintext.

    ~5 min

    • ShowPress "Change the 1 to a 9". The no-tag panel decrypts to $900.00, the GCM panel rejects. Then click individual ciphertext bytes to flip a bit anywhere: the no-tag side changes exactly that spot in the plaintext, and GCM still rejects.
    • SayEncryption hides content; it doesn't stop changes. In a stream mode, flipping a ciphertext bit flips the same plaintext bit, so someone who knows the format can edit the message without the key. That's why we only use authenticated encryption: the tag covers the ciphertext, and checking it comes first.
    • TipCBC has its own failure: padding oracles (Vaudenay, 2002), where error behaviour while checking padding leaks plaintext. Moxie Marlinspike's "Cryptographic Doom Principle" (2011) argues you should verify the MAC before touching the ciphertext at all, which is what an AEAD does for you. OWASP: "Where available, authenticated modes should always be used."

    // ENCRYPTION WITHOUT FOOTGUNS 02

    Nonces: random or counter, and how long a key lasts

    • A nonce is "number used once" per key. Repeat one and the guarantees go.
    • Random nonces need a big space. With random 96-bit nonces NIST caps a key at 232 messages (collision odds stay under 2-32).
    • Counters never repeat, but state must survive restarts, crashes and many servers. Lose the count and you repeat.
    • Long random nonces (XChaCha20's 192 bits) make "random" safe without counting.
    • Better: let the library make the nonce, and rotate the key long before the limit.

    Sources: NIST SP 800-38D, §5.2.1.1 and §8.3 (a revision is in progress) · RFC 8439 · libsodium XChaCha20-Poly1305

    ~5 min

    • ShowChoose 16 bits and draw: a repeat after a few hundred nonces. Try 24, 32, 40: each step takes longer. Then move to 96 bits: the button explains it can't run (about 248 draws expected, far more memory than any browser has). Slide the message count to 32 with 96 bits: roughly 1 in 8.6 billion. Push it to 48 and watch it become real.
    • SayThat's the birthday effect: a repeat shows up near the square root of the space. NIST's rule for random 96-bit IVs is a limit of 232 invocations per key, which keeps the chance of any repeat below 2-32. Reuse isn't a small risk: next slide.
    • CheckSP 800-38D (November 2007) §8.3: the total number of invocations "shall not exceed 232" for the RBG-based construction; §5.2.1.1 recommends 96-bit IVs; §5.2.1.1 also limits plaintext to 239-256 bits per call. NIST is revising it, but there's no draft text yet: a second pre-draft call for comments closed on 31 July 2026 (checked 8 Nov 2026). Check its current status before quoting limits.

    // ENCRYPTION WITHOUT FOOTGUNS 03

    What a repeated nonce breaks

    Ciphertext A
    Ciphertext B
    A ⊕ B
    cipher A ⊕ cipher B

    • Stream-style modes (CTR, GCM, ChaCha20) make a keystream from key and nonce. Same pair, same keystream.
    • XOR the two ciphertexts and the keystream cancels: you have A ⊕ B. Know one message, get the other.
    • In GCM it also lets someone recover the authentication key, and forge messages.

    Source: Böck et al., WOOT 2016: 184 HTTPS servers repeated nonces, and the paper's proof of concept forged traffic.

    ~4 min

    • ShowWith "A fresh nonce each time": the two XORs look unrelated, and the recovered text is noise. Switch to "The same nonce twice": the last two rows match exactly and the secret reappears. Edit message B and watch the recovery follow.
    • SayThis is the "two-time pad": the oldest mistake in stream encryption. Real messages have predictable structure (headers, templates, JSON keys), so "I don't know either message" is not much protection. With GCM it gets worse, because the authentication key leaks too: the forgery attack Böck et al. demonstrated against live HTTPS servers.
    • TipThis demo shows what reuse does, using the same AES-GCM used elsewhere in the talk. It only recovers text you could already compare against; it's not a tool.

    // ENCRYPTION WITHOUT FOOTGUNS 04

    Associated data: bind a ciphertext to its context

    RowOwnerStored ciphertext
    • Associated data (AAD) is authenticated, not encrypted. You pass the same value to decrypt.
    • Put in what the data belongs to: user ID, record ID, purpose, format version.
    • Then a valid ciphertext moved to another row, another user, or another purpose fails to open.
    • Store the AAD or rebuild it from context. Never trust one that came with the ciphertext.

    ~5 min

    • ShowWith the box ticked, read Bob's row (his own data). Press "Copy Alice's ciphertext into Bob's row" and read Bob again: rejected. Untick the box, reset and copy again: Bob's row now cheerfully shows Alice's salary.
    • SayWithout AAD every ciphertext is valid anywhere the key works. That's how "a user can read another user's record" bugs appear in encrypted databases: nobody tampered with the bytes, they just moved them. Binding the context costs nothing and removes a whole class of confusion.
    • TipPython cryptography: AESGCM(key).encrypt(nonce, data, associated_data); decrypting with different associated data raises InvalidTag, the same as a changed ciphertext. Node: cipher.setAAD() before update. Web Crypto: additionalData in the algorithm parameters.

    // ENCRYPTION WITHOUT FOOTGUNS 06

    Envelope encryption: wrap the data keys

    Key-encryption key (KEK)
    DocumentSizeWrapped data key
    • Each document gets its own data key (DEK). A KEK, kept in a KMS or HSM, encrypts the DEKs.
    • Store the wrapped DEK next to the data. Only the KEK needs strong protection.
    • Rotate the KEK by re-wrapping tiny keys, not re-encrypting the data.
    • Destroy the KEK and the data is unreadable (often called crypto-shredding).

    Sources: AWS KMS: envelope encryption · OWASP Cryptographic Storage

    ~4 min

    • ShowRead a document: the KEK unwraps its DEK, the DEK opens the data. Press "Rotate the KEK": four 32-byte keys are re-wrapped instead of re-encrypting 83 MB, and reads still work. Press "Destroy the KEK": every read now fails, though the ciphertext is still there.
    • SayEnvelope encryption is how cloud KMS products work: AWS KMS describes it as encrypting plaintext data with a data key, then encrypting the data key under another key. The benefits are the ones in the demo: wrapped keys are safe to store beside the data, and re-keying means re-wrapping, not re-encrypting. OWASP says the KEK must be stored separately from the DEK.
    • TipThe demo uses real AES-GCM from the shared Lab code with small sample texts, and shows the sizes as stated. Wrapped keys bind the document ID as associated data, so a wrapped key can't be moved to another document.

    // ENCRYPTION WITHOUT FOOTGUNS 07

    Version your ciphertexts so you can change later

    RecordStored blob

    • Start every blob with a version: v1.nonce.ciphertext.tag. Include the algorithm if you can have more than one.
    • On read, the version picks the code path. On write, always use the newest.
    • Upgrade lazily: re-encrypt old records as they're read, with a background job for the rest.
    • Without a version, changing algorithm means guessing, or a risky big-bang migration.

    ~3 min

    • ShowThe six records start as v1 (no associated data, like the one in the previous demo that moves between rows). Read one: it opens with the v1 rules and is rewritten as v2, which binds the record ID. "Read every record" does the whole lot.
    • SayYou will need to change algorithms, parameters or key hierarchy someday: a limit lowers, a weakness appears, or you learn about AAD after shipping. A version byte is the cheapest insurance you can add. Good password hash strings already do this: they carry the algorithm and parameters inside the string.

    // CHECKPOINT 2 · 5 MIN

    Pause and discuss

    Talk with a neighbour for a couple of minutes, then we share answers.

    1. Your teammate encrypts with AES-CBC and no tag "because it's standard". What do you suggest, and why?

      Hint

      What can someone do to the ciphertext, without the key?

      Answer

      Use an authenticated mode (AES-GCM or ChaCha20-Poly1305) or a recipe like secretbox. Without a tag, ciphertext can be altered undetected, and CBC's padding errors can become an oracle.

    2. When is a random nonce fine, and when do you need a counter (or a longer nonce)?

      Hint

      Think of the birthday effect and the NIST limit of 232 messages.

      Answer

      Random 96-bit nonces are fine below about 232 messages per key. Beyond that, rotate the key, use a safe counter, or use a long random nonce such as XChaCha20's 192 bits.

    3. Why add the record ID as associated data?

      Hint

      What happens if a valid ciphertext is copied to another row?

      Answer

      It binds the ciphertext to its context, so a ciphertext moved to another record, user or purpose fails to decrypt instead of being accepted.

    • SayThe 2012 study found that many non-browser programs had broken certificate validation, some because of API misuse and some because developers disabled checks while testing. Switching verification off turns encryption into a lock with the door open: the connection is private to whoever is in the middle. The fix is almost never harder than the shortcut.
    • CheckNames verified against docs: Requests verify=False and verify="/path/to/certfile"; Node rejectUnauthorized (default true) and the ca option in tls/https; also the NODE_TLS_REJECT_UNAUTHORIZED=0 environment variable (Node CLI docs). Go's tls.Config fields InsecureSkipVerify and RootCAs (with x509.NewCertPool and AppendCertsFromPEM), and curl's -k/--insecure and --cacert, checked against Go's crypto/tls docs and curl's manual.
    • Next"What your code says about secrets: logs and errors."
    

    


    
  
    // EVERYTHING ELSE THAT GOES WRONG 06
    Logs and errors: say little to callers, keep secrets out of logs
    
  
    
    
    
      
    
        
        
        
      
    
      
      
      
    
    
    
    
    
      
    Detailed errors to the caller"padding invalid at byte 14" versus "MAC check failed". Two answers let someone tell which step failed, and that can turn the decryption service into an oracle.
    
      
    One generic error, full detail in your logs"decryption failed" for every cause, plus a request ID. Log the real reason privately, without the secret.
    
      
      
        
    • Never log keys, tokens, passwords, or whole request headers. Redact at the logger, not by remembering.
      • 
        
    • Log events (a key was rotated, a token was rejected), not values.
      • 
        
    • Treat a leaked log as a leaked secret: rotate.
      • 
      
    
      
    The scrubber is a toy with five patterns, using fake secrets. Sources: OWASP Logging · Vaudenay, 2002
    
    
    
  
    
  
    ~4 min
    • ShowPick the web log: a bearer token, a JWT, a cloud key ID and a password in a URL light up, and the right-hand text shows the redacted version. The clean log has nothing to flag, but the note says that proves little: the toy only knows a few shapes.
    • SayTwo habits. First, secrets in logs: logs are copied, shipped, indexed and retained far longer than the request, and many more people can read them. Second, errors: when decryption fails, say the same thing every time. Vaudenay's 2002 paper showed how different errors for padding versus MAC failures made CBC decryption an oracle; AEAD removes the padding step, but uniform errors are still the habit.
    • TipAll secrets in the samples are fake. AKIAIOSFODNN7EXAMPLE is the key ID AWS uses in its own documentation. Check OWASP's Logging cheat sheet for the data-to-exclude list your audience's rules require.

    // CHECKPOINT 3 · 5 MIN
    Pause and discuss
    
  
    
    
    Talk with a neighbour for a couple of minutes, then we share answers.
    
    
      
      
    1. Why is if (token == expected) a problem for secret tokens?
      Hint
      What does an early exit tell someone who can measure time?
      Answer
      A normal comparison stops at the first different byte, so the time can reveal how much of the guess was right. Use the constant-time comparison from your standard library, on equal-length values.
      2. 
      
    2. A reset token is made with Math.random().toString(36). What's wrong, and what's the fix?
      Hint
      What is Math.random built for?
      Answer
      It isn't a secure generator, so tokens can be predicted. Use the system generator (crypto.getRandomValues, secrets.token_urlsafe, crypto.randomBytes) with at least 16 bytes, and store only a hash of the token.
      3. 
      
    3. A JWT library lets the token say which algorithm to verify with. What can go wrong?
      Hint
      Think of "alg": "none".
      Answer
      An attacker can pick an algorithm that skips or weakens verification. Pin the algorithm (and key type) on the server, and check exp, iss and aud.
