A talk on Memory Safety

Most of the serious bugs in big C and C++ codebases are about memory. Why, what the mitigations really buy you, how to catch the bugs early, and how to move to code that can't have them.

How much of the trouble is memory?

~70%of the vulnerabilities Microsoft fixes and assigns a CVE, as it reported in 2019: "memory safety issues"
~70%of Chromium's high-severity bugs, on its own memory-safety page: 912 high or critical bugs since 2015
<20%of Android's vulnerabilities in 2025, the first year below 20%, as new code moved to Rust (Google, November 2025)
Read the number carefullyEach vendor counts something different: CVEs, high-severity bugs, all vulnerabilities. They're vendor-reported figures about their own big, old C and C++ codebases. The pattern is consistent. Your share could be higher or lower.
Why they rank so highA memory bug often lets an attacker influence what the program does next, not just crash it. That's why so many of them are rated serious.
The Android resultGoogle reports a 1000× lower density of memory-safety vulnerabilities in its Rust code than in its C and C++ (an estimate: 0.2 per million lines against about 1,000).

  • SayThis is a pretend heap: 24 cells and an allocator that reuses freed space, like a real one. Pick a bug and press Step. Start with the write past the end: scores has four cells, the loop writes five, and cell 4 belongs to limit. Nothing crashes. Nothing says anything. limit is now 50. That is what "undefined behaviour" looks like in practice: usually silence. Now flip to Checked and run it again: the same program stops at the bad write, before anything changes. That's all a sanitizer, a bounds-checked library or a memory-safe language does.
  • ShowWalk all six, one minute each. Out-of-bounds write (CWE-787). Out-of-bounds read: a length that came from outside was believed; this is the shape of Heartbleed (CVE-2014-0160), where up to 64 KB of neighbouring memory could be returned. Use after free (CWE-416): p outlives the memory, and the allocator gives the cells to token. Double free (CWE-415): the second free releases cells that someone else now owns. Uninitialised memory (CWE-908): malloc doesn't clear, so the new block still shows the old letters. Type confusion (CWE-843): a Cat read as a Dog.
  • AskIn the use-after-free, which line is the bug: the free, the reuse, or the read? Answer: the read. The free and the reuse are both fine; the bug is the pointer that outlived the memory.
  • CheckThe heap is a toy: cells, not bytes, a first-fit allocator, no real addresses. Real allocators differ in layout and in how soon they reuse freed memory, which is why real use-after-free bugs are flaky. The CWE numbers are the standard ones: 787, 125, 416, 415, 908 and 843. Heartbleed: the OpenSSL advisory of 7 April 2014 says "a missing bounds check in the handling of the TLS heartbeat extension" can expose up to 64k of memory; affected the 1.0.1 and 1.0.2-beta releases (1.0.1 through 1.0.1f, and 1.0.2-beta1); fixed in 1.0.1g; credited to Neel Mehta of Google Security, with the fix by Adam Langley and Bodo Moeller.

Why "just be careful" doesn't scale

Snippet 1 of 6

      

      

        
        
        
        
      

      

      

    

    

      
Spatial: where?Does the access stay inside the object? Indexes, lengths, copies.

      
Temporal: when?Is the object still alive, and still the same one? Free, reuse, moves, a container that grew.

      
The compiler trusts youIn C and C++ an out-of-range access is undefined behaviour: no promise at all. The compiler may assume it never happens.

      
Careful doesn't scaleEvery access is a promise, across millions of lines and years of change. The tool should check, not the tired reviewer.

    

  

  
~6 min
  • SaySix snippets, none of them exotic. Click your verdict and read the explanation. The point isn't to catch you out: it's that two are fine, four aren't, and the bad ones look completely reasonable in review. Spatial bugs ask "where does this access land?". Temporal bugs ask "is this object still the one I think it is?". Then the awkward part: C and C++ leave out-of-range access undefined, so even the compiler may assume you never do it.

Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. What's the difference between a spatial and a temporal memory bug? Give one example of each.
    Hint
    One is about where an access lands; the other is about when.
    Answer
    A spatial bug accesses memory outside the object it was meant to use: a write past the end of an array, a copy with the wrong length. A temporal bug uses an object outside its lifetime: use after free, double free, a reference to something that moved or was destroyed. Uninitialised reads and type confusion are related cousins.
    2. 
      
  2. Why isn't "we just need to be more careful" a plan for a codebase of millions of lines?
    Hint
    Think about how many accesses there are, how many people touch them, and how long.
    Answer
    Every access to memory is a small promise (in range, still alive, right type) that has to hold on every path, forever, through every refactor by every author. Reviews catch some, but the bugs look reasonable, and the 70% figures come from teams that were careful. A plan needs the machine to check, or the language to make the bug impossible.
    3. 
      
  3. How would you find out what share of your own project's serious bugs are memory-safety bugs?
    Hint
    What does your bug tracker record about root cause?
    Answer
    Add a root-cause or bug-class field (or a label) when triaging, tag the last year or two of security fixes by hand, and count. Sanitizer and fuzzer reports already name the class: "heap-use-after-free" is a label you can keep.

    // MITIGATIONS 03
    Hardware help: memory tagging
    
  
    
    
    
      
    Memory gets a small tag, and so does every pointer to it. A mismatch on access stops the program.
    
      
    
      
    Tag size
    
      
    
        
        
        
      
    
      
    
        
        
        
        
      
    
    
    
    
    
      
    
      
    
      
    1,000 stale-pointer trialsFree A and retag it at random, then use the old pointer. How often does the tag happen to match?
    
      
    Where it shipsArm's Memory Tagging Extension (MTE). Apple turned an enhanced version on by default in iPhone 17 and iPhone Air (Memory Integrity Enforcement); Android offers MTE as an option.
    
    
    
  
    
  
    ~5 min
    • SayThe idea: when memory is allocated, give it a small random tag, and put the same tag in the pointer. On every access the hardware compares the two. Walk the four buttons. A reading its own memory: tags match. One granule past its end: that memory belongs to B and the tags differ (allocators usually give neighbours different tags), so it stops. Free A and use it: the memory was retagged, so the old pointer no longer matches: usually. "Usually" is the trade-off: with 4-bit tags a random new tag equals the old one one time in sixteen. Run the trials: about 6%. Pick 2-bit tags and it's a quarter; 8-bit, well under 1%. And the last button: an overflow inside the same 16-byte granule isn't seen at all.
    • ShowApple's version adds secure typed allocators and keeps the tags confidential from side channels, and runs the check synchronously, so the program stops at the bad access. Apple's own post says some classes, such as overflows inside a single allocation, survive.
    • CheckFrom Android's MTE documentation I verified: a tag granule is a 16-byte aligned chunk; MTE can't detect an overflow within the same granule; synchronous mode stops at the faulting access, asynchronous mode only later; it targets use after free and buffer overflow. The 4-bit tag size is confirmed by the Linux kernel's arm64 MTE documentation: "a 4-bit allocation tag for each 16-byte granule", with the pointer's tag in bits 59 to 56 of the address. Apple (security.apple.com, Memory Integrity Enforcement, 9 September 2025): all models of iPhone 17 and iPhone Air, A19 and A19 Pro, EMTE in synchronous mode; "minimal performance impact" is Apple's own claim, not independently measured here, and the surviving class it names is "intra-allocation buffer overflows". Whether every allocator gives neighbouring allocations different tags is an implementation choice that I haven't verified for each; the demo assumes it. The trials use a seeded random generator, so the same button gives the same numbers each time unless you change the tag size.

    // CHECKPOINT 2 · 5 MIN
    Pause and discuss
    
  
    
    
    Talk with a neighbour for a couple of minutes, then we share answers.
    
    
      
      
    1. Why doesn't ASLR fix the underlying bug?
      Hint
      What does ASLR change, and what does it leave alone?
      Answer
      ASLR randomises where things are; it doesn't change what the code does. The out-of-bounds write or the dangling pointer still happens and still corrupts data. It only makes the next step harder for someone who needs to know addresses, and a bug that leaks an address can undo it.
      2. 
      
    2. Which mitigations would you want in a debug build, and which in production? Why might they differ?
      Hint
      Think speed, memory, and what you want to happen on a mistake.
      Answer
      Debug and test builds want the strongest detection (sanitizers, tagging in synchronous mode) because the cost is paid once by developers and every report is a bug found early. Production wants cheap, always-on hardening (zero-initialisation, a hardened allocator or standard library, canaries, CFI), plus hardware tagging where the platform provides it, because speed matters and a crash is a user-visible event.
      3. 
      
    3. With 4-bit tags, one stale pointer in sixteen is missed by chance. Why can that still be a very good deal?
      Hint
      What happens to an attacker who has to guess, and fails?
      Answer
      A miss on a failed guess is usually a crash, and a crash is noisy, so exploiting a tagged bug reliably is much harder. And for developers, tagging turns a large share of silent corruption into immediate, reproducible reports. It's a probabilistic catch, not a proof, which is why it complements safe languages instead of replacing them.

      Fuzzer and sanitizer: different jobsThe fuzzer finds an input that makes the program misbehave. The sanitizer makes the misbehaviour loud and explains it. Together: input plus report.
      
    
      
  
      
  
      ~7 min
      • SayA fuzzer runs your code over and over on mutated inputs, and watches for crashes and sanitizer reports. This is a toy: a tiny parser for an invented record format, with a planted bug (the length check says 16 but the buffer holds 8). Random bytes have to guess the magic byte R and the version 2 before the interesting code is even reached: here it almost never gets there. A coverage-guided fuzzer keeps any input that reaches new branches and mutates that: so it starts from a well-formed record, learns the gates, and steps toward the bug. Run it a few times with different seeds: it usually finds it, sometimes not, and random almost never.
      • Ask(Checkpoint question, preview) What's the difference between what a fuzzer finds and what a sanitizer reports? Answer: the fuzzer finds the input that reaches a failure; the sanitizer is what turns a silent memory error into a failure and says what and where. A fuzzer without a sanitizer misses silent corruption.
      • CheckThe parser, the numbers and the seeds are invented: this is not a benchmark, and real random fuzzers do better on simple formats than the toy suggests. The gate bytes (magic, version) are chosen to make the point; real formats have the same kind of gates: magic numbers, checksums, length fields. Real engines are libFuzzer, AFL++ and Honggfuzz (OSS-Fuzz's README names these); as of May 2025 OSS-Fuzz's README says it has helped identify and fix over 13,000 vulnerabilities and 50,000 bugs across 1,000 projects: figures from the README (re-read 11 November 2026), which I haven't cross-checked. Developer 17 in this series, Fuzzing for Developers, covers fuzzing in depth.

      How safe languages stop the bug
      
  
      
    
      
      
      
      
      
        
      C and C++
      
        
      Go, Java, C# …

      Managed languagesA garbage collector frees memory only when nothing refers to it, and every index is checked. The price: some speed and memory, and less control.
      
      
      RustNo collector. Ownership and borrowing are checked when you compile, so a use after free or an invalidated reference doesn't build. Indexes are still checked at run time.
      
      
      "unsafe" is still thereRust has an escape hatch for the places that need it. In Android's Rust, about 4% of the code is in unsafe blocks: a small area to review hard, instead of everything.

The middle column, from the languages' documented behaviour, is that you can't free memory manually, and indexes are checked. The categories aren't ranked by quality: it's a question of when the mistake is found: never, at run time, or before the program exists.

      // MEMORY-SAFE LANGUAGES 02
      Where to start in a big C++ codebase
      
  
      
    
      
      
      An invented codebase. Pick the three components you'd move first:
      
      
      
      
      
      
      
    
      
    
      
      
      New code firstStop adding to the pile: write new components in a memory-safe language. Most of your future bugs live in code you haven't written yet.
      
      
      Then the riskiest parsersCode that reads untrusted input and has a bug history: file and network parsers, decoders. Small and self-contained wins first.
      
      
      Keep the border smallSafe and unsafe code talk through a narrow, reviewed interface, with binding tools to help. Fuzz that boundary.
      
      
      Not a big-bang rewriteRewriting everything stalls features and adds new bugs. The goal is a falling curve, not a flag day.
      
    
      
  
      
  
      ~6 min
      • SayTick three. The scoring rule is mine and deliberately simple: how much untrusted input reaches the component counts double, its history of memory bugs counts once, and a small component gets a small bonus because it is cheaper to move. You'll see your score against the best three. The image decoder, the network handler and the font code win because attackers can feed them anything. The settings UI loses because nobody sends a hostile file to a button. Crypto routines score low here not because they don't matter but because they're small, reviewed, and handle little untrusted input.
      • Ask(Checkpoint question, preview) Where would you start in your own codebase? Answer: wherever untrusted bytes are parsed in C or C++, and any new component.
      • CheckThe codebase, the scores and the weights are invented for teaching, not a standard method. The ONCD report (February 2024) suggests rewriting the critical functions and libraries most at risk and building new products in memory-safe languages; I read that through press coverage and the report's own title, not the full PDF. Binding tools (bindgen, cxx and similar) are mentioned from background knowledge, not checked here.

      // MEMORY-SAFE LANGUAGES 03
      What the guidance says, and what's already moving
      
  
      
    
        
      
      1. Feb 2024White House ONCD"Back to the Building Blocks": memory-safe languages for new products, memory-safe hardware, better metrics.
        2. 
      
      2. Jan 2025CISA and FBIProduct Security Bad Practices v2.0: manufacturers of critical-infrastructure software should publish a memory-safety roadmap by the end of 2025. Voluntary.
        3. 
      
      3. Jun 2025CISA and NSA"Memory Safe Languages: Reducing Vulnerabilities in Modern Software Development": memory-safe languages as the most comprehensive mitigation.
        4. 
      
      4. Sep 2025AppleMemory Integrity Enforcement: always-on hardware tagging and typed allocators on iPhone 17 and iPhone Air.
        5. 
      
      5. Nov 2025Google, AndroidMemory-safety vulnerabilities below 20% of the total for the first time.
        6. 
      
      6. Dec 2025Linux kernelMaintainers conclude Rust in the kernel is no longer "experimental" (reported by LWN).
        7. 
    
      
    
      
      
      What a roadmap holdsA prioritised list of components in memory-unsafe languages (network-facing and security-sensitive code first), a plan that shows a significant reduction in these bugs, and evidence of reasonable effort to follow it.
      
      
      It's guidance, not lawThe CISA text is voluntary. It exempts products whose end of support is before 1 January 2030. Check what applies to you.
      
      
      C++ is moving tooC++26 adds a hardened standard library and makes some uninitialised reads defined instead of undefined. Compiler support varies, so check yours.
      
    
      
  
      
  
      ~4 min
      • SayYou don't need to memorise dates. The pattern is what matters: in two years the advice went from "consider it" to "publish a roadmap", and the vendors who've done it are reporting results. The roadmap isn't "rewrite everything": it's a list of what you'll do first, and a number you can watch fall. If you ship software that matters to critical infrastructure, ask what your customers will expect to see.
      • CheckCISA and FBI Product Security Bad Practices: I read the CISA page: Version 2.0, January 2025 (version 1.0 was October 2024): "publish a memory safety roadmap by the end of 2025", for existing products in memory-unsafe languages used for critical infrastructure or national critical functions; exempt if end-of-support is before 1 January 2030; voluntary and non-binding. Some press coverage says 1 January 2026: use CISA's own wording. The June 2025 CISA and NSA information sheet: CISA's alert of 24 June 2025 ("New Guidance Released for Reducing Memory-Related Vulnerabilities") gives the title and the "most comprehensive mitigation" wording; I did not open the full PDF. ONCD: "Back to the Building Blocks: A Path Toward Secure and Measurable Software", February 2024; title and date confirmed from the White House PDF's listing and press coverage; I didn't read it in full. Apple and Google: their own posts, covered earlier. Linux: decided at the December 2025 Maintainers Summit and reported by LWN (a subscriber link, so read second-hand); Miguel Ojeda's patch "rust: conclude the Rust experiment" is dated 13 December 2025 on LKML, and he notes that some configurations (mixed GCC and LLVM builds, GCC support) are still experimental. C++26: P2795 (erroneous behaviour for uninitialised reads) and P3471 (standard library hardening, adopted at the February 2025 Hagenberg meeting) are both in C++26; whether a library is hardened is implementation-defined, compiler support varies (GCC implemented P2795 in late 2025, Clang's was still in review in 2026) and safety profiles were reported deferred: say "check your compiler".

      // CHECKPOINT 3 · 5 MIN
      Pause and discuss
      
  
      
    
      Talk with a neighbour for a couple of minutes, then we share answers.
      
    
        
      
      1. Where would you start introducing a memory-safe language in a large C++ codebase?
        Hint
        Think about untrusted input and about what you're about to write anyway.
        Answer
        Two places: new components from now on, and the existing code that parses untrusted input and has a history of memory bugs (decoders, protocol handlers, file parsers). Choose small, self-contained pieces with clean interfaces, keep the boundary narrow, and fuzz it. Leave stable, rarely exposed code for later.
        2. 
      
      2. What's the difference between what a fuzzer finds and what a sanitizer reports?
        Hint
        One supplies the input; the other turns the failure loud.
        Answer
        A fuzzer searches for an input that makes the program misbehave and keeps those inputs. A sanitizer instruments the program so that a memory error (an out-of-bounds access, a use after free) stops it and prints what, where and where the memory came from. Without a sanitizer the fuzzer only sees crashes; without a fuzzer the sanitizer only sees what your tests reach. Use them together.
        3. 
      
      3. If you wrote your team's memory-safety roadmap, what would the first three lines say?
        Hint
        Components, order, a number to watch.
        Answer
        For example: (1) new code in these areas is written in a memory-safe language by default; (2) these three parsers move first, in this order, with owners and dates; (3) we track the share of our security bugs that are memory-safety bugs and review it each quarter. Plus: tests run under sanitizers and the parsers are fuzzed meanwhile, so nothing waits for the rewrite.
        4.
