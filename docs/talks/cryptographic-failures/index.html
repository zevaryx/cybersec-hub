// RANDOMNESS AND KEYS 01 · CASE

Debian OpenSSL, 2006 to 2008: a cleanup removed the randomness

Design
OpenSSL stirs several inputs into a random pool, then makes keys from the pool.
Failure
A Debian-only patch, made to silence a memory-checker warning, removed the code that mixed in entropy. The process ID was the only variable left.
Found
Luciano Bello reported it; Debian's advisory DSA-1571 is dated 13 May 2008.
Impact
Keys made since the 17 Sep 2006 upload: SSH, OpenVPN, DNSSEC, X.509. 32,767 possible streams per architecture, so the list of weak keys is small enough to publish.
Fix
A fixed package, then regenerate every key made on an affected system. Blocklists and checkers (ssh-vulnkey, dowkd) find the known-weak ones.
Lesson
Nobody can see key generation. Test that two runs differ, and review changes to randomness code like a security patch.

SOURCES Debian DSA-1571-1 · Debian wiki: SSLkeys

~7 min

  • SayNothing was wrong with RSA or DSA. A well-meant change made the key generator draw from a pool with almost nothing in it. The keys looked fine: that is the problem with key generation, nobody can see it. Debian's own wiki calls the change "an overzealous, well-intentioned elimination of code".
  • ShowThe demo makes toy keys from a seed, the way the broken generator effectively did. Build the list with 15 bits: the list is complete in a moment, so a defender (or anyone) can list every weak key. Then make a weak key and check it: it is on the list. A good key comes from 128 random bits and can't be listed. Drag the slider to 18 bits to see the cost grow, and read the scale line: each extra bit doubles the work.
  • SayDebian's numbers: the wiki counts 32,767 possible random streams per architecture and 98,301 across the three it lists, which is why the blocklists were small enough to ship in packages. The advisory says all DSA keys ever used for signing or authentication on affected systems should be considered compromised, because a single signature made with a predictable value can reveal the key (the PS3 story, next but one).
  • TipThe control that would have caught it is boring: a test that generates two keys and checks they differ. Known-answer tests pass even when the generator is broken.
  • CheckDSA-1571-1 (13 May 2008), the Debian wiki and the Debian security team's detector are the sources; the exact date Bello found it isn't in the advisory. The demo's keys are 64-bit fingerprints of SHA-256 of a seed: invented, not OpenSSL's real format.

// RANDOMNESS AND KEYS 02 · CASE

ROCA, 2017: a key-generation shortcut with a public fingerprint

Design
RSA needs two big random primes. A chip library built them from smaller parts: faster on small devices, and it met certification rules.
Failure
The primes had a special form, so the keys carried far less entropy than their size. Not a bad random generator: a flaw in how primes were built.
Found
Masaryk University researchers noticed statistical oddities in smartcard public keys. Reported to the manufacturer in February 2017; public 16 Oct 2017.
Impact
Worst cases for 1024- and 2048-bit keys: under 3 CPU-months and about 100 CPU-years. Tens of millions of devices; ID cards, TPMs, tokens, PGP, software signing.
Fix
Library and firmware updates, replace affected keys, scan your public keys with the fingerprint test.
Lesson
Certified is not analysed. Keep an inventory of which chip made each key, and plan to rotate.

SOURCES Nemec et al., CCS 2017 (the researchers' paper) · CVE-2017-15361

The public-key fingerprint test toy keys

Public modulus20 small-prime testsResult

~7 min

  • SayROCA stands for Return Of Coppersmith's Attack: the researchers extended an older attack to this special prime shape. The important defender fact is in the paper's abstract: the keys contain "a strong fingerprint that is verifiable in microseconds", so everyone could scan their keys for it without knowing any secret.
  • ShowMake five keys from ordinary random primes: most tests fail, so they aren't flagged. Switch to structured primes (the toy follows the shape in the paper, with a shorter list of small primes): every test passes, every time. The test only reads the public modulus. Then read the odds line: with these 20 tests a random key passes about once in the number shown; the real test uses more primes (the paper's example is 2^-154 for 512-bit keys).
  • SayThe paper says the library was in FIPS 140-2 and Common Criteria EAL 5+ certified devices, and that the code dated to 2012 at the latest. Neither certification is a statement that the key-generation output was analysed for this. The lesson is not "certification is bad": it is "don't treat a label as a test of the output".
  • TipThis is the same family as Debian: the keys looked random, and only statistics over many public keys showed otherwise. Anyone with an inventory of public keys can run a check like this when a vendor publishes a pattern.
  • CheckNumbers are from the CCS 2017 paper (abstract and sections 1-4); I read the paper itself. The disclosure dates (reported 1 February 2017, public 16 October 2017) are from the researchers' own page as returned by search; that page (crocs.fi.muni.cz) didn't load here, so the paper link is the ACM CCS copy I read. The toy uses 112-bit primes and 20 small primes, not the real parameters, and the real library's format isn't reproduced.

// RANDOMNESS AND KEYS 03 · CASE

Sony PS3, 2010: a signing key recovered from signatures

Design
Game code is signed with ECDSA, and the console checks the signature before running it.
Failure
Each ECDSA signature needs a fresh, unpredictable value. Two signatures made with the same value let anyone compute the private key.
Found
The fail0verflow team presented it at 27C3 on 29 December 2010.
Impact
A private key that signs anything the console will run. Their slide: "With private keys you can SIGN THINGS."
Fix
In general: derive the value from key and message (RFC 6979) or use a vetted signing API, and never let application code pick it.
Lesson
The maths is two lines. A test that two signatures differ would have caught it.

SOURCE fail0verflow, "Console Hacking 2010", 27C3 (slides)

The algebra, from the talk's own slides

R = (m·G)x          S = (e + k·R) / m
e = hash of the data
m = random per signature
k = the private key

same m twice  →  same R, and
  m = (e1 − e2) / (S1 − S2)
  k = (m·S − e) / R
Where you've seen thisThe same mistake with an encryption nonce is What a repeated nonce breaks; the same algebra for a Schnorr proof is the extraction slide.

Their slide titled "Sony's ECDSA code" is a joke slide: a function that returns 4, "chosen by fair dice roll", borrowed from a well-known web comic. It illustrates the failure; it is not Sony's source code.

~4 min

  • SayHere the algorithm and the generator were not the problem: one value that must be fresh every time was not. The talk's own slide states the rule: "It is imperative to have a random m for every signature: from a pair of signatures that use the same m, we can compute m and k." The letters are theirs: m is the per-signature value and k is the private key.
  • ShowThe algebra. Subtract the two S equations and m falls out; then k does. No lattices, no cleverness.
  • SayBe careful with the joke slide: the slide deck shows a comic-style function that returns 4. It makes the point that a constant is not random. It is not a quote of Sony's code, so don't present it as one.
  • TipWhy this keeps happening: signing code looks like a pure function of key and message, so nobody tests it for freshness. Deterministic nonces (RFC 6979) remove the need for a good generator at signing time.
  • CheckThe date (29 December 2010) and the algebra are from the slide PDF, which I downloaded and read; I rendered the "Sony's ECDSA code" slide to confirm it is the joke slide. The statement that Sony's implementation reused the value comes from the talk and its coverage, not from Sony. Sony's response isn't covered here.

// RANDOMNESS AND KEYS 04 · CASE

Dual_EC_DRBG, 2007 to 2015: constants nobody could explain

Design
A NIST-standardised random generator (SP 800-90A) built on two elliptic-curve points, P and Q, with recommended values.
Failure
If whoever chose P and Q knows how they relate, a short stretch of output reveals the internal state, and every later output follows. The standard gave no hint how its points were chosen.
Found
Shumow and Ferguson (Microsoft) raised the possibility at the CRYPTO 2007 rump session. In September 2013, "in light of recent reports", NIST reopened its comment period.
Impact
It shipped in products. In December 2015 Juniper disclosed unauthorised code in ScreenOS: an admin backdoor (CVE-2015-7755) and VPN decryption (CVE-2015-7756).
Fix
NIST recommended against it (Sept 2013) and removed it in SP 800-90A Rev. 1 (June 2015). Juniper issued patched releases.
Lesson
Constants are part of the design: ask how they were chosen. And watch third-party code for changed constants.

SOURCES NIST SP 800-90 history · CERT/CC VU#640184 · Checkoway et al., Juniper analysis

2007back door possibility raised
Sep 2013NIST: stop using it
Jun 2015Rev. 1: "has been removed"
17 Dec 2015Juniper advisory public
  • The Juniper analysis (CCS 2016): contrary to Juniper's earlier statements, the ScreenOS VPN code had been vulnerable since 2008 to passive attack by whoever chose the Dual_EC curve point.
  • CERT/CC on the VPN issue: "There is no way to detect that this vulnerability was exploited."

This slide sticks to what NIST, the researchers and Juniper documented. Who, if anyone, held a back door is not established there and is not claimed.

~5 min

  • SayThis is a trust failure more than a maths failure: a standard with unexplained constants, adopted widely, and later a vendor whose own code was changed. The 2007 observation, in Finney's summary, was that if you know the discrete logarithm of one point relative to the other, you can recover the internal state from the output. The standard published a pair of points without saying how they were derived.
  • SayNIST's own page records the sequence: on 10 September 2013 it reopened the comment period, and the accompanying bulletin recommended that Dual_EC_DRBG no longer be used; in April 2014 and again in November 2014 it requested comments on a revision that removes it; Rev. 1 was published in June 2015.
  • AskWhat in your own supply chain has constants, curve points, seeds or parameters nobody on the team can explain? Look at VPN appliances, embedded libraries and anything with a "magic number" in its crypto setup.
  • TipDefences: prefer designs that explain their constants, diff third-party and firmware code for changed constants, and don't use one generator's output raw (mix sources). Crypto agility means you can switch away.
  • CheckI read NIST's historical page and CERT/CC's note. CERT/CC doesn't mention Dual_EC; the link between Juniper's issues and Dual_EC rests on the CCS 2016 paper's abstract (via its ePrint record) and the researchers' analysis, which I did not read in full. The 2007 rump-session detail is from secondary summaries of the talk. I downloaded SP 800-90A Rev. 1 (June 2015) and its change notes say "The Dual_EC_DRBG has been removed". Contested parts of the story are deliberately left out.

// CHECKPOINT 1 · 5 MIN

Pause and discuss

Talk with a neighbour for a couple of minutes, then we share answers.

  1. Debian, the PS3 and eMudhra (PKI in Depth) all failed at key generation or signing. What control would have caught each one?

    Hint

    What would a test, a reviewer and a monitor each have seen?

    Answer

    Debian: a test that two key generations differ, review of the patch, and a scan of keys against a blocklist. PS3: a test that two signatures differ, and a vetted signing API or deterministic values. eMudhra: checking the public output of key generation, and the public logging that let browsers react quickly. None of them could be seen from the outside by an ordinary user.

  2. Why can't users see this kind of flaw?

    Hint

    Look at a weak key next to a good one.

    Answer

    Key generation happens once, out of sight, and the result looks random either way. The Debian blocklist and ROCA's fingerprint exist because defenders examined many keys, not one.

  3. ROCA's library was in certified devices. What does that tell you about relying on a certification?

    Hint

    What did the certification test, and what did it not?

    Answer

    A certification is evidence that a process was followed, not proof that the output has no structure. Keep your own inventory, scan public keys when advisories appear, and keep lifetimes short enough to rotate.

5 min

  • ShowPairs talk for 2 minutes, then share. The timer starts by itself.
  • TipThe common thread for the room: key generation is never visible to users, so the controls are tests, reviews, scans of public output and short lifetimes.

// HASHES AND TRUST 01 · CASE

MD5, 2008 to 2012: from a rogue CA to Flame

Design
A certificate is signed over its hash. If nobody can build two certificates with the same hash, the signature can be trusted.
Failure
MD5 collisions were shown in 2004, yet some CAs still signed with MD5, with predictable serial numbers and issue times.
Found
2008: a team of seven researchers built a rogue CA certificate as a demonstration. 2012: Flame malware was found signed with a forged Microsoft certificate.
Impact
The forged certificate let malware pass as a Windows Update. Microsoft: "active attacks using unauthorized digital certificates derived from a Microsoft Certificate Authority."
Fix
Microsoft revoked trust in the affected intermediates through Windows Update (advisory 2718704, 3 June 2012).
Lesson
Retire a broken hash everywhere, including odd corners like a licensing service, and know every CA and key purpose you trust.

SOURCES Microsoft Security Advisory 2718704 · CWI, 7 June 2012 · Rogue CA project

  1. 2004First MD5 collision demonstrated
  2. 30 Dec 2008"MD5 considered harmful today": a rogue CA certificate, using about 200 PlayStation 3 consoles for the collision
  3. Jan 2009Microsoft stops accepting MD5-based signatures elsewhere, but one licensing CA path still did
  4. 3 Jun 2012Microsoft advisory: trust revoked for the Enforced Licensing intermediates
  5. 7 Jun 2012CWI: Flame used a new variant of a chosen-prefix collision attack
  • Per Microsoft's explanation, systems older than Windows Vista were exposed without any collision; on Vista and later the attackers needed one.
  • DigiNotar's lesson (2011) was "watch your CAs". Flame's (2012) is "retire the weak hash everywhere".

~5 min

  • SayTwo separate stories joined. In 2008 researchers showed the whole chain: a chosen-prefix MD5 collision, a CA that still signed with MD5, and serial numbers and issue times predictable enough to line things up. In 2012, malware used a collision against a Microsoft licensing CA to sign code as Microsoft. CWI's Marc Stevens found it was a new variant of the attack rather than the published one.
  • SayPer Microsoft's advisory, the update revoked trust in the Microsoft Enforced Licensing Intermediate PCA (two certificates) and the Microsoft Enforced Licensing Registration Authority CA (SHA1). CWI called the licensing path's continued MD5 acceptance "an important oversight". Microsoft's blog post "Flame malware collision attack explained" (6 June 2012) says older systems didn't need a collision and Vista and later did; I couldn't open that page, so this comes from its search snippet, and CWI's item says Microsoft's licensing customers also had code-signing ability without a collision.
  • AskWhere in your estate does an old hash still sign something? Think of code signing, internal CAs, SAML, firmware, and RADIUS (see the 2024 slide).
  • TipCertificate Transparency didn't exist yet. It is part of why a rogue certificate would be noticed sooner today: see PKI in Depth.
  • CheckI read Microsoft's advisory (published 3 June 2012, revised 13 June) and CWI's news item (7 June 2012). The 2008 details (30 Dec 2008, 25C3, about 200 PS3s, RapidSSL, predictable serials) are from the researchers' project page results and a mailing-list copy of their announcement: I didn't read the paper itself. The claim that Microsoft disallowed MD5 elsewhere in January 2009 is CWI's. "2004" is the date the Blast-RADIUS site gives for the first MD5 collision.

// HASHES AND TRUST 04 · REVISITED
DigiNotar and eMudhra, in six beats

  

    

      
DigiNotar, 2011

      

        
Design
A CA signs certificates that every browser trusts.

        
Failure
Intruders reached all eight CA servers and tampered with the logs.

        
Found
A routine check on 19 July; a rogue *.google.com certificate surfaced publicly on 28 August.

        
Impact
531 rogue certificates; about 300,000 users, 95% in Iran.

        
Fix
Browsers removed DigiNotar from their trust stores.

        
Lesson
Ship logs off the machine; watch the CAs you trust.

      

      
Full story: PKI in Depth, DigiNotar. Source: Fox-IT's report of 13 August 2012.

    

    

      
eMudhra, October 2026

      

        
Design
Subordinate CAs sign certificates under a trusted root.

        
Failure
Keys for eight intermediates "were generated with insufficient randomness" (Google).

        
Found
A researcher's report on Saturday 17 October.

        
Impact
None logged: no certificate had been seen in Certificate Transparency before the block.

        
Fix
Chrome blocked within two hours, Firefox within three, then the root was removed.

        
Lesson
It is Debian again: a badly made key is a key anyone can guess.

      

      
Full story: PKI in Depth, eMudhra. Sources: Google and Mozilla.

    

  

  
~3 min
  • SayYou've seen both of these in PKI in Depth, so this is only the six-beat summary. The point of putting them side by side is the "found" beat: DigiNotar was found after weeks of abuse; eMudhra was reported by a researcher and blocked in hours. What changed in fifteen years is public logs, pushed blocklists and published policies. What didn't change is that a badly made key is a key anyone can guess.

// MODES, PADDING AND NEGOTIATION 01 · CASE
Padding oracles, 2002 to 2017: when an error message is an answer

  

    

      

        
Design
Encrypt in CBC mode with padding and a MAC. On receipt, decrypt, check the padding, then check the MAC.

        
Failure
How the receiver reacts to bad padding (an error, a delay) says whether the padding was valid. That is a decryption oracle for anyone who can send altered messages.

        
Found
Vaudenay (EUROCRYPT 2002); Lucky Thirteen, AlFardan and Paterson (4 Feb 2013); POODLE, Möller, Duong and Kotowicz at Google (Sept 2014); ROBOT, Böck, Somorovsky and Young (Dec 2017).

        
Impact
Lucky Thirteen: full plaintext recovery against OpenSSL. POODLE: secure cookies from SSL 3.0 sessions. ROBOT: 27 of the top 100 domains had vulnerable subdomains.

        
Fix
AEAD cipher suites, encrypt-then-MAC (RFC 7366), one identical error for every failure, no RSA key exchange, and no SSL 3.0 (RFC 7568).

        
Lesson
Fail the same way every time, and authenticate before you decrypt or parse.

      

      
SOURCES Lucky Thirteen · POODLE advisory · ROBOT · RFC 7366

    

    

      

        
POODLE · CVE-2014-3566In SSL 3.0's CBC the padding isn't covered by the MAC, so it can't be fully checked. Clients that retried with older versions after a failed handshake could be pushed into SSL 3.0 by a network attacker.

ROBOT · 2017"The return of a 19-year-old vulnerability": Bleichenbacher's 1998 oracle on RSA key exchange, still leaking from servers. The fix is to turn RSA key exchange off.

        
Why AEADAn authenticated cipher suite rejects any altered message before it looks at padding. TLS 1.3 allows only AEAD ciphers.

  • SayThe family resemblance is the point. Different decades, different protocols, the same shape: a receiver does something with unauthenticated input and then reveals, by an error or by timing, how far it got. The mitigation is also the same shape: reject altered messages at the authentication step, before any padding or format check, and answer every failure identically.
  • SayFrom the POODLE advisory: CBC padding in SSL 3.0 "is not deterministic, and not covered by the MAC", and "unlike with the BEAST and Lucky 13 attacks, there is no reasonable workaround", so SSL 3.0 had to be avoided entirely. That is why RFC 7568 prohibits it.
  • TipLucky Thirteen's page lists the long-term advice: move to AEAD cipher suites such as AES-GCM. Random delays were not effective, and RC4 was only a stopgap.

Why distinguishable errors leak

  

    

      

        
        
      

      

      

      

    

    

      
    
        
  • The toy has an 8-byte block cipher (a made-up 4-round network) in CBC mode, with PKCS #7 padding. It is not a real cipher.
    • 
        
  • The grid asks the toy server about 256 altered messages: each changes one byte of the block before the target.
    • 
        
  • With distinct errors ("padding OK" or "bad padding"), exactly one answer differs. That cell reveals the last byte of the hidden block.
    • 
        
  • With one uniform error every cell is the same. The server tells nobody anything.
    • 
      

      
The defenceAuthenticate first: check a MAC over the whole message (or use AEAD), and answer every failure the same way and in the same time. Then there is no question to ask.

      
Teaching code on invented data. Real attacks repeat this for every byte and need many sessions or a vulnerable server; none of that is automated here.

  • SayWe only show one byte, one position, on a toy. The point is the information flow, not a recipe. A receiver that says "bad padding" versus "bad MAC" has told the sender something that only the key holder should know.
  • AskWhat are the ways a server can answer differently without printing a different message? Timing, a different HTTP status, a different connection behaviour, a log line the sender can read.

FREAK, Logjam, DROWN: the weakest option wins

  

    

      
FREAK · 3 March 2015Found: "Factoring attack on RSA-EXPORT Keys"; CVE-2015-0204 in OpenSSL, with similar bugs elsewhere. Impact: 36.7% of HTTPS servers with browser-trusted certificates at disclosure. Fix: disable export suites; update TLS libraries and browsers.

  • Lesson: backwards compatibility is attack surface. Test every service, including mail and appliances.

    // MODES, PADDING AND NEGOTIATION 05 · CASE
    Sweet32, 2016: a cipher that was fine until the data grew
    
  
    
    
    
      
    
        
    Design
    3DES and Blowfish encrypt in 64-bit blocks. In CBC mode, repeated blocks start to appear sooner than you'd expect.
    
        
    Failure
    With 64-bit blocks the birthday bound is about 232 blocks: roughly 32 GB under one key. Long-lived connections go past it.
    
        
    Found
    Bhargavan and Leurent at Inria; CCS 2016, August 2016. CVE-2016-2183 (TLS) and CVE-2016-6329 (OpenVPN).
    
        
    Impact
    They recovered a two-block HTTPS cookie from 610 GB captured over 30.5 hours, and an OpenVPN token in 18.6 hours (705 GB). At least 0.6% of HTTPS connections were vulnerable.
    
        
    Fix
    Stop using 64-bit block ciphers, or cap the data per key. NIST later disallowed three-key TDEA encryption after 2023.
    
        
    Lesson
    Ciphers have limits on data per key, not just on key size. Something has to enforce the limit.
    
      
    
      
    SOURCES sweet32.info · NIST: withdrawal of SP 800-67 Rev. 2
    
    
    
    
    
      
    How much data until blocks collide?
    
      
    
        
        
      
    
      
    
        
    –blocks to reach the birthday bound
    
        
    –data under one key
    
        
    –to send that at this speed
    
      
    
      
    
      
    The bound is where repeated blocks become likely, not where an attack finishes: the researchers needed about 236.6 blocks (785 GB) for their full cookie attack.
    
    
    
  
    
  
    ~3 min
    • Say3DES wasn't broken by a clever new attack. It was used for longer connections than a 64-bit block can safely carry. The same birthday arithmetic you ran on the hash slide applies to blocks: after about 2^32 of them under one key, two will match, and in CBC a match leaks the XOR of two plaintext blocks.
    • ShowSwitch between 64-bit and 128-bit blocks at 100 Mbit/s: 64-bit reaches the bound in under an hour of saturated 100 Mbit/s traffic (hours at 10 Mbit/s); 128-bit blocks need an astronomically larger amount.
    • TipThis is why TLS 1.3 and modern libraries limit the data per key and rekey (RFC 8446 section 5.5 is titled "Limits on Key Usage"; the nonces slide in Using Crypto Correctly in Code covers how long a key lasts).
    • CheckAll Sweet32 numbers (32 GB bound; 785 GB / 2^36.6; 610 GB in 30.5 h; 18.6 h and 705 GB for OpenVPN; 0.6%) are from sweet32.info, which I read.     CRIME and BREACH, 2012 to 2013: compression leaks length
    
  
    
    
    
      
      
        
    • Design: compress a response, then encrypt it. Both are fine on their own.
      • 
        
    • Failure: if a secret (a token) and text the attacker controls are compressed together, matching text compresses smaller, and encryption doesn't hide length.
      •

    • Lesson: encryption hides content, not size. Treat length as output.

    // PROTOCOLS, CODE AND LESSONS 01 · CASE
    KRACK, 2017: a proof that didn't cover the step that broke
    
  
    
    
    
      
    
        
    Design
    WPA2's four-way handshake derives fresh keys and installs them; the cipher's nonce is a packet counter that must never repeat under a key.
    
        
    Failure
    Message 3 of the handshake can be retransmitted, and a client that installs the key again resets its counter. A repeated nonce reuses the key stream.
    
        
    Found
    Mathy Vanhoef and Frank Piessens (KU Leuven), disclosed 16 October 2017. Ten CVEs (CVE-2017-13077 to -13088 in part).
    
        
    Impact
    Worst on Linux's wpa_supplicant 2.4 and later, and so Android 6.0 and later: they could be tricked into installing an all-zero key.
    
        
    Fix
    Backwards-compatible patches on both clients and access points. Changing the Wi-Fi password doesn't help; "keep using WPA2".
    
        
    Lesson
    A proof covers what it models. Test the state machine: retransmission, loss and replay, not only the happy path.
    
      
    
      
    SOURCE krackattacks.com (the researchers' site)
    
    
    
    
    
      
    The proof question, in the researchers' words"The brief answer is that the formal proof does not assure a key is installed only once." The proofs covered key secrecy and handshake authentication, not when keys are installed.
    
      
      
        
    • This is nonce reuse again, in a protocol: see What a repeated nonce breaks. The difference is that the implementation, not the application, reset the counter.
      • 
        
    • WEP before it was broken in 2001 (Fluhrer, Mantin and Shamir; practical key recovery by Stubblefield, Ioannidis and Rubin the same year). WPA followed in 2003 and WPA2 in 2004. Sources differ on the exact retirement dates.
      • 
        
    • HTTPS or a VPN on top of Wi-Fi limits what one broken link exposes.
      • 
      
    
    
    
  
    
  
    ~4 min
    • SayThis is the case that most changed how people think about proofs. The handshake had been analysed and proven secure for secrecy and authentication. The break was in an action the proof didn't describe: installing the same key twice. The fix is also instructive: it's a change to the client's behaviour, not to the cryptography.
    • AskWhere in your own protocols does a "reinstall", "retry" or "resume" path exist that a spec and a test suite might not exercise? Think of session resumption, token refresh, handshake retransmission and key rollover.
    • TipThe page says both client and AP must be patched to defend against all attacks, and that routers can reduce exposure by disabling client or repeater modes and fast roaming (802.11r).
    • CheckI read krackattacks.com. The disclosure date (16 October 2017) isn't printed on the page itself; it is dated by the press items it links. The WEP 2001 papers are from IACR/Springer and AT&T technical-report listings as returned by search, and the WPA (2003) and WPA2 (2004) dates are from the Wi-Fi Alliance's history as summarised by several sources that disagree slightly about WEP's "retirement". The earlier timeline slide uses "WPA2, 2004" only as an approximate start.

    // PROTOCOLS, CODE AND LESSONS 02 · CASE
    Heartbleed, 2014: not a crypto bug at all
    
  
    
    
    
      
    
        
    Design
    OpenSSL implemented the TLS heartbeat extension (RFC 6520): a peer sends some data and a length, and the other side echoes it back.
    
        
    Failure
    The code trusted the length it was given and read past the data. OpenSSL calls it "a missing bounds check" that can reveal "up to 64k of memory". A programming mistake, not a flaw in the protocol.
    
        
    Found
    Neel Mehta of Google Security and a team at Codenomicon, in early April 2014. Fixed in OpenSSL 1.0.1g on 7 April 2014. CVE-2014-0160.
    
        
    Impact
    Anyone could read server memory: secret keys, passwords, session data. Netcraft counted about 17% of SSL web servers with trusted certificates, around half a million.
    
        
    Fix
    Patch to 1.0.1g or later, revoke and reissue certificates, invalidate sessions, then change passwords. Or rebuild without heartbeats.
    
        
    Lesson
    Crypto libraries are programs: fuzz them, review them, use memory-safe code for parsers, and rehearse key rotation.
    
      
    
      
    SOURCES OpenSSL advisory, 7 Apr 2014 · heartbleed.com · Netcraft
    
    
    
    
    
      
      
        
    1. Dec 2011The vulnerable code is written
      2. 
        
    2. 14 Mar 2012OpenSSL 1.0.1 is released with it
      3. 
        
    3. 3 Apr 2014Discovered
      4. 
        
    4. 7 Apr 2014Fixed release and public disclosure
      5. 
      
    
      
      
        
    • heartbleed.com: "Exploitation of this bug does not leave any trace of anything abnormal happening to the logs." That is a logging lesson as much as a coding one: see Logging, Monitoring and Incident Response.
      • 
        
    • Forward secrecy limits what stolen keys unlock later. It wouldn't help against memory that holds live session data.
      • 
      
    
    
    
  
    
  
    ~4 min
    • SayNot every cryptographic failure is cryptography. Heartbleed sits in the same category as any parser bug: a missing bounds check. What made it a crypto event is where it lived and what was in the memory next door: private keys.
    • SayRecovery had four steps, and the site lists them: patch, revoke compromised keys and reissue, invalidate session keys and cookies, then password changes once trust is restored. Netcraft later reported many sites reissued certificates and some reused the same private key, which defeats the point.
    • AskIf one of your TLS keys leaked tonight, how long would reissue and revoke take, end to end? This is the "crypto agility" question again.

    Blast-RADIUS · CVE-2024-3596 · public 9 July 2024
    
      
    
        
    Design
    RADIUS authenticates server replies with a home-made MD5 construction from the 1990s.
    
        
    Failure
    An attacker on the path can use an MD5 chosen-prefix collision to turn a "Reject" into an "Accept" without the shared secret.
    
        
    Found
    Researchers from several universities and companies; coordinated by CERT/CC.
    
        
    Fix
    Require the Message-Authenticator attribute; move to RADIUS over TLS or DTLS. EAP-only deployments are unaffected.
    
        
    Lesson
    It's the Flame lesson again, 12 years on: a legacy protocol still leaning on MD5.
    
      
    
    
    
    
    
      
    EUCLEAK · Yubico YSA-2024-03 · 3 September 2024
    
      
    
        
    Design
    A hardware security key keeps ECDSA private keys on a chip, using a vendor crypto library.
    
        
    Failure
    A side channel in the library's ECDSA code could let someone with the device and equipment recover a private key.
    
        
    Found
    Dr. Thomas Roche of NinjaLab reported it to Yubico on 19 April 2024.
    
        
    Fix
    Newer firmware (5.7, and 2.4.0 for the HSM) uses Yubico's own library. Yubico says affected keys can't be updated in the field.
    
        
    Lesson
    Hardware you can't patch needs a replacement plan, and a threat model that includes physical possession.

It's the same chip-maker family as ROCA, but a different flaw by a different team; the advisory doesn't connect them and neither should you.

    • AskWhere do you disagree? ROBOT (implementation of a legacy design), FREAK (client bugs plus legacy suites) and Flame (a weak hash and a process gap) are good ones to argue about.

    What almost every break had in common, and what helps
    
  
    
    
    
      
      
        
    1. Legacy kept for compatibility.SSL 3.0, export suites, MD5, 3DES, SSLv2.
      2. 
        
    2. Keys nobody can see being made.Debian, ROCA, the PS3, eMudhra.
      3. 
        
    3. Behaviour that answers.Error messages, timing and length: padding oracles, CRIME and BREACH.
      4. 
        
    4. Parts left unauthenticated or unmodelled.SSL 3.0's padding; KRACK's key installation step.
      5. 
        
    5. Complexity and unexplained choices.Dual_EC's constants; negotiation that could be steered.
      6. 
        
    6. The library, not the maths.Heartbleed, ROBOT's servers, EUCLEAK.
      7. 
      
    
      
    Controls that help: known-answer tests (but they miss weak randomness), fuzzing, independent review, formal analysis (only of what it models), transparency logs, short lifetimes, and crypto agility: the ability to change algorithms and keys quickly.

    How to check, without payloads
    
      
      
        
    • Read configuration and versions first: TLS settings, library versions, firmware versions, and vendor advisories for every crypto library, HSM and smartcard you use.
      • 
        
    • Use standard, well-known scanners against your own servers to list protocol versions and cipher suites. Name what you scan, and get permission for anything you don't own.
      • 
        
    • Check public keys and certificates you already hold: key sizes, hash algorithms, issuers and expiry.
      • 
        
    • Write down who owns each key and how you would replace it in a day.
