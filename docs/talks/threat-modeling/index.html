// WHY THIS WORKSHOP

Some problems are in the design, not the code

A bug is code that doesn't do what the design says. A flaw is a design that does exactly what it says, and that's the problem.

  • A reset link that works for any account number isn't a typo: the design never said whose link it was.
  • An admin function that the client simply hides works as designed. The design forgot the server.
  • Scanners and tests look for what the code does. Nothing in the code says what's missing.

Sources: Threat Modeling Manifesto · OWASP Threat Modeling Cheat Sheet

Cheapest while it's a drawingMoving a box on a whiteboard costs a minute. Moving where data lives, or who may call what, costs a quarter. No number needed: you've felt this.
It's a conversation firstThe Manifesto puts it plainly: "people and collaboration over processes, methodologies, and tools". The value is the shared picture, not the document.
It can be smallA 15-minute pass on one changed flow beats a 40-page model nobody opens. We'll practise the small version.

~3 min

  • SayAsk how many people have fixed something in production that was, honestly, a design decision. The point is that some security problems are decisions: nobody wrote the check because nobody decided there should be one. A threat model is a structured way to find those decisions while they're cheap to change.
  • AskThink of the last "bug" you fixed that took a design change. Could someone have asked about it a month earlier? Answer: usually yes, and that question is what we're practising.
  • TipThe quotation is from the Threat Modeling Manifesto's values ("People and collaboration over processes, methodologies, and tools"), read on its site on 11 November 2026. The three examples are generic illustrations, not a specific incident. There's no cost-of-fixing multiplier on the slide on purpose: the famous numbers are shaky.

// THE FOUR QUESTIONS 01

Four questions are the whole method

  1. 1 · What are we working on?Produces a diagram: who, what runs, where data rests, how it moves.
  2. 2 · What can go wrong?Produces a list of threats, found with prompts rather than inspiration.
  3. 3 · What are we going to do about it?Produces decisions: a fix, a design change, a hand-off or an accepted risk with an owner.
  4. 4 · Did we do a good enough job?Produces checks: tests, and a date to look again.

Source: Threat Modeling Manifesto, which uses these four questions (Adam Shostack's framing, shorter on his own site: "Did we do a good job?").

Try it on a small thing: a password reset

~8 min

  • SayEverything else today is a way of answering these four. Click through the password-reset example: it's small enough to do in your head, and it uses all four. Notice question 4 produces something concrete: tests, and a date.
  • ShowClick the four buttons in order, and read each answer aloud. The answers are an illustration of the shape, not a complete model of a reset flow.
  • AskWhich question would your team skip if you were short of time? Answer: usually the fourth, and it's the one that makes the exercise worth repeating.
  • CheckThe Manifesto page (no date shown on the page, PDF labelled "release 1") says "Did we do a good enough job?". Shostack's own page words it "Did we do a good job?"; the OWASP cheat sheet follows the Manifesto. The slide says "good enough" and notes the difference. Re-read the Manifesto before presenting.

// THE FOUR QUESTIONS 02

When it's worth doing, and how big to make it

What does the change do? Tick all that apply

Or try an example

  • Triggers: a new boundary, new kind of data, new third party, or a change to who may do what.
  • Fit it into what you already do: design reviews, big changes and new vendors, not a separate ceremony.
  • Revisit when the system changes: a model nobody updates is a historical document.

~7 min

  • SayYou don't threat-model every pull request. Four questions about a change decide how much: does it cross a trust boundary that's new, handle new data, add a third party, or change who's allowed to do what? None of them means a one-line note. One means a quick pass. Two, a short session. Three or more, a workshop. This is a rule of thumb I use, not a standard.
  • ShowPress the example buttons, then tick your own. Try "Let admins impersonate users": only one trigger, but it's a big one, which is the limit of counting. Say so: the counter is a starting point and judgement overrides it.
  • TipThe OWASP cheat sheet says to threat model early in the lifecycle and treat it as a standard step, and to maintain the model as the system changes. The trigger list and the sizes on this slide are the speaker's own guidance, not from a standard.

// CHECKPOINT 1 · 5 MIN

Pause and discuss

Talk with a neighbour for a couple of minutes, then we share answers.

  1. Is a threat model a document or a conversation?

    Hint

    What does a document capture, and what does a conversation create?

    Answer

    Both, in that order. The shared understanding comes from the conversation; the document records it so it can be checked and updated.

  2. A teammate changes a button's colour. Do you threat model it?

    Hint

    Count the four triggers.

    Answer

    No: it crosses no boundary, adds no data, party or permission. A one-line note in the pull request is plenty.

  3. Which of the four questions turns a one-off into a habit?

    Hint

    Which one has a date in it?

    Answer

    The fourth: checking the model and the fixes against reality, and looking again when the system changes.

5 min

  • ShowPairs talk for 2 minutes, then share. The timer starts by itself.

// DRAWING THE SYSTEM 01

Data-flow diagrams: four kinds of thing

  • Data moves through processes. Two stores or two outside parties don't talk directly: something runs in between.
  • Name things with nouns, and flows with what moves, not "data".
  • Draw one level first. If it doesn't fit on a whiteboard, split it.
  • A process that only receives is a black hole; one that only sends is a miracle. Both mean something is missing.
  • The STRIDE letters on the left are the prompts each kind earns: that's why the kind matters.

~7 min

  • SayFour shapes are enough. Something outside our control (a person, another company). Something that runs our code. Somewhere data rests. And the arrows. The reason to bother with kinds is on the left of each card: each kind of thing has its own list of what can go wrong, which saves you from asking six questions of everything.
  • ShowClick through the four. Tick "logs" on a data store: it earns an extra letter, Repudiation, because logs are where "who did that?" is answered. Processes earn all six; outside parties only two, because we don't control them, we only decide what to trust from them.
  • CheckThe "STRIDE per element" chart: the usual version has external entities S and R, processes all six, stores and flows T, I and D, with stores that hold logs also earning R. Confirmed against Microsoft's own description of STRIDE-per-element (Larry Osterman's MSDN blog, September 2007, archived on Microsoft Learn, read 11 November 2026): external entities Spoofing and Repudiation; processes all six; data stores Tampering, Information Disclosure, Denial of Service "and repudiation", with a note that logs in data stores are "almost always the mitigation against a repudiation threat"; data flows Tampering, Information Disclosure, Denial of Service. Shostack's book adds that data-flow spoofing is contested. The Threat Dragon and Microsoft tools may mark these slightly differently, so still call it "the usual chart".
  • Next"Trust boundaries."

// DRAWING THE SYSTEM 02

Trust boundaries: where the rules change

Flows that cross a boundary

    • A boundary is where who controls it, or what it's allowed to do, changes.
    • Crossings are where to start: checks belong at the line, on the side we control.
    • Inside a zone isn't safe, just shared trust. Boundaries can sit inside our own cloud too.

    ~8 min

    • SayA trust boundary is a line you draw where the situation changes: a different owner, a different network, a different level of permission. Switch the highlight on: the pink arrows cross a line, and most of what goes wrong happens at one. The app on the phone is in the user's hands, so anything it says is a claim, not a fact. The payment provider is somebody else's computer.
    • ShowToggle the boundaries and crossings off and on. Read the list on the right aloud: each crossing is one place to ask who's calling, whether the data could have changed, and what happens if it's too much.
    • AskWhere would you draw a boundary inside "Our cloud"? Answer: between the public API and the image processor, which handles untrusted files; and around the audit log, which admins shouldn't be able to edit.
    • TipThe OWASP cheat sheet says a useful DFD shows trust boundaries and notes they often mark possible attack points. The three zones and the photo app are invented for the workshop.
    • Next"Exercise 1: draw one."

    // EXERCISE 1 · 15 MIN

    Draw it: a photo-sharing app

    The brief

    People take photos on a mobile app and upload them to an API. Photos are kept in storage and a worker makes thumbnails. Accounts live in a user database, and admin actions go to an audit log. Subscriptions are paid through an outside payment provider, which calls back with a webhook. Groups: draw it, then compare with the reference.

      ~15 min

      • ShowGroups of three or four. Five minutes to read the brief and add elements and flows; five to put each element on the right side of a line; then compare with the reference answer. Elements sit in columns by zone, so the zone is the trust boundary. The builder points out common mistakes: a flow that skips a process, a process that only receives or only sends, everything in one zone.
      • SayDon't aim for completeness. Aim for an argument: "is the audit log inside our cloud or separate?" is exactly the useful kind. If two groups disagree about where a line goes, that's the finding.
      • TipReference answer: 8 elements (User, Mobile app, API, Image processor, Photo storage, User database, Audit log, Payment provider) and 9 flows, with 3 crossing a boundary (app to API, API to the payment provider, and the webhook back); the user to the app stays inside the device zone. Prepare for groups that draw the user as a process, or skip the webhook: both are good conversations.
      • CheckThe element names, zones and flows are the workshop's own sample, not a real product. On a phone the diagram scrolls sideways inside its box.

      // FINDING THREATS 01

      STRIDE: six questions, one for each way to break a promise

      Which kind of thing earns which letter

      • Each letter breaks a property you wanted: authenticity, integrity, accountability, confidentiality, availability, authorization.
      • Go per element and per flow: for every box and arrow, ask its letters. It's a checklist, not an inspiration contest.
      • Start at the boundary crossings from the last slide.
      • Write one sentence per threat: who does what, and what goes wrong.
      • Not a finding yet: "we use TLS". That's a response. The threat is what TLS is for.

      Sources: Microsoft Learn: STRIDE · OWASP cheat sheet

      ~8 min

      • SaySTRIDE is a mnemonic from Microsoft's security work, and each letter is the opposite of something you wanted to be true. Click through them. The table at the bottom shows which letters each kind of thing earns. Processes get all six; an outside party only gets spoofing and repudiation, because we can't tamper with their systems, only decide what we believe from them.
      • ShowClick each letter and read the question. Ask for one example from the room per letter before showing the slide's example.
      • TipMicrosoft's page says the Threat Modeling Tool uses STRIDE and describes each category; OWASP lists the same six with the property each violates (for Repudiation OWASP says "accounting"; Microsoft says non-repudiation). The slide says "non-repudiation (accountability)". The "defence" column is the speaker's summary.
      • CheckThe per-element chart is the usual one, confirmed against Microsoft's 2007 STRIDE-per-element post (see the notes two slides back).
      • Next"A worked example, then the reference answer."

      // FINDING THREATS 03

      Threat cards: prompts to draw when you're stuck

      • Four prompts per STRIDE suit. Draw one, pick an element or flow from your diagram, and answer it for that thing.
      • No threat? Say why not in one line: that's also a result.
      • Rotate the card-holder so the loud person doesn't hold every card.
      • Published decks exist: Elevation of Privilege (Shostack, 2010, Creative Commons) and OWASP Cornucopia. These 24 prompts are our own.

      Sources: Elevation of Privilege game · OWASP Cornucopia

      ~6 min

      • SayStuck groups are the norm, not the exception. Cards turn a blank page into a question: "a webhook arrives from the provider: how would we know it was?" Draw one per round, aim it at a specific box or arrow on your diagram, and answer it.
      • ShowDraw a few. Filter to a suit (Repudiation is usually the one people leave out). Show all 24 to see the whole deck at once.
      • TipElevation of Privilege was created by Adam Shostack in 2010 after Laurie Williams described Protection Poker, and its files are Creative Commons licensed (shostack.org/eop, read 11 November 2026). OWASP Cornucopia is a separate deck for web and mobile apps, listed as a Production project at version 3.5. The 24 prompts here are written for this workshop; they aren't a copy of either deck. Printing is not built in: take a screenshot of the grid, or use the real decks.

      // FINDING THREATS 04

      Privacy threats, and people using the system "wrongly"

      LINDDUN: the privacy cousin of STRIDE

      Abuse cases: ask what a legitimate user could do

        Sources: LINDDUN (KU Leuven DistriNet) · OWASP cheat sheet

        ~5 min

        • SaySTRIDE asks what an attacker can break. Privacy asks a different question: what does the system know about people, and who can learn it? LINDDUN has seven prompts, from linking and identifying to non-compliance. Use it when the system holds personal data. Abuse cases are the same idea from another side: nobody is "attacking" anything, they're using the system out of order, repeatedly, at the same moment, or for a purpose it wasn't meant for.
        • ShowClick through the seven. Notice "non-repudiation" appears on both lists but means the opposite: for security you want people not to be able to deny an action; for privacy, sometimes you want them to be able to.
        • CheckThe seven names come from linddun.org (read 11 November 2026), which lists Linking, Identifying, Non-repudiation, Detecting, Data Disclosure, Unawareness and Non-compliance, and credits the DistriNet Research Unit at KU Leuven. The site showed no version number; some publications add "and unintervenability" to Unawareness. The examples are the speaker's. The abuse-case prompts follow the OWASP cheat sheet's description (workflows used out of order, repeatedly, concurrently or for unintended outcomes) with two extras added.
        • Next"Attack trees."

        // FINDING THREATS 05

        Attack trees: start from what they want

        • OR branches are alternatives: the attacker takes the cheapest. AND branches need every step: costs add.
        • Click a step to add a defence. Watch the cheapest path move, not vanish.

        ~8 min

        • SaySTRIDE walks the diagram. An attack tree starts from one thing an attacker wants and works backwards: how could they get there? OR nodes are alternatives and the attacker takes the cheapest; AND nodes need every step. The costs are an invented "effort" scale, not dollars. The point is the second click: defend the cheapest path and the next cheapest becomes the new weakest point.
        • ShowStart with nothing defended: the cheapest path is a one-step API change. Defend it, and it moves to the storage branch (two steps). Keep going until every path costs about the same: that's balance. Defend everything and the tree says no path remains, which really means "no path we thought of".
        • AskWhat did we leave out of this tree? Answer: the user is tricked into sharing it themselves, a bug in an image library, a stolen backup. A tree is only as complete as the people drawing it.
        • TipBruce Schneier's "Attack Trees" (Dr. Dobb's Journal, December 1999) is the classic source: the goal is the root, ways to reach it are the nodes below, with OR and AND nodes and values like cost that propagate up (article read 11 November 2026). The photo-app tree and every number are invented.

        Find at least two threats per letter

          ~15 min

          • ShowBack at your group's diagram. Each group logs threats here: pick the element or flow, the letter, and one sentence. The six chips fill up to two each. The hint under the target shows which letters that kind of thing earns, as guidance rather than a rule. If a group is stuck, "Add the reference threats" loads 16 sample ones: use them to compare, not to copy. If you built your own diagram, targets come from it; otherwise the photo app is used.

          // CHECKPOINT 2 · 5 MIN

          Share your most surprising threat

          Each group shares one, then we compare notes.

          1. Which threat surprised you most, and on which element or flow?

            Hint

            Think about the one you'd never have found without the prompt.

            Answer

            No single answer. The useful part is that it came from a prompt (a letter, a card, a boundary), not from inspiration: that's repeatable.

          2. Which letters were hardest to fill?

            Hint

            Which ones are about how the system behaves, rather than what a clever attacker does?

            Answer

            Often Repudiation and Denial of service: they're about missing records and limits, which are easy to overlook. If that was your group, that's normal, and those gaps are often the cheapest to fix.

          3. Did you find anything that wasn't about the diagram at all?

            Hint

            Think about people, processes and the build pipeline.

            Answer

            Good: note it. Threats outside the diagram usually mean the diagram needs another box, or a second diagram for the process around it.

          5 min

          • ShowTake one surprise per group in turn. Listen for the ones that came from a boundary crossing. The timer starts by itself.

          // DECIDING AND FOLLOWING UP 01

          Ranking: likelihood × impact, kept simple

            Where your threats fall

            • Three levels each, because finer scales invent precision nobody has.
            • Rate as a group, and write down why a rating moved.
            • It ignores how hard the fix is: a high threat with a one-line fix goes first.

            ~7 min

            • SayYou can't fix everything on day one, so you rank. Likelihood times impact, three levels each: nine possible scores. Don't argue the difference between a 6 and a 7; argue about whether it's high or low. And if everything comes out a 9, the scale has stopped telling you anything, so re-rate relative to each other.
            • ShowLoad the reference threats (or use your own from exercise 2). Change a rating and watch the list reorder and the grid update. Set every threat to 3 and 3 to see what that does.
            • TipThe OWASP cheat sheet says, in theory, rank by likelihood multiplied by impact, notes this is hard to calculate and ignores the effort to fix, and that some teams add effort to the prioritisation. The bands (1 to 2 low, 3 to 4 medium, 6 and 9 high) and the 1 to 3 scales are the speaker's convention for the workshop, not a standard; CVSS and other scoring systems exist for vulnerabilities, not for design threats.
            • CheckReference ratings are the speaker's judgement: groups will disagree, and that discussion is the point.
            • Next"Responses."

            // DECIDING AND FOLLOWING UP 02

            Responses: four answers, each with an owner

            MitigateAdd a control that makes it harder or less harmful.
            EliminateChange the design so it can't happen: drop the feature, data or permission.
            TransferSomeone better placed takes it on: a provider, a contract, insurance.
            AcceptKnowingly live with it, written down, with an owner and a date to look again.

            ~7 min

            • SayFour possible answers, and "ignore it" isn't one of them. Eliminate is the best and the one teams forget: can we simply not hold that data? Accept is legitimate, but only if it's written down with a name and a date. The most common bad response is an accepted risk that nobody owns and nobody revisits.
            • ShowThe top three threats by rank appear here. Choose a response, add an owner and a few words about the fix. Try accepting one with no owner or no date: the page won't call it done.
            • TipMitigate, eliminate, transfer and accept are the common four; some lists use "avoid" or "reduce" and call them "treat". Owners are people by name; "the platform team" is acceptable only if it exists and someone there has said yes. The review date defaults to 90 days from today, which is the speaker's habit, not a rule.
            • Next"Writing them down."

            // DECIDING AND FOLLOWING UP 03

            Write threats as tickets, with a test that says "done"

            
      
            
    
            
    
            
      
              
        
            • A ticket has where, what goes wrong, the response, an owner and a way to know it's done.
              • 
        
            • "Done when" is a test: given, when, then. If you can't test it, you can't tell it's fixed.
              • 
        
            • Put it in the same backlog as everything else. A separate security list is a list nobody schedules.
              • 
        
            • Link the ticket back to the diagram and the threat, so a later change can find it.
              • 
      
            
      
            
    
            
  
            
  
            ~6 min
            • SayA threat that lives in a document doesn't get fixed. It has to become a ticket in the place the team already works, with a clear "done". The test sentence is the important part: "given a user without the role, when they call the function, then the server refuses it" is something a developer can turn into an automated test, and which then keeps the fix from quietly regressing.
            • ShowChoose a threat from the list. The ticket is built from the fields you gave it: ratings, response, owner and fix. The "Done when" line is a template per letter: edit it for the real system. Without a log, the list shows the reference threats.
            • TipThe ticket format and the test templates are the speaker's convention, not a standard. Use whatever your tracker supports.
