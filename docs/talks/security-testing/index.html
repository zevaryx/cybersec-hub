A talk on Security Testing in Your Workflow

Security testing shouldn't be a once-a-year event. Which tools catch what, the tests only you can write, and how to fit checks into your pipeline without drowning in noise.

// WHY THIS TALK

Find it where it's cheap to fix

  1. Design"Should anyone be able to do this?"
  2. EditorA linter or a secret check
  3. Pull requestA test goes red; a reviewer asks
  4. PipelineScans and longer tests
  5. ProductionA scan, or a customer
  6. The outside worldA researcher, or a criminal
Cheaper, earlierThe same bug costs a one-line fix in the editor and an incident response at the far end. I'm not quoting a multiplier: the point is the direction.
Tools see patternsA scanner finds what it was built to look for. It can't know who should be allowed to see an invoice.
The goal is a fixA report nobody acts on is just a more expensive way to feel informed.

~3 min

  • SayWalk left to right: every step to the right is more people, more context lost and less time. Then the three ideas that run through the talk: earlier is cheaper, tools find patterns while tests state your rules, and the output that matters is a fix.
  • AskWhere do most of your security bugs get found today? Answer: usually the far right: production, a pentest or a report. Moving that left is the whole talk.
  • CheckThere's a well-known claim that bugs cost a fixed multiple more to fix later. Its sources are famously weak, so the slide deliberately gives the direction and no number. Don't add one unless you have your own data.

    // THE TOOLBOX 02

    Static analysis: patterns, and their blind spots

    
      
    
        
        
      
    
      
    
      
    
    
    
    
    
      
    
      
    A toy scanner of about thirty lines, built for this page. Real tools are far more capable; the shape of the blind spots is the same.
    
    
    
  
    
  
    ~6 min
    • SayStart with snippet A in pattern mode: it finds the query built from a string. Then B: the query is built in another file, so the scanner never sees it. Then D: it's safe because the table name is checked against an allowlist, but the pattern match flags it, a false alarm. Switch to "follow the data" and D goes quiet, because the value no longer comes from the request. Finally E: nothing is wrong with the code that's there. A check is missing, and no scanner flags something absent.
    • AskThe scanner reports nothing on E. Is E safe? Answer: no, anyone can read anyone's invoice. A clean report means "no known patterns", not "no bugs".
    • TipReal analyzers go further than this toy: cross-file data-flow analysis, framework knowledge and queries you can write yourself. GitHub's code scanning can run its own CodeQL engine or a third-party tool, and results from third-party tools travel in SARIF, an open OASIS standard (2.1.0, approved in March 2020, errata edition August 2023). Their blind spots are of the same shapes: logic, missing checks and anything the rules don't model.
    • CheckPointing out where the toy scanner differs from products is fine; don't claim a particular product misses snippet B, because many follow data across files.

    // THE TOOLBOX 03
    Dynamic scanning: probe the running app
    
  
    
    
    
      
    What it's good atIt sees what a browser sees: security headers, cookie flags, error pages, exposed files, reflected input, forms that behave oddly. It doesn't need your source code or your language.
    
      
    What it struggles withAnything behind a login it hasn't been given. Anything it can't find by crawling. Rules it can't know: user A may not read user B's invoice needs two logged-in users and an idea of whose data is whose.
    
    
    
    
    
      
    Two styles, both useful
    
      
      
        
    • Passive baseline. Browse the app and look at the responses, without attacking. ZAP's baseline script works this way: its own docs say it doesn't perform "actual attacks", runs the spider for about a minute by default and suits CI, "even against production sites".
      • 
        
    • Active, authenticated scans. Log in as real test users and try things. Slower and noisier, and it changes data: run it against a test environment you own.
      • 
      
    
      
    RULE Only scan systems you own or have written permission to test. A scan against someone else's site isn't "just testing".
    
    
    
  
    
  
    ~4 min
    • SayDynamic scanning is the opposite view to static: no source, just the running thing. That's its strength, because it finds problems that only exist when everything is deployed together (headers added by a proxy, a debug page switched on), and its weakness: it can only test what it can reach and what it knows to look for. The cheap, safe place to start is the passive baseline in your pipeline against a staging site.
    • AskA scanner reports no issues on your staging site, but it never logged in. What has it told you? Answer: about the login page and the public pages. Nothing about the application.
    • TipZAP is open source and is now branded "ZAP by Checkmarx" on its own site, which calls it "an independent Open Source project". Several write-ups still call it OWASP ZAP, and sources disagree on how formal the OWASP link remains, so the slide says only "ZAP". The baseline facts above are from its documentation page for the baseline scan. Its docs show docker run -t ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t https://www.example.com, with -m setting the spider minutes; re-check before showing it live.
    • CheckThe OWASP Web Security Testing Guide (latest stable 4.2 at my last check, with 5.0 in development) is the reference for what a manual tester looks at, if you want a next step.
    • Next"Two scanners that read lists, not code."
    

    


    
  
    // THE TOOLBOX 04
    Dependency and secret scanning
    
  
    
    
    
      
    Dependencies: your list vs a database
    
      
      
        
    • Reads your lock file, and compares each version with a database of known vulnerabilities (GitHub's Dependabot alerts use the GitHub Advisory Database).
      • 
        
    • Fast, and the most reliable "free win": the fix is often just an upgrade.
      • 
        
    • The catch: "present" isn't "reachable". Most flagged functions aren't ones you call. Go's govulncheck reports only the vulnerabilities your code can reach, and GitHub is adding reachability analysis to Dependabot, in a public preview for JavaScript and TypeScript at the time of writing.
      • 
      
    
    
    
    
    
      
    Secrets: a pattern, found early
    
      
      
        
    • Token formats are recognisable, so detection is precise and the signal is high.
      • 
        
    • Push protection blocks the push and says why. Secret-scanning alerts report after the secret has already landed. The first is far better.
      • 
        
    • A bypass is a decision, not a hole: GitHub asks for a reason ("used in tests", "false positive", "I'll fix it later") and the last one stays an open alert.
      • 
        
    • Anything found is revoked first, cleaned up second.
      • 
      
    
    
    
  
    
  
    ~4 min
    • SayBoth of these read lists and patterns rather than understanding code, which makes them fast and precise. For dependencies the big lesson is that a finding isn't an exploit: the question to ask is "can my code reach it?". For secrets it's about timing: the cheapest moment is before the commit. We have a whole talk on keeping secrets out of code (Secrets Management).
    • AskA critical CVE appears in a library you use in a build script only. How urgent is it? Answer: it depends on what it processes. A build-time tool fed only your own files is rarely urgent. Record why, and upgrade routinely.
    • TipRead against primary pages: GitHub's push-protection docs (the three bypass reasons and how each is recorded), the Dependabot alerts page (reviewed advisories from the GitHub Advisory Database; optional reachability analysis described as a public preview supporting JavaScript repositories using npm, pnpm or Yarn, and TypeScript repositories, at the time I read it) and the Go blog on govulncheck (reports only vulnerabilities in functions your code transitively calls). The Gitleaks README says the project is "feature complete" and that the author is moving to a successor, so check its status before recommending it for a new setup.
    • CheckPreview features move quickly: re-read the Dependabot reachability page before presenting. Which scanner names your audience uses matters more than the ones I mention.
    • Next"And the strangest one, in one slide."
    

    


    
  
    // THE TOOLBOX 05
    Fuzzing in one slide
    
  
    
    
    
      
    A fuzzer feeds a function huge numbers of generated inputs, steered by what code they reach, and watches for crashes, hangs and broken promises. In Go it's built in:
    

    func FuzzParse(f *testing.F) {
    f.Add("1,2,3")                 // a seed input
    f.Fuzz(func(t *testing.T, s string) {
        got, err := Parse(s)
        if err != nil { return }   // rejecting is fine
        if Render(got) != s {      // a promise it must keep
            t.Errorf("round trip failed for %q", s)
        }
    })
}
    
    
    
    
    
      
      
        
    • Great for: parsers, decoders, anything that takes bytes from outside.
      • 
        
    • Needs: a harness you write, and a property to check ("doesn't crash", "round-trips").
      • 
        
    • Free regression test: a failing input is saved under testdata/fuzz and re-run on every plain go test.
      • 
        
    • Related idea: property-based testing (Hypothesis for Python), with the same "for all inputs…" thinking.
      • 
      
    
      
    LATER IN THIS TRACK Fuzzing for Developers (Developer 17) goes deeper. For now: one harness for your riskiest parser is a good start.
    
    
    
  
    
  
    ~3 min
    • SayFuzzing is the one tool here that doesn't read code for patterns or compare against a list: it just tries a very large number of inputs and sees what breaks. Because the harness states a property, it also finds logic bugs, not just crashes. Three lines of seed and a property check is a real harness.
    • TipThe shape of the Go harness (FuzzXxx taking *testing.F, f.Add for seeds, f.Fuzz for the body, and a failing input written under testdata/fuzz and replayed by a plain go test) is from Go's fuzzing tutorial, which I read. The Parse and Render functions are invented for the slide. Hypothesis describes itself as a property-based testing library for Python; I didn't verify its example-database behaviour, so the slide doesn't mention it.
    • CheckOther languages have similar tools (for example cargo-fuzz and Atheris); I haven't checked their current state, so the slide names only Go.

    // CHECKPOINT 1 · 5 MIN
    Pause and discuss
    
  
    
    
    Talk with a neighbour for a couple of minutes, then we share answers.
    
    
      
      
    1. Your static analyzer reports nothing. What kinds of bugs could still be there?
      Hint
      Think of the empty rows in the tool map, and snippet E.
      Answer
      Anything that isn't a pattern in the code: a missing authorization check, a business-logic flaw (a coupon used twice), a vulnerable dependency, a misconfigured server, and data flows the tool doesn't model, such as a query built in another file. "Nothing found" means "none of my rules matched".
      2. 
      
    2. You turn on a new scanner and it reports 400 findings on its first run. What do you do, and what do you not do?
      Hint
      What is different about old findings and new ones?
      Answer
      Don't ask the team to fix 400 things at once, and don't silence the tool. Record today's findings as a baseline so the pipeline fails only on new ones, then triage the baseline in the background, highest risk first. We'll build this later in the talk.
      3. 
      
    3. Which tool would have caught a leaked cloud key, and when is the best moment for it to run?
      Hint
      Which row in the map has a strong tool, and where in the timeline is a secret still cheap to remove?
      Answer
      A secret scanner, ideally as push protection or a pre-commit check, so the key never reaches the repository. If it does get in, revoke the key first: scanning and deleting don't help once someone has copied it.
      4. 
    
    
  
    
  
    5 min
    • ShowPairs talk for 2 minutes, then share. The timer starts by itself.
    

    



    
  
    // TESTS YOU WRITE 01
    Authorization tests: "A can't read B's data"
    
  
    
    
    
      
    
        
        
      
    
      
    
      
      
      
      
    
      
    
      
      
      The test that went red
      
      
      
      
      
      
      The recipeCreate two users, and for each action write one test where the right user succeeds and one where the wrong user is refused. Check the status and that nothing changed.
      
    
      
  
      
  
      ~7 min
      • SayThis is the test no tool can write for you, because only you know who should be allowed to do what. Pick a bug and exactly one test goes red, and its name says what broke. Now the uncomfortable half: untick that test (it's the checkbox beside it) and the bug sails through, all green. A suite is only as good as the rules it states. Write the "wrong user" test for every action you add, not just the "right user" one.
      • AskWhich of these bugs would your current tests catch? Answer: for most teams, only the happy-path ones: "the owner can read their invoice" passes whatever the bug.
      • TipThe API is a mock written for this page: three invoices, three users, and five switchable bugs, each covered by exactly one test. In a real project the same tests run against your app through its test client. The "admin by header" bug is the classic of trusting a role from the client; the server must decide who's an admin.
      • Next"Same idea for what users send you."
      

      


      
  
      // TESTS YOU WRITE 02
      Input-handling tests: nasty strings
      
  
      
    
      
      
      
      
      
    
      
    
      
      
      
      
      
        
        
      
      
      
      
      
      
      
      Test the property, not just examples"The result never contains a slash, a dot-dot, a control character, a reserved name, or more than 100 characters." Then feed it the whole battery.
      
    
      
  
      
  
      ~7 min
      • SayHere's a function every upload feature needs: turn a user's filename into something safe to store. Three versions of increasing care, and the same twelve inputs. Version 1 removes ".." and fails nearly everything. Version 2 deals with slashes and control characters, and still lets through percent signs, device names, a ten-thousand-character name and a right-to-left override. Version 3 allows only a short safe alphabet and caps the length. The test isn't clever: it's a list of nasty strings and the properties you want to hold. Keep the list in your repo and add to it whenever something odd breaks you.
      • AskWhich of these would a code review have caught? Answer: slashes, probably. The right-to-left override and the Windows device names, rarely. That's what a battery of test strings is for.
      • TipThe properties are a teaching list, not a complete standard: real needs differ by filesystem and platform, and often the best answer is to ignore the user's filename entirely and store the file under a generated ID. Windows device names (CON, PRN, AUX, NUL, COM1 to COM9, LPT1 to LPT9) and the trailing dot or space behaviour are well known platform quirks that I did not re-verify against Microsoft's current documentation. The percent-encoded case matters because some other layer may decode it later.
      • Next"And what to do after you've found a bug."
      

      


      
  
      // TESTS YOU WRITE 03
      A regression test for every bug you fix
      
  
      
    
      
      
        
        
      1. Reproduce it as a test first. It should fail for the reason in the report.
        2. 
        
      2. Fix the code. The same test now passes.
        3. 
        
      3. Prove the test can fail. Take the fix away, run it, see red, put the fix back.
        4. 
        
      4. Name it after the rule, and point to the report in a comment.
        5. 
        
      5. Look for siblings. If one endpoint forgot the check, test them all.
        6. 
      
      
    
      
    
      

      $ git stash push src/invoices.py     # take the fix away
$ pytest tests/security/test_invoices.py
FAILED test_other_user_cannot_read_invoice
$ git stash pop                      # put it back
$ pytest tests/security/test_invoices.py
9 passed
      
      
      WHY A bug that came back is the most embarrassing kind, and the cheapest to prevent. The test is the memory your team keeps.
      
    
      
  
      
  
      ~5 min
      • SayEvery security bug is a free test case: you've just learned exactly what the code did wrong. Step three is the one that's skipped: a test that has never been seen failing might not test anything. The git-stash trick takes ten seconds. Step five is where bugs come in pairs: if one endpoint forgot the owner check, ask which others did.
      • AskWhere does a regression test live so it isn't deleted in a refactor? Answer: in the normal test suite, with a name that states the rule, so removing it looks like removing the rule.
      • CheckThe terminal is an illustration with invented file names. Adjust the commands to your language and test runner.
      • Next"Now: where do all of these run?"
      

      



      
  
      // FITTING IT IN 01
      Fast checks on every commit, slow ones nightly
      
  
      
    
      
      
      
        
        
      
      
      
        
    
        
    
        
      
          
      
          
      
            
      
            
    
            
  
            
  
            ~6 min
            • SayTwo measures decide where a check belongs: how fast it is and how good its signal is. Fast and precise things run early, even before the commit: a secret scan on the diff, a formatter. Medium things run on the pull request: your tests, a dependency scan, a short fuzz run. Slow and noisy things run after merge, nightly or weekly, and report. The default is "everything on every pull request", which looks safe and teaches your team to wait, and then to skip. Click the suggested layout and compare the warnings.
            • AskWhich check does your team skip today, and how long does it take? Answer: usually the slowest one. Move it later instead of arguing about it.
            • TipThe durations and the stage budgets (10 seconds, 10 minutes, 30 minutes, 8 hours, 24 hours) are teaching numbers I chose, not measurements of any product. Your own pipeline's times matter more. A check that fails the build should be fast and nearly always right; a slow or noisy one should report, not block, until you trust it.
            • Next"What to do with a finding you can't fix today."
            

            


            
  
            // FITTING IT IN 02
            Baselines and suppressions with a reason and an expiry
            
  
            
    
            
      
            
        
        
      
            
      
            
        
        
      
            
    
            
    
            
      
              
      
              
      
              The three things a suppression needsA reason a stranger can check, an owner who can answer for it, and an expiry date, so "not now" can't become "never" by accident.
              
    
              
  
              
  
              ~6 min
              • SayTwo tools for living with a noisy scanner. A baseline says "these findings exist today, fail only on new ones", which lets you adopt a scanner on a big old codebase without a freeze. A suppression says "this one is acceptable, here's why". The linter on the right is the policy: no reason, no owner or no expiry and the line is flagged, and an expired one is flagged too, because the finding is back. The sloppy file has one good line and four bad ones.
              • TipHow real tools do it, from their docs: Semgrep accepts an inline nosemgrep: rule-id comment on the line or the one above, and its docs describe no inline syntax for a reason (the platform has an "ignore reason" when triaging); OSV-Scanner's config file takes an id, an optional reason and an optional expiry named effectiveUntil; Gitleaks can ignore a single finding by its fingerprint in a .gitleaksignore file, which its README calls experimental, and can compare against a baseline report with --baseline-path. The file format in the demo is invented, and so are the rule names. The 180-day expiry limit and the 15-character reason minimum are my suggestions, not standards.
              • CheckIf your audience uses a different scanner, replace the examples with its suppression syntax. The idea carries over: where the tool has no field for a reason or an expiry, put them in a comment and enforce them with a small script, like this one.
              • Next"Now the game: real or noise?"
              

              


              
  
              // FITTING IT IN 03
              Triage: real, or noise?
              
  
              
    
              
      
              
      
              
      
              
        
        
      
              
    
              
    
              
      
              
      
              
      
              
      
      
              
      
              Four questions for any findingIs it true? Can an attacker reach it in our setup? What would it cost us? Who owns the fix, and by when?
              
    
              
  
              
  
              ~7 min
              • SayFive invented findings, one at a time. Ask the room to call each, then reveal. The SQL injection is real. The fixture password is noise, and so is AWS's own documented example key. The critical library CVE is the interesting one: it isn't reachable from your inputs, so "critical" doesn't describe your risk, but "we never call it" is itself a claim, so you write it down with an owner and an expiry. The fifth is a live token in an old commit, and that's today's problem.
              • AskWhat extra evidence would move the TIFF finding from "noise" to "real"? Answer: finding any upload path that decodes TIFF, such as an admin import or a thumbnailer. That's why a failing test is better than a belief.
              • TipAll five findings, files and names are invented. AKIAIOSFODNN7EXAMPLE is the example access key ID from AWS's documentation. Severity scores describe a vulnerability in general: the CVSS specification itself says the Base score reflects intrinsic severity and that you enrich it with threat and environmental information, "a more comprehensive input to risk assessment". For ranking, two public signals help: EPSS (FIRST's model of the probability a CVE will be exploited in the next 30 days) and CISA's Known Exploited Vulnerabilities catalogue, which CISA says to use "as an input to their vulnerability management prioritization framework", and which we covered in the Vulnerability Management talk.
              • Next"How do you know any of this is working?"
              

              


              
  
              // FITTING IT IN 04
              Measure time to fix, not the number of findings
              
  
              
    
              
      
              Day 80 for a team that fixes what it finds. Now change something:
              
      
              
        
        
      
              
      
              
      
              
    
              
    
              
      
                
        
              • Time to fix (median, and the slowest) says whether the team acts.
                • 
        
              • Age of the oldest open finding says what's being ignored.
                • 
        
              • The count goes up when you improve your tools, and down when you hide things. It can't tell you whether you're safer.
                • 
        
              • Escapes: bugs found after release that a check should have caught, each one a hole to close.
                • 
      
              
      
              The 54 findings, their dates and their fix times are invented for this demo.
              
    
              
  
              
  
              ~4 min
              • SayStart with the baseline: 24 findings over 80 days, 6 still open, median 7 and a half days to fix. Add the scanner: the count jumps to 54 and 7 are open, and the dashboard looks worse. But the median time to fix hardly moves: the team is fine, the tooling got better. Now reset and suppress the old findings: the open count falls and the median doesn't move, because nothing was fixed. The count can be fooled in both directions; time to fix and age are much harder to fake.
              • AskIf leadership asks for one number, which? Answer: a time-to-fix for the issues that matter (the high-severity ones), plus what escaped.
              • CheckEverything here is simulated. Real teams need to define when the clock starts (found? triaged?) and what counts as fixed. Don't quote a "good" time-to-fix from this slide: pick your own target from your own history.
              • Next"Another pause."
              

              


              
  
              // CHECKPOINT 2 · 5 MIN
              Pause and discuss
              
  
              
    
              Talk with a neighbour for a couple of minutes, then we share answers.
              
    
                
      
              1. How would you write a test that proves a user can't see another user's data?
                Hint
                How many users do you need, and what are the two assertions?
                Answer
                Create two users and a record owned by one. Ask as the other user, assert that the response is a refusal (403 or 404, whichever your API uses) and that the record's contents aren't in the body. Then repeat for every action: read, change, delete, list. And write the test first, so you've seen it fail.
                2. 
      
              2. Your dependency scanner flags a critical CVE in a library you use. How do you decide what to do?
                Hint
                Is the vulnerable code reachable, and what does the attacker need?
                Answer
                Check whether your code can reach the affected function, with what input, and whether the vulnerability is being exploited in the wild. If it's reachable or exploited, treat it as urgent and upgrade. If it isn't, suppress it with a reason, an owner and an expiry, and upgrade in the next routine update.
                3. 
      
              3. Which one metric would you show your manager instead of "number of findings", and why?
                Hint
                Which number goes down only when something real was fixed?
                Answer
                Time to fix for serious findings (and the age of the oldest one open), plus bugs that escaped to production. Counts rise when tools improve and fall when findings are hidden. Time to fix and escapes measure behaviour and outcomes.
