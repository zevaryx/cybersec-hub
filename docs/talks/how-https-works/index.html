// BEFORE 02

Finding the server: DNS

    Who saw the name?

    Plain DNS questions travel unencrypted, so your Wi-Fi and internet provider can read every site name you look up. Encrypted DNS ("DNS over HTTPS") hides them from the network, but the resolver you choose still sees them.

    ~5 min

    • SayComputers connect to numbers, not names. DNS is the internet's phone book.
    • ShowPress "Look it up": the resolver asks the root, then .com, then example.com's own name server, and caches the answer. Then tick "Encrypted DNS" and look again: the Wi-Fi and internet provider drop off the "who saw" list.
    • SayEncrypted DNS moves trust; it doesn't remove it. Someone still answers the question.
    • TipThe IP shown is a documentation address, not example.com's real one.

    // HANDSHAKE 01
    The handshake's three jobs
    
  
    
    
    
      
    Agree on keysMake a shared secret in public, over a network anyone can watch.HOWKey exchange (ECDH, plus ML-KEM)
    
      
    Prove who it isShow that this really is example.com, not an impostor in the café.HOWA certificate and a signature
    
      
    Detect meddlingMake sure nobody altered the handshake messages along the way.HOWA "Finished" checksum over everything
    
    
    
    
    TLS 1.3 does all three in a single round trip: one message from your browser, one reply from the server, and the browser can already send its request.
    
  
    
  
    ~4 min
    • SayThree jobs: agree on keys, prove identity, detect meddling. If any fails, no page.
    • SayCrypto 101 covered each piece: key exchange, signatures, and tags. The handshake glues them together.
    • Next"Let's run one for real."
    

    


    
  
    // HANDSHAKE 02
    A live TLS 1.3 handshake
    
  
    
    
    
      
    
        
        
      
    
      
      
    
      
    
      
      
      
      
      
      
      
    
      
  
      
  
      ~10 min
      • SayEvery value here is real: a real P-256 key exchange, real HKDF key derivation as TLS 1.3 does it, real signatures and real AES-GCM. Only the message formats are simplified.
      • ShowDrag through the 8 steps. 1–2: hellos, sent in the clear, each with a public key share; the site name is visible. 3: both sides compute the same secret. 4: keys are derived; everything after this is encrypted.
      • Show5: the certificate chain, checked signature by signature. 6: the server signs the whole conversation so far with the certificate's private key. 7: both send "Finished" checksums. 8: the actual request, encrypted.
      • Tip"New connection" makes fresh keys every time: that's forward secrecy.
      

      


      
  
      // HANDSHAKE 03
      Agreeing on keys, today and after quantum
      
  
      
    
      
      
      browser's key sharecombined secretserver's key share
      
      
        
        
      • ECDH (usually X25519): both sides mix their secret with the other's public share and reach the same value. Crypto 101's paint demo, for real.
        • 
        
      • Fresh keys every connection: steal the server's long-term key later and old recordings still stay locked (forward secrecy).
        • 
        
      • Hybrid with ML-KEM: major browsers now combine X25519 with the post-quantum ML-KEM, so traffic recorded today stays safe from future quantum computers.
        • 
      
      
    
      
    
      
      
      What each side knows
      
      
      
        
      BrowserNetworkServer
      
        
          
      Browser's secretyesnono
      
          
      Both public sharesyesyesyes
      
          
      Server's secretnonoyes
      
          
      Shared session keysyesnoyes
      
              
      
      
      
      The network sees both public shares, but turning them back into the secret is the hard puzzle from Crypto 101.
      
    
      
  
      
  
      ~4 min
      • SayThe key exchange is the paint-mixing idea from Crypto 101, done with elliptic curves.
      • SayForward secrecy: every connection uses throwaway keys, so a stolen server key later can't unlock old traffic.
      • SayHybrid post-quantum: browsers already send an ML-KEM share alongside X25519. Breaking the connection would need breaking both.
      

      


      
  
      // HANDSHAKE 04
      Certificates: proving it's really the site
      
  
      
    
      
      
      Break something and watch what your browser does.
      
      
      
        
        
        
        
      
      
      
      
    
      
    
      
      
      
      
      
    
      
  
      
  
      ~5 min
      • SayThe browser ships with a list of trusted root authorities. A root signs an intermediate, which signs the site's certificate. The browser checks every link, the name, and the dates.
      • ShowTick each problem one at a time and read the warning it causes. Then untick them all: padlock.
      • SayThese signatures are real P-256 signatures, made fresh when the page loaded.
      

      


      
  
      // HANDSHAKE 05
      Why TLS 1.3 is faster
      
  
      
    
      
      
    
      
    
      
    
      
  
      
  
      ~3 min
      • SayEach back-and-forth costs one round trip. TLS 1.2 needed two before the request; TLS 1.3 needs one; HTTP/3 (QUIC) merges the connection and the handshake.
      • ShowDrag the slider up to a slow mobile or satellite link: the savings grow with distance.
      • SaySecurity got stronger and faster at the same time: TLS 1.3 also removed old, weak options.

      Talk with a neighbour for a couple of minutes, then we share answers. Guesses are welcome.
      
    
        
      
      1. Why does the browser need a certificate at all, if the key exchange already creates a shared secret?
        Hint
        Who did you exchange keys with?
        Answer
        Without it you could have a perfectly secret conversation with an impostor. The certificate and signature prove the other end is really the site.
        2. 
      
      2. An attacker records your encrypted traffic today and steals the server's private key next year. Can they read today's traffic?
        Hint
        Which key encrypted the conversation?
        Answer
        No, with forward secrecy: the session keys came from throwaway key shares that were deleted. The server's key only proves identity.
        3. 
      
      3. Why are browsers adding ML-KEM to the key exchange now, before big quantum computers exist?
        Hint
        Harvest now, decrypt later.
        Answer
        Traffic recorded today could be decrypted later by a quantum computer. Adding ML-KEM now protects today's recordings.
        4. 
    
      
  
      
  
      5 min
      • ShowPairs talk for 2 minutes, then share.
      • SayQ1 is the big one: encryption without authentication is a private chat with a stranger.
      • TipTiming: Part 2 should finish around minute 52.
      

      



      
  
      // AFTER 01
      Encrypted records
      
  
      
    
      
      
      
      
      
        
        
      
      
      
      
      
      
    
      
    
      
      
        
        
      • Everything after the handshake travels in records: a 5-byte header, then encrypted bytes, then a 16-byte tag.
        • 
        
      • The header is readable: it says "application data" and the length.
        • 
        
      • Each record uses a new nonce (a counter), so nothing repeats.
        • 
        
      • One flipped bit and the tag fails: the connection closes.
        • 
      
      
      
      LENGTH LEAKS Encryption hides content, not size. Sites can pad records, but most don't.
      
    
      
  
      
  
      ~5 min
      • ShowType a longer request: the record grows by exactly as much. Tick "pad": now different requests look the same size.
      • ShowFlip a bit: decryption fails and TLS closes the connection with a "bad_record_mac" alert. AES-GCM from Crypto 101, doing its job.
      • Next"So what can the network still learn?"
      

      


      
  
      // AFTER 02
      What the network still learns
      
  
      
    
      
      
      
      
    
      
    
      
    
      
  
      
  
      ~4 min
      • SayWith plain HTTPS, your Wi-Fi and internet provider still see which site, its IP address, and how much and when. Never the page, your cookies or your data.
      • ShowTick encrypted DNS and ECH: the site name disappears from the network's view, though the IP address can still hint at it. Tick VPN: everything moves to the VPN company instead.
      • SayEvery tool moves trust somewhere. The question is always "hidden from whom?"
      

      


      
  
      // AFTER 03
      Certificate warnings: when to stop
      
  
      
    
      
      
      "Your connection is not private"The certificate failed a check: wrong name, expired, untrusted issuer, or tampered. On a public site, stop. Don't click through, especially for banking or logins.
      
      
      Why it happens innocentlyA site forgot to renew, a device's clock is wrong, or café Wi-Fi is showing its sign-in page. Check the date, then try again later or on another network.
      
      
      Some sites won't let you click throughSites that use HSTS tell the browser "always HTTPS, no exceptions", so the warning has no "continue" button at all.
      
    
      
    
      THE PADLOCK MEANS "this connection is encrypted and the certificate matches this name". It doesn't mean the site is honest: scam sites get certificates too.
      
  
      
  
      ~3 min
      • SayWarnings are rare now, so when one appears, take it seriously.
      • SayMost innocent causes: an expired certificate, a wrong device clock, or a Wi-Fi sign-in page.
      • SayThe padlock is about the connection, not the company. A phishing site can have a perfectly valid padlock for its own look-alike name.
      

      


      
  
      // AFTER 04
      HSTS: never take the unencrypted road
      
  
      
    
      
      
      
      
    
      
    
        
    
        You type bank.example, with no https://. What happens next depends on whether the browser already knows to use HTTPS.
        
  
        
  
        ~4 min
        • SayIf you type a bare name, the browser may start with plain http:// and get redirected. That first unencrypted step is a gap: someone on the network could keep you on http.
        • ShowThe three scenarios. HSTS: the site told your browser "always HTTPS", so it upgrades before sending anything. Preload: browsers ship with a list of HSTS sites, protecting even the very first visit.
        • TipFun fact: whole domain endings like .app and .dev are on the preload list, so every site under them must use HTTPS.
        

        


        
  
        // AFTER 05
        Certificate Transparency: catching bad certificates
        
  
        
    
        
      
        
        
        
        
      
        
      
          
      
          
    
          
    
          
      
            
        
          • Every publicly trusted certificate must be written to public, append-only logs, or browsers reject it.
            • 
        
          • Anyone can watch the logs. Sites get alerts when a certificate appears for their name.
            • 
        
          • Each entry is chained to the previous ones by hashes, so entries can't be quietly removed.
            • 
        
          • Browsers remove CAs that misbehave. In October 2026 they blocked eMudhra's dangerously weak certificates within days of researchers reporting them.
            • 
      
          
    
          
  
          
  
          ~4 min
          • SayCAs can make mistakes, or be hacked. Transparency logs make every certificate public so mistakes get spotted fast.
          • ShowRenew normally: the bank's monitor sees an expected entry. Mis-issue one: the monitor raises an alarm. Try to delete an entry: every later hash breaks.
          • SayCertificates are also getting much shorter lifetimes, so mistakes expire faster; renewals are automated.
          

          


          
  
          // CHECKPOINT 3 · 5 MIN
          Pause and discuss
          
  
          
    
          Talk with a neighbour for a couple of minutes, then we share answers. Guesses are welcome.
          
    
            
      
          1. With HTTPS, can the network see which site you visit? Which page? Your password?
            Hint
            Think DNS, the ClientHello, and the encrypted records.
            Answer
            Usually the site (through DNS and the ClientHello name), but not the page, and not your password, cookies or content. Encrypted DNS and ECH can hide the site name too.
            2. 
      
          2. A scam site shows a valid padlock. How is that possible?
            Hint
            What does a certificate actually vouch for?
            Answer
            A certificate only proves control of that domain name. Scammers can get one for their own look-alike name; the padlock says nothing about honesty.
            3. 
      
          3. Why can't a site's HSTS warning page be clicked through?
            Hint
            What did the site promise the browser earlier?
            Answer
            The site told the browser it always uses valid HTTPS, so any problem must be an attack or a serious fault. Removing the button stops people being talked past it.
            4.

          Inspect this connection, right now
          
  
          
    
          
      
          See the certificate
          
      
            
        
          • Chrome / Edge: click the icon left of the address, then "Connection is secure", then "Certificate is valid".
            • 
        
          • Firefox: click the padlock, then "Connection secure", then "More information", then "View Certificate".
            • 
        
          • Safari: click the padlock, then "Show Certificate".

          Crypto 101's certificate slide explains every field.
          
    
          
    
          
      
          See the handshake
          
      
            
        
          • Open your browser's developer tools (F12) and find the security section: it shows the TLS version, the key exchange and the cipher this page is using.
            • 
        
          • Look for TLS 1.3, a key exchange like X25519MLKEM768 (the hybrid from earlier), and AES-GCM or ChaCha20.
            •
