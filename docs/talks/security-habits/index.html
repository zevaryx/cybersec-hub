// DEFENDER 01

Everything that reaches your code is input

If it came from outside your code, someone else might control it.

RULE "Never trust input" really means: check it at the point it enters, every time, on a computer you control.

Formsevery field, including hidden ones
URLspaths, query strings, IDs
Headers and cookiesthe browser sends what it's told to
Filesuploads, names, sizes, contents
Other servicesAPIs, webhooks, message queues
Databasesdata someone else wrote earlier
AI model outputit may repeat text an attacker planted
Your own dependenciescode you didn't write, run as you

~3 min

  • SayMost people think "input" means form fields. It's anything your code didn't produce itself. Two that surprise people: data already in your database (someone typed it once), and the output of an AI model (it can repeat instructions hidden in a web page it read).
  • AskWhich of these does your current project read? Usually most of them.
  • Next"So where exactly should we check? At the boundaries."

// DEFENDER 03 · CLASSIC MISTAKE 1
Treating data as code

  

    

      

      

      

    

    

      
    
        
  • Gluing input into a query, command or template lets the input change the code. That's injection.
    • 
        
  • Parameters keep them apart: the code is fixed, the input is only ever a value.
    • 
        
  • Same idea everywhere: SQL, shell commands, HTML, regex patterns, AI prompts.
    • 
      

      
OCTOBER GitLab compiled patterns users typed. Ruby's regex engine had bugs. A pattern is code.

    

  

  
~4 min
  • ShowType Ada: both versions find one row. Press ' OR '1'='1: the glued-together query now says "or true" and returns every student. The parameterised one finds nobody, correctly. Try O'Brien: the glued version breaks on a real name, which is how a lot of these bugs get found.
  • SayThis is a simulation of how the database reads the text, not a real database.
  • EggRobert'); DROP TABLE students;-- (xkcd 327).
  • Next"Mistake two: believing what the browser tells you."

Trusting the client

// CHECKPOINT 1 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. A form disables the "admin" checkbox for normal users. Is the admin feature protected?
    Hint
    Who controls the browser?
    Answer
    No. Anyone can re-enable it or send the request directly. The server must check the user's role on every request.
    2. 
      
  2. Your app summarises web pages with an AI model, then runs the actions it suggests. Where's the trust boundary?
    Hint
    Who wrote the web page?
    Answer
    Between the model's output and your code. A page can hide instructions the model repeats, so treat its output as untrusted input and limit what it can trigger.
    3. 
      
  3. Name one trust boundary in something you've built.
    Hint
    Where does data arrive from somewhere you don't control?
    Answer
    Common ones: form handlers, API endpoints, file uploads, webhooks, and anything reading another service's response.
    4.

// HABITS 1 AND 2
Validate on the way in, encode on the way out

  

    

      

      

        
Inserted as HTML

        
Encoded by the template

      

    

    

      
1 · Validate input on the serverCheck type, length and format against what you allow (an allowlist), and reject the rest.

      
2 · Use the framework's safe defaultsQuery parameters, auto-escaping templates, the ORM. Don't switch them off; be suspicious of "raw" and "unsafe" in function names.

      
ENCODE FOR THE DESTINATION The same text needs different escaping in HTML, a URL, JavaScript or SQL. Templates do this for you.

    

  

  
~4 min
  • ShowThe comment contains an image tag with an onerror handler. Left: what the browser would do if you pasted it into the page as HTML (we describe it rather than run it). Right: the template encodes it, so it shows up as harmless text.
  • SayThat's cross-site scripting: data treated as code, in the browser this time. React, Vue, Django, Rails and most modern templates encode by default. The bugs live in the escape hatches: innerHTML, dangerouslySetInnerHTML, |safe, raw().
  • Next"Habit 3: the server decides who may do what."






  
// HABIT 3
Check permissions on every request

  

    

      
You're signed in as customer 7. Your invoice is 1042.

      
https://shop.example/invoices/

      

      

    

    

      
    
        
  • Hiding a button isn't access control. Every endpoint asks: is this user allowed to do this, to this thing?
    • 
        
  • Changing an ID in a URL to see someone else's data is one of the most common bugs there is.
    • 
        
  • Put the check in one place every request passes through, so a new endpoint can't forget it.
    • 
      

      
OWASP Broken access control is number 1 on the OWASP Top 10.

    

  

  
~3 min
  • ShowChange 1042 to 1041 or 1043: you see other customers' invoices. Tick the ownership check and try again: 404, which also doesn't reveal that the invoice exists.
  • SaySigned in isn't the same as allowed. Authentication says who you are; authorisation says what you may touch.
  • CheckConfirm the current OWASP Top 10 edition before presenting (2025 at the time of writing, with broken access control first).
  • Next"Habit 4: secrets."






  
// HABIT 4
Keep secrets out of code, and out of Git

  

    

      

      

    

    

      
    
        
  • Keys go in environment variables or a secret manager. Add .env to .gitignore before your first commit.
    • 
        
  • Deleting a key in the next commit doesn't remove it. Git keeps every version, and bots scan public repos within minutes.
    • 
        
  • Leaked a key? Revoke it first, then clean up. Turn on your host's secret scanning and push protection.
    • 
      

      
OCTOBER LiteLLM: an admin key committed in May, never revoked, used in October.

    

  

  
~4 min
  • Showgit log: three innocent commits, one says "remove key". git log -p: the key is right there in the history. Rotate the key: now the leaked one is useless, which is the only real fix.
  • SayRewriting history to remove it is good hygiene, but forks, clones and caches may already have it. Assume it's out; make it worthless.
  • Next"Habit 5: don't build your own locks."






  
// HABITS 5 AND 6
Use well-known libraries, and keep them few and current

  

    

      
5 · Don't write your own crypto, auth or parsersUse the well-reviewed library: a password-hashing library, your framework's sessions, a real parser. Small mistakes in these become big holes.

      
The crypto on this hub is written from scratch, on purpose, to show how it works. Production code uses a vetted library. Crypto 101 shows why.

      
6 · Keep dependencies few and currentEvery package is code that runs as you. Fewer is better; updated is essential.

    

    

      
    
        
  • Lock files with hashes, so a build installs exactly what you tested.
    • 
        
  • Update bots (Dependabot, Renovate) open the pull requests for you.
    • 
        
  • Don't jump to a release published an hour ago. Let it settle.
    • 
        
  • Updating isn't done until the running program is restarted or the image rebuilt.
    • 
      

      
OCTOBER LiteLLM 1.107.0 and a Claude Code extension version were both malicious for hours. A Brotli bug sat in a trusted library for eight years.

    

  

  
~4 min
  • SayThese two pull in opposite directions on purpose: use libraries instead of writing risky code yourself, but every library is someone else's code you now depend on. So pick well-known ones, keep the list short, and keep it updated.
  • SayPinned, hash-checked installs were safe from LiteLLM's bad release. A brand-new release installed automatically was not.
  • Next"Habit 7: what happens when things go wrong."






  
// HABIT 7
Fail safely: helpful to you, useless to an attacker

  

    

      

      

        
What the user sees

        
What your logs record

      

    

    

      
    
        
  • Users get a generic message and a reference number.
    • 
        
  • Your logs get the details: stack trace, request ID, what failed.
    • 
        
  • Never secrets, passwords, tokens or full card numbers in either.
    • 
        
  • Fail closed: if a permission check errors, the answer is no.
    • 
      

    

  

  
~3 min
  • ShowTrigger the bug in development mode: the stack trace shows the database host, the query and the connection string, password included. Tick production mode: the user gets a reference number; the log keeps the detail with the secret redacted.
  • SayDetailed errors are wonderful while you build and a map for attackers once you ship. Make sure production mode is really on in production.
  • EggLook closely at the dev-mode password.
  • Next"Habit 8: give everything as little power as possible."






  
// HABIT 8
Least privilege: every key can only do its job

  

    

      
A token for the nightly sales report. It needs to read orders. What does it get?

      

        
        
        
        
        
        
      

      

    

    

      
    
        
  • Database users that can't drop tables. API tokens with one scope. Cloud roles for one job.
    • 
        
  • Give keys an expiry date, and one owner who'd notice if it leaked.
    • 
        
  • When (not if) something leaks, least privilege decides how bad the day is.
    • 
      

      
OCTOBER Zeabur: never-expiring admin tokens in a config repo, reachable from the internet.

    

  

  
~3 min
  • ShowWith only read:orders, a leak exposes order data. Tick more boxes and watch the "if this leaks" list grow. Least privilege doesn't stop the leak; it shrinks the damage.
  • EggTick everything.
  • Next"The last two habits are about people."






  
// HABITS 9 AND 10
Review each other, and learn without blame

  

    

      
9 · Review code with security on the checklistFour questions for every pull request:

      
    
        
  1. Where does new input enter, and is it validated?
    2. 
        
  2. Is any input used as code: SQL, HTML, shell, regex, a prompt?
    3. 
        
  3. Does every new endpoint check who may do this?
    4. 
        
  4. Any secrets, new dependencies or detailed errors?
    5. 
      

    

    

      
10 · Learn from incidents, blamelesslyWhen something breaks, ask what made the mistake easy, not who made it.

      
    
        
  • Write it up: what happened, how it was found, what changes so it can't happen the same way again.
    • 
        
  • Read other people's write-ups too. October's incident reports are free lessons.
    • 
        
  • People who are blamed hide mistakes. People who aren't, report them early.
    • 
      

    

  

  
~3 min
  • SayCode review catches what one tired person misses. Four questions cover most of today's talk.
  • SayLiteLLM, Railway and Zeabur all published detailed incident reports. That's the industry doing habit 10 in public, and it's why this talk could use real examples.
  • Next"Checkpoint."






  
// CHECKPOINT 2 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. You pushed an API key by accident and deleted it in the next commit. Are you safe?
    Hint
    What does git log -p show?
    Answer
    No. It's still in the history, and may already be copied. Revoke or rotate the key first, then clean up.
    2. 
      
  2. Why is a detailed error page useful to you, and dangerous in production?
    Hint
    Who else can read it?
    Answer
    It shows exactly what failed, which helps you debug. In production it shows attackers your stack, queries, file paths and sometimes secrets. Log the detail; show users a reference number.
    3. 
      
  3. Which of the ten habits would have helped most in your last project?
    Hint
    Validate, defaults, permissions, secrets, libraries, updates, errors, privilege, review, learning.
    Answer
    There's no wrong answer. Pick one and make it automatic this week.
    4.
