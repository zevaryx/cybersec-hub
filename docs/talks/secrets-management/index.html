// WHY THIS TALK

Secrets leak constantly, and stay valid

28.65Mnew hard-coded secrets added to public GitHub commits in 2025, up 34%.
64%of secrets confirmed valid in 2022 still worked when retested in January 2026.
~28%of leak incidents came entirely from outside repositories: chat, tickets, wikis.
  • A secret is a string that opens something. Leaking one is easy, noticing is slow, and replacing it is the part most teams never practised.
  • So the goal isn't "never leak". It's fewer secrets, shorter lives, and a rehearsed response.

Sources: GitGuardian, State of Secrets Sprawl 2026 · CircleCI · Wiz · GitGuardian on Toyota

Toyota, 2017 to 2022 · a key in public codeA subcontractor put part of the T-Connect source code, with an access key to a customer-data server, on public GitHub in December 2017. About 296,000 people's emails and customer numbers were exposed. Noticed in September 2022; no misuse detected.
Microsoft AI research, 2023 · a token that was too muchA storage link in a public repository carried a Shared Access Signature token with full control of the whole storage account and an expiry in 2051. Wiz reported it on 22 June 2023; it was revoked two days later.
CircleCI, 2022 to 2023 · the platform holds your secretsMalware on one engineer's laptop stole a 2FA-backed session. The attacker took customers' stored tokens, keys and environment variables, and customers were told to rotate everything.

      1. A secret was committed, and then deleted in the next commit. Is it safe?
        Hint
        Who else has a copy of the first commit, and does the key still work?
        Answer
        No. It's still in history, in every clone, possibly in forks and cached views, and the key still works. Revoke or rotate it first; cleaning history is optional afterwards.
        2.

        Hint
        What does the scanner actually look at: meaning, or shape?
        Answer
        Scanners match shapes: known prefixes, secret-looking names, randomness. A commit ID looks random (false alarm); a plain password with an innocent name has no shape (miss). So keep secrets out of code entirely and treat scanning as a safety net.

        Hint
        Where does a build argument's value end up?
        Answer
        Use a build secret mount (RUN --mount=type=secret), which exposes the secret only while that instruction runs. Build arguments and environment variables persist in the final image.

      // WHERE SECRETS LIVE 02
      Envelope encryption: the key never leaves
      
  
      
    
      
      
      
        
        
      
      
      
      
        
        
        
        
        
      
      
      
      
      
      
    
      
    
      
      
      data key (one per record)encrypts the data
      
      
      master key (stays in the service)wraps the data key
      
      
      
      
        
        
      • Store the wrapped data key next to the data. Ask the key service to unwrap it when needed.
        • 
        
      • Rotating the master key means rewrapping small keys, not re-encrypting all the data.
        • 
        
      • Tie each record to a context (here: the user), so a ciphertext can't be moved to another record.
        • 
      
      
      
      
    
      
  
      
  
      ~6 min
      • ShowThe page starts with two encrypted records. Add your own. The table shows, for each, the ID of the master key that wraps its data key, a short piece of the wrapped data key, and a short piece of the ciphertext. Press "New master key (no rewrap)": new records use it, old ones still point at the old one. Press "Retire old master keys" now and Decrypt fails for the old records. That is rotation going wrong. Reset, add records, then "New master key", "Rewrap to latest": the wrapped keys change but the ciphertext doesn't, and nothing was re-encrypted.
      • SayThis is what AWS KMS and the other key services do. The service never gives you the master key; it generates data keys, hands you one in the clear for immediate use plus an encrypted copy to store, and later unwraps the copy on request. The data never goes to the service, only small keys do. Real KMS calls limit direct encryption to 4,096 bytes, one practical reason for data keys.
      • TipThe demo uses this deck's from-scratch AES-256-GCM: the data key encrypts the record with the context as authenticated data; the master key wraps the data key with the context in the associated data too, so changing the label makes both decryption steps fail. It's a teaching model, not a library to use: in real code use your cloud's SDK or a vetted library (see the Crypto in Code talk). Facts: AWS KMS docs (data keys: plaintext copy for immediate use plus an encrypted copy; the service doesn't store or use data keys; remove the plaintext key from memory as soon as possible; symmetric ciphertext carries the key ID; Encrypt takes up to 4,096 bytes; an encryption context is recommended and may appear in logs, so keep secrets out of it).

      // WHERE SECRETS LIVE 03
      HSMs and key ceremonies: what they guarantee, and what they don't
      
  
      
    
      
      
      
        
      GuaranteesThe key is generated and used inside tamper-resistant hardware, isn't exportable in the clear, and every use can be limited and logged.
      
        
      Doesn't guaranteeThat a compromised caller can't misuse it while it has access, that the software around it is bug-free, or that the key was generated well.
      
      
      
      
      eMudhra, October 2026 · a CA key that wasn't random enoughGoogle reports that private keys for eight eMudhra intermediate CA certificates were "generated with insufficient randomness". Chrome blocked them the same day it was told. The lesson: protecting a key is only as good as how it was made.
      
      
        
        
      • Ceremonies exist so no one person can make or use the master key alone.
        • 
        
      • Script it, witness it, record it, and practise the recovery.
        • 
      
      
    
      
    
      
      
      A tiny key ceremony. The key is split into 5 shares; any 3 can recover it.
      
      
      
      
      
      
      
      
      
      
      
    
      
  
      
  
      ~6 min
      • ShowTick shares. With one or two, the recovered value is meaningless; with any three, it matches the key. Try different trios: it works for every trio. This is Shamir's secret sharing, and it's what makes "no single person can unlock the master key" real. Two shares don't just make the key hard to find: they leave every possible key equally likely.
      • SayAn HSM or key service protects a key you've already got. A ceremony covers the moment of creation and the recovery path: who attends, what's checked, what's recorded. And as eMudhra shows, even strong hardware can't rescue a key that started life without enough randomness.
      • TipeMudhra: Google's post says the keys for eight subordinate CA certificates were generated with insufficient randomness, received by the Chrome Root Program on Saturday 17 October 2026 at 18:05 UTC, blocked by a CRLSet update at 19:45 UTC the same day, with Android covered by a later Play Services update; Mozilla's post is linked in the PKI talk. IANA's DNS root signing key ceremonies are a public example: usually four times a year, with Trusted Community Representatives. The demo uses Shamir sharing over the field of integers modulo 2^255 - 19 with a 128-bit key; real ceremonies use vetted tools and hardware, not a web page.
      • CheckGoogle's post says "eight" intermediate CA certificates in its introduction but "these six intermediate CAs" later, without explaining the difference: say "eight" as the PKI talk does, and attribute it. Neither Google nor Mozilla has published how the keys were generated beyond "insufficient randomness", so don't speculate on the cause. The IANA page doesn't say who holds or witnesses each ceremony in detail: read the ceremony pages themselves before describing them.

        •

        •

        •

      • ShowStart with "our repo, main branch" and the "Repo + main" policy: allowed. Move through the jobs. A pull request token has a different subject, so it's refused.       • SayThis is the idea behind GitHub Actions' OpenID Connect support, workload identity on the major clouds, and Kubernetes service accounts: replace "a secret we store" with "a proof of who is asking, valid for minutes". It shrinks the blast radius of a leak from "until someone notices" to "until it expires". It doesn't remove the need to scope the role to what the job needs.
      • AskWhy is a short-lived credential better than a well-protected long-lived one? Answer: protection can fail, and when it does the long-lived key keeps working for the thief; the short one doesn't. And there's nothing to store, rotate or leak.
      • TipFrom GitHub's OIDC docs: the workflow needs the id-token: write permission; the cloud checks the token's subject and other claims against conditions you set; you must define at least one condition so untrusted repositories can't request tokens; scope to a repository and, where possible, an environment or branch; the subject formats are repo:ORG/REPO:ref:refs/heads/BRANCH, repo:ORG/REPO:environment:NAME and repo:ORG/REPO:pull_request. AWS STS: temporary credentials from AssumeRoleWithWebIdentity last one hour by default, from 15 minutes up to the role's maximum session (1 to 12 hours). GitHub's secrets page notes that, apart from GITHUB_TOKEN, secrets aren't passed to workflows triggered from forks. The cloud and issuer names in the demo are fictional.

      // ROTATION AND INCIDENTS 01
      Rotation without an outage: two keys at once
      
  
      
    
      
      
        
        
      1. Verifiers learn to trust A and B.
        2. 
        
      2. New tokens carry B's key ID.
        3. 
        
      3. Tokens signed with A reach their expiry.
        4. 
        
      4. Remove A from the verifiers.
        5. 
      
      
      
      
        
        
        
      
      
      
      
    
      
    
      
      
      
      
      
      
      
    
      
  
      
  
      ~6 min
      • ShowPress "Issue a token" (signed with key A), then step 1, step 2, issue another (signed with B). Both verify, because the verifier trusts both. Now press step 4 right away: the old token fails with "unknown key", though it hasn't expired. That's an outage caused by rotating too eagerly. Reset and do it in order, with step 3 in between, and nothing ever fails. Real ECDSA signatures from this deck's code sign each token.
      • SayThe trick that makes rotation routine is overlap: two valid keys at the same time, and every signature carrying a key ID so the verifier knows which to use. The retire step waits for the longest-lived thing signed by the old key to expire. This is exactly how JWKS key sets, certificate renewals and database credential rotation work.
      • TipThe same shape with other secrets: database passwords (create a second valid credential, switch the app over, remove the old one), webhook signing secrets (accept both for a window), and encryption keys (new data uses the new key, old data keeps its key ID until rewrapped, as on the previous slide).

      // ROTATION AND INCIDENTS 02
      Rotation in practice
      
  
      
    
      
      
      Versions and labelsSecret managers keep versions with labels. AWS Secrets Manager, for example, marks the live version AWSCURRENT, a candidate AWSPENDING, and the last good one AWSPREVIOUS, so a failed rotation can fall back.
      
      
      Two identities, taking turnsFor databases, the "alternating users" pattern keeps two users: rotate the one that isn't in use, then switch the app to it. No moment where the password in use is wrong.
      
      
      Key IDs travel with the dataPut the key ID or version in every ciphertext, token and signature header. Then old and new can coexist, and you can see what still uses the old key.
      
    
      
    
      
      
        
        
      • Rotate on events: a leak, a person leaving, a vendor incident, a dependency compromise.
        • 
        
      • Rotate on a schedule only if it's automatic. A manual yearly rotation is an outage waiting for a date.
        • 
        
      • For people's passwords, don't force periodic changes: NIST says verifiers shall not, but shall force a change on evidence of compromise.
        • 
        
      • Practise rotating every secret once, before the day you need it. The first rotation always finds a hidden dependency.
        • 
        
      • Know who uses each secret. A secret with no owner can never be safely revoked.
        • 
      
      
      
      Sources: AWS Secrets Manager · NIST SP 800-63B-4 · AWS KMS
      
    
      
  
      
  
      ~3 min
      • SayYou don't have to build rotation yourself: managers and clouds do the dance for supported services. What you do have to do is design your own code so it tolerates two valid secrets at once, and read the secret at use rather than caching it for the life of the process.
      • TipNIST SP 800-63B-4: "Verifiers and CSPs SHALL NOT require subscribers to change passwords periodically" and "verifiers SHALL force a change if there is evidence that the authenticator has been compromised." That's about people's passwords: machine secrets are different because automation makes rotation cheap. The alternating-users strategy and the AWSCURRENT and AWSPREVIOUS labels were confirmed against AWS's rotation-strategy page on 11 November 2026 (the rotation function clones the user on the first rotation, then alternates which user's password it updates); AWSPENDING is the label the rotation function uses for the candidate version.
      • Next"And when one leaks anyway: the runbook."
      

      


      
  
      // ROTATION AND INCIDENTS 03
      The leaked-secret runbook
      
  
      
    
        
      
      1. Confirm and scope.What is it? What can it do? Who owns it? Where else is it used?
        2. 
      
      2. Revoke or rotate now.Create the replacement, deploy it, revoke the old one. Minutes, not days.
        3. 
      
      3. Read the logs, from the first exposure.From when it was committed or pasted, not from when you noticed. Unfamiliar IPs, new users, keys or roles, unusual reads.
        4. 
      
      4. Contain what you find.End sessions, delete anything the attacker created, and rotate whatever the key could read.
        5. 
      
      5. Find the leak path and close it.How did it get there? Add the control that would have stopped it.
        6. 
      
      6. Clean up, tell people, learn.Tidy history if worthwhile, notify as your obligations require, and hold a review that looks at systems, not blame.
        7. 
    
      
    
      
      
      RULERotate first, clean up later. A revoked key sitting in public history is harmless; an unrevoked one in a private repo isn't.
      
      
      The first thing to doRevoke or rotate the secret. Everything else (history, blame, write-ups) can wait the extra ten minutes; the key can't.
      
      
      Have it ready before you need itKnow who can revoke each secret, where its usage logs are, and how long they're kept. Test it with a made-up key.
      
    
      
  
      
  
      ~3 min
      • SayOrder matters because time matters: every minute the key works is a minute someone else can use it. Notice that "look at the logs" starts at the time of exposure, which is often hours before the alert, as the tabletop will show.
      • AskWhat's the very first thing you do when a production key leaks? Answer: revoke or rotate it. If revoking would break production, create and deploy the replacement first, then revoke straight away.
      • TipGitHub's own guide: as a first step revoke or rotate the secret, and rewriting history "may not be warranted" afterwards. CircleCI's January 2023 guidance to customers is a worked example: rotate everything stored on the platform, review activity from 16 December 2022 until your rotation was complete, and treat secrets entered after 5 January 2023 as safe. How long logs are kept, and who may notify regulators or customers, differs by cloud, country and contract: this slide doesn't give legal advice.

        // ROTATION AND INCIDENTS 05
        Everyday habits, beyond the incidents
        
  
        
    
        
      
        In your code and tools
        
      
          
        
        • Add .env to .gitignore before the first commit, and commit a .env.example with placeholders.
          • 
        
        • One secret per purpose and per environment. A leaked dev key should open nothing in production.
          • 
        
        • Least privilege. A key that can only read one bucket is a smaller incident.
          • 
        
        • Never put secrets in URLs or command-line arguments: they end up in logs, history and process lists. Use a file or stdin.
          • 
        
        • Scrub what you log, and don't log whole requests or environments.
          • 
        
        • Label every secret with an owner and what it's for, so it can be revoked without a search.
          • 
      
        
    
        
    
        
      
        With people
        
      
          
        
        • Share credentials through a password manager or secret manager, never chat, email, tickets or screenshots.
          • 
        
        • Make reporting easy and blame-free. "I pasted a key in the wrong channel" should get a thank-you and a rotation.
          • 
        
        • Treat laptops as leaky: keep production secrets off them; fetch development secrets on demand.
          • 
        
        • Offboard secrets, not just people: when someone leaves, rotate what they could read.
          • 
        
        • Prefer to have no secret at all: an identity, a short-lived token, or a managed service, instead of a string.
          • 
      
        
      
        
    
        
  
        
  
        ~3 min
        • SayNone of this is dramatic, which is why it works. Each habit removes a place a secret can be, or limits what it can do once it's out. And the best secret is the one you never had to store.
        • TipThese are widely recommended practices (see the OWASP Secrets Management Cheat Sheet linked on the last slide) rather than claims from one source. The point about command-line arguments: on a default Linux system any local user can see other users' process arguments, and shell history files keep what you typed.
