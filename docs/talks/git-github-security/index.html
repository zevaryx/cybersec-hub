// WHY IT MATTERS

The repository is a front door

March 2025 · tj-actions/changed-filesA popular GitHub Action's version tags, v1 to v45.0.7, were quietly pointed at a malicious commit. Workflows using it printed their secrets into build logs. CISA listed it as known exploited.Tags can move. Commits can't.
October 2026 · LiteLLMWith three developers' stolen GitHub tokens, an attacker pushed a workflow change past branch protection, approved the release with a second account, then hid the change with a revert and force-push.Protections are only as strong as who can switch them off.

SOURCES CVE-2025-30066 · CISA (18 Mar 2025) · LiteLLM attack chain · Black October

// COMMITS 01

A commit's author is just text


    

    

      
    
        
  • Git records whatever user.name and user.email say. It never checks.
    • 
        
  • GitHub links the commit to whichever account owns that email, avatar and all.
    • 
        
  • So a commit "by" a famous developer, or by you, proves nothing on its own.
    • 
      

      
TRY IT Set your name to someone else's and look at the log. That's the whole attack.

    

  

  
~3 min
  • ShowChange the name and email: the log looks completely real. Nothing on your machine or on GitHub's side checked it.
  • SayThis isn't a bug. Git was designed to record authorship, not prove it. Proving it needs a signature.
  • EggCommit as Linus Torvalds.
  • Next"So how do you prove a commit is yours?"






  
// COMMITS 02
Signed commits: proof, not a promise

  

    

      

        
        
        
      

      

    

    

      
    
        
  • A signature covers the whole commit: the code snapshot, its parents, the author and the message.
    • 
        
  • Change one byte afterwards and it no longer verifies.
    • 
        
  • Only your private key can make it. GitHub checks it against the public key on your account.
    • 
      

      
CRYPTO 101 The same digital signatures, here real P-256 ECDSA in your browser. Revisit the slide.

    

  

  
~4 min
  • ShowSign a commit: it verifies. Forge one with your name but no key: no signature at all. Change the signed one's message: the signature fails.
  • SayGit signs with SSH, GPG or S/MIME keys. This demo uses P-256 ECDSA to show the idea; the commit text is simplified.
  • Next"What does GitHub's Verified badge actually promise?"






  
// COMMITS 03
What "Verified" does and doesn't prove

  

    

      

        
Verified
Signed, and the signature checks out against a key on the committer's account.

        
Unverified
Signed, but the signature didn't check out. Or, with vigilant mode on, not signed at all.

        
no badge
Not signed. This is the default for unsigned commits, so forgeries look normal.

      

      
VIGILANT MODE Turn it on in your GitHub settings and unsigned commits using your email are marked Unverified. It's off by default.

    

    

      

        
It provesThe commit was signed by a key registered to that account, and hasn't changed since.

        
It doesn't proveThe code is safe, a human meant it, or the account wasn't compromised.

      

      
LiteLLM's malicious workflow change came from real accounts with real tokens. A signature tells you which key; reviews and branch rules decide whether it gets in.

    

    
SOURCES GitHub Docs: about commit signature verification

  

  
~3 min
  • SayVerified is a strong statement about where a commit came from, and nothing else. Treat it like the padlock in HTTPS: it means the connection is genuine, not that the site is honest.
  • SayVigilant mode is the setting that makes forgeries of you stand out. Turn it on once you sign everything.
  • Next"Setting it up takes three commands."






  
// COMMITS 04
Sign every commit with your SSH key

  

    

      
# 1. sign with SSH, using your existing key
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
# 2. sign every commit and tag by default
git config --global commit.gpgsign true
git config --global tag.gpgsign true
# 3. check locally (Git 2.34 or later)
echo "$(git config user.email) $(cat ~/.ssh/id_ed25519.pub)" >> ~/.ssh/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers
git log --show-signature -1

    

    

      
    
        
  • Then on GitHub: Settings → SSH and GPG keys → New SSH key, and choose key type Signing key.
    • 
        
  • The same key can be used for pushing and signing, but it must be added once for each.
    • 
        
  • allowed_signers lets your own Git verify signatures, without GitHub.
    • 
      

      
FUN FACT Every commit to this hub is signed this way. Check the repository's history for the badges.

    

  

  
~3 min
  • SayIf you already push over SSH, you already have the key. Two settings make Git use it to sign; two more make it sign everything by default.
  • TipUse a key with a passphrase, or one held by a hardware key or password manager, so a stolen laptop can't sign as you.
  • CheckCommands from GitHub Docs ("Telling Git about your signing key"). SSH signature verification needs Git 2.34 or later.
  • Next"Before the account: two everyday Git habits."






  
// GOOD GIT 01
Commits worth reading

  

    

      

      

      

    

    

      
    
        
  • One change per commit. Easy to review, easy to revert, easy to find with git bisect.
    • 
        
  • Subject: what it does, in the imperative ("Fix login redirect"), about 50 characters.
    • 
        
  • Body: why. The diff already shows what changed; only you know why.
    • 
        
  • Check before you commit: git add -p to choose hunks, git diff --staged to read them.
    • 
      

      
SECURITY BONUS Reading your staged diff is also how you catch the .env file before it's history.

    

  

  
~4 min
  • Show"fixed stuff" gets three suggestions. Rewrite it live with the room: "Fix redirect loop after login", then add a body explaining why. Watch the checks turn green.
  • SaySix months from now you'll read your own history to find out why something is the way it is. Write for that person.
  • EggTry "asdf" or "wip" as the subject.
  • Next"And when a commit goes wrong anyway?"






  
// GOOD GIT 02
Undo without fear

  

    

      
What happened?

      

    

    

      

      
THE RULE Rewrite only what you haven't shared. Once it's pushed and others have it, revert instead.

    

  

  
~4 min
  • ShowAsk the room for their worst Git moment, then find it in the list. The reflog one gets the biggest sigh of relief: Git keeps a record of where your branch has been for weeks.
  • SayPrefer --force-with-lease to --force: it refuses to overwrite work someone else pushed since you last fetched.
  • Next"Back to security: your account."






  
// COMMITS 05
Your GitHub account is the master key

  

    

      
Sign in with a passkey or security keyPhishing-resistant, like the Passwords talk showed. Keep an authenticator app as backup, not SMS.

      
Save your recovery codesIn your password manager. Losing every factor locks you out of your own code.

      
Review what can act as youSSH keys, personal access tokens, authorised OAuth and GitHub Apps, active sessions. Remove what you don't recognise.

    

    

      
    
        
  • Everything else in this talk can be undone by someone who controls your account.
    • 
        
  • Old laptops, old tokens and old app grants are doors you forgot you left open.
    • 
        
  • Do the review twice a year, and whenever you change jobs or machines.
    • 
      

      
More on passkeys and recovery: Passwords and Accounts.

    

  

  
~3 min
  • SayYour GitHub account can push, approve, change settings and create tokens. Protect it like a bank account, because for your users it's more important than one.

// CHECKPOINT 1 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. Someone's commits show your name and email. How would anyone tell they aren't yours?
    Hint
    What does your real work have that theirs can't?
    Answer
    If you sign every commit and turn on vigilant mode, theirs show as Unverified while yours show Verified.
    2. 
      
  2. A commit shows "Verified". Is it safe to merge?
    Hint
    What does a signature say about the code inside?
    Answer
    Not by itself. It proves which key signed it and that it hasn't changed, not that the code is good or the account wasn't stolen. It still needs review.
    3. 
      
  3. Which is worse to lose: your laptop's SSH key, or your GitHub password with no second factor?
    Hint
    Which one can create new keys and tokens?
    Answer
    The account. It can add keys, mint tokens and change settings. Revoke the laptop's key from the account either way.

// REPOSITORY 01
Branch rules: nobody pushes straight to main

  

    

      
A ruleset for the default branch

      
    
        
  • Require a pull requestwith at least one approving review
    • 
        
  • Require status checkstests and scans must pass first
    • 
        
  • Require signed commitsevery commit must carry a verifiable signature
    • 
        
  • Block force pusheshistory on main can't be rewritten
    • 
        
  • Restrict deletionsthe branch can't be removed
    • 
      

    

    

      
    
        
  • Rulesets are GitHub's newer form of branch protection: several can apply at once, and they can cover tags too.
    • 
        
  • Keep the bypass list short. Anyone on it, including admins, can skip every rule.
    • 
        
  • Require approval of the most recent push, so nobody slips a change in after review.
    • 
      

      
OCTOBER LiteLLM's attacker used an organisation owner's token to disable protections and force-push. Fewer owners, fewer bypasses.

    

  

  
~4 min
  • SayBranch rules turn "please don't push to main" into "you can't push to main". The weak spot is whoever can turn the rules off.
  • CheckConfirm current ruleset option names in GitHub's settings before presenting; they change occasionally.
  • Next"Rules make reviews happen. Now make them good ones."






  
// GOOD GIT 03
Pull requests people want to review

  

    

      
Small and focusedUnder a few hundred lines, one purpose. Big PRs get skimmed; small ones get read.

      
A description that answers three questionsWhat does it change? Why? How did you test it? Screenshots for anything visible.

      
Draft earlyOpen a draft PR to get feedback on the approach before you've built all of it.

    

    

      
    
        
  • CODEOWNERS requests the right reviewers automatically, for the right folders.
    • 
        
  • Review kindly and specifically: suggest, explain why, and say what's good too.
    • 
        
  • As the author, review your own diff first. You'll catch half the comments before anyone else does.
    • 
        
  • Keep the four security questions from Developer 01 on your review checklist.
    • 
      

      
The four review questions from Security Habits.

    

  

  
~4 min
  • SayBranch rules make reviews mandatory; these habits make them worth having. A reviewer who understands a small change can spot the security problem in it.
  • Next"What about secrets that slip into a PR?"






  
// REPOSITORY 02
Secret scanning and push protection

  

    

      

      

      

    

    

      
    
        
  • Secret scanning finds known token formats in your repository and alerts you.
    • 
        
  • Push protection blocks the push before the secret ever lands. You can bypass it, but you must give a reason.
    • 
        
  • For your personal account it's on by default when pushing to public repositories. For a repository, an admin has to enable it.
    • 
      

      
DEPENDABOT TOO Turn on Dependabot alerts and security updates: pull requests for vulnerable dependencies, written for you.

    

    
SOURCES GitHub Docs: about push protection

  

  
~4 min
  • ShowPush the clean file: accepted. Press "Add a token by mistake" and push again: blocked, with the line number, before it reaches GitHub. This is a simulation that looks for token-shaped text; GitHub's real scanner knows hundreds of formats and checks many with the provider.
  • SayBypassing asks why: "used in tests", "false positive", or "I'll fix it later". The last one opens an alert, so it isn't forgotten.
  • Next"Your own tokens deserve the same care."






  
// REPOSITORY 03
Tokens: fine-grained, few, and expiring

  

    

      
Classic tokenBroad scopes like repo: every repository you can reachCan be made to never expireEasy to create, easy to forget

      
Fine-grained tokenChosen repositories onlySpecific permissions, read or write, one by oneAn expiry date you choose; organisations can require approval and limit lifetimes

    

    

      
    
        
  • For automation, prefer a GitHub App or the workflow's own GITHUB_TOKEN over a person's token.
    • 
        
  • Never automate with your GitHub CLI login. It acts as you, everywhere you can act.
    • 
        
  • Name each token after its job, so the one to revoke is obvious on a bad day.
    • 
      

      
OCTOBER LiteLLM's lesson in its own words: stop relying on GitHub CLI OAuth tokens for automation; use scoped tokens.

    

  

  
~3 min
  • SayThis is least privilege from the Security Habits talk, applied to GitHub. If a token leaks, the blast radius is whatever you gave it.
  • Next"The biggest token of all lives in your workflows."






  
// REPOSITORY 04
GitHub Actions: the weakest link, if you let it be

  

    

      

        
        
        
        
      

      

    

    

      

      
    
        
  • Least privilege: default GITHUB_TOKEN to read-only; raise it per job.
    • 
        
  • Lock or pin third-party actions. GitHub now recommends a lockfile, actions.lock made by gh actions-lock; otherwise pin full commit SHAs.
    • 
        
  • Forks are strangers: never check out a fork's code in pull_request_target.
    • 
        
  • Input is code again: pass titles and branch names through environment variables.
    • 
      

    

    
SOURCES GitHub Docs: security hardening for Actions · workflow dependency lockfiles · github/gh-actions-lock

  

  
~6 min
  • ShowStart with the risky defaults: four findings. Fix them one by one: read-only token, lock or pin, plain pull_request, title through an env variable. The YAML updates as you go.
  • SayThe tag option is the tj-actions story: a tag is a name someone can move. A commit SHA or a lockfile entry can't be moved. GitHub's docs say pull_request_target with untrusted checkout can be used to "take over a repository".
  • TipThe Actions lockfile is generally available. Install with gh extension install github/gh-actions-lock, then run gh actions-lock to write .github/workflows/actions.lock. In CI, gh actions-lock --verify checks it; --relock moves tags like v4 to their current commits on purpose, so updates are reviewed.
  • EggFix all four.

// CHECKPOINT 2 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. Which three repository settings would you turn on first, and why?
    Hint
    Think: what gets in, what leaks, what runs.
    Answer
    A common pick: a ruleset on main (what gets in), push protection (what leaks), and a read-only workflow token (what runs). Any well-argued three is a good answer.
    2. 
      
  2. Your workflow uses some/action@v3. What could change without you noticing?
    Hint
    Who controls where v3 points?
    Answer
    Everything: the action's owner, or anyone who takes over their account, can move the tag to new code. Lock it or pin a full commit SHA.
    3. 
      
  3. Who in your organisation can bypass branch rules? Should they?
    Hint
    Check the bypass list and the owners.
    Answer
    Often more people than anyone realises. Keep owners few, keep the bypass list short, and protect those accounts the hardest.
    4.

    // LEAKS 02
    Rewriting history doesn't un-leak a secret
    
  
    
    
    
      
      
        
    • Clones: everyone who pulled already has it.
      • 
        
    • Forks: copies of your repository keep their own history.
      • 
        
    • Caches and pull requests: GitHub can keep cached views; its docs say to contact support to remove them.
      • 
        
    • Scrapers: bots scan public pushes for keys, often within minutes.
      • 
      
    
      
    SO Clean the history to stop the leak spreading, but assume the secret is already out. Revoking it is the real fix.
    
    
    
    
    
      
    The flip side: a force-push can also hide things from you.
    
      
    October 2026 · LiteLLMThe attacker's workflow change was pushed, used to publish a malicious release, then removed from main's history with a revert and a force-push, and the workflow run records were deleted.
    
      
    Blocking force pushes on main, and watching the audit log, make that much harder.
    
    
    
  
    
  
    ~3 min
    • SayHistory rewriting tools (git filter-repo, BFG) are worth using, but they only change your copy and GitHub's. Everything already copied stays copied.
    • CheckGitHub Docs, "Removing sensitive data from a repository", for current steps and how to request removal of cached views.
