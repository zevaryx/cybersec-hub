// WHY THIS TALK

A hash is a name you can check

2017the year the first practical SHA-1 collision was published (SHAttered).
30hashes are enough to prove one entry is in a log of a billion.
10 minis how long a Sigstore signing certificate stays valid.
  • A good hash is a fingerprint: same input, same output, and no known way to make two inputs share one.
  • So if you know the right fingerprint, you can check the content. The whole game is who gave you the fingerprint.
  • Three jobs built on that: naming data, proving things about big collections, and verifying what you download.

Sources: shattered.io · RFC 9162 · Sigstore: certificate authority

Git · every object has a hash for a nameFiles, folders, commits and tags are stored under the hash of their content. The commit ID is a fingerprint of the whole history behind it.
Containers and packages · digests and lock filesA container image digest, an npm lock file's integrity value and Python's --hash all pin exact bytes, not a version label.
Certificates and releases · public, hash-based logsCertificate Transparency, Go's checksum database and Sigstore's log all use Merkle trees so nobody can quietly rewrite the past.

~3 min

  • SayYou probably think of hashes as the thing that stores passwords. That's one job, and a special one: there you want the hash to be slow. Everywhere else you want it fast and you want it to be a fingerprint. The talk is about the fingerprint jobs.

Sigstore's certificate authority page says Fulcio certificates are valid for 10 minutes.

Name it by what it is

Edit the message, or change one character, and watch the fingerprint.

WhereThe name looks like

The two rules that make it workChange any byte and the name changes (try it on the left). And nobody can make a different file with the same name. A version label like 1.4.2 or a tag like latest promises neither.

    

  

  
~4 min
  • SayNormal names are labels: someone chooses them, and someone can move them. A content address is computed from the bytes, so it can't point at anything else. Type a different message: about half of the 256 bits flip every time, however small the change. That's the avalanche effect, and it's what makes the hash useful as a fingerprint.
  • AskIf I tell you a package's name and version, do you know exactly which bytes you'll get? Answer: no, only if the registry never changes it. A hash is the only name that guarantees the bytes.
  • TipSources: Docker's digest page (tags are mutable, digests are immutable); npm's package-lock docs (the integrity field is a Subresource Integrity string, sha512 or sha1); pip's secure-installs page (--hash pins an exact file, and using it on one requirement turns hash-checking on for all). The Go row comes from the Go blog's checksum-database post (go.sum records hashes of module versions).
  • CheckThe Docker digest page doesn't say what exactly is hashed; per the OCI image specification the digest of an image is the SHA-256 of its manifest, which lists the layers by their own digests. Confirm against the spec if you say it out loud.

// CONTENT ADDRESSING 02
Git under the hood: a mini Git

  

    

      

      

      

    

    

      1 · Edit the README of commit…
      

        
        
        
      

      
      

        
        
      

      2 · Hash format
      

        
        
      

      
Each object is named by the hash of type size NUL content. A file is a blob, a folder a tree of names and IDs, and a commit points at one tree and its parent.

    

  

  
~7 min
  • SayThis is real Git's format, written from scratch, and I checked its IDs against the real git program. A blob's name is the hash of its content with a small header. A tree lists names and the IDs of what they point to. A commit names one tree and one parent. Now edit the README of the oldest commit and look at what turns pink: the blob, the tree, that commit, and then every commit after it, because each one holds its parent's ID inside it. Trees and files of the later commits stay the same: they never mention the parent. Now edit the newest commit instead: only that one changes. That's why you can't change history quietly: everyone who holds the old tip ID can tell.
  • AskWhat does a force-push really do, then? Answer: it makes new commit IDs from the changed point onward, and moves a branch label to them. The old commits still exist until they're cleaned up, and everyone else's copy has to be fixed.
  • TipFormat: Git's hash-function-transition document says an object's name is the hash of its type, length, a NUL byte and its content, and that a SHA-256 repository names objects with SHA-256 throughout (trees hold raw 32-byte IDs). The demo's timestamps and author are fixed so every run gives the same IDs. Tested against Git 2.56.0: the commit, tree and blob IDs for a three-commit history matched in both object formats.
  • ShowFlip to SHA-256 and the IDs get longer (64 hex characters instead of 40); everything else behaves the same. Real Git does this for a repository created with git init --object-format=sha256.

Git's slow move from SHA-1 to SHA-256

  

    

      

      

      
Same file, two namesOn Git 2.56.0, printf 'hello\n' | git hash-object --stdin printed the SHA-1 form above. In a repository made with --object-format=sha256 it printed the SHA-256 form.

      
Sources: Git: hash function transition · Git: breaking changes · shattered.io

    

    

      
    
        
  1. 2017SHAttered: a real SHA-1 collision. Git adds a collision-detecting SHA-1 (Git 2.13).
    2. 
        
  2. 2018The project picks SHA-256 as the successor.
    3. 
        
  3. 2020Git 2.29 ships SHA-256 repositories, marked experimental, with no interoperability yet.
    4. 
        
  4. SinceWork on a compatibility mode that maps between SHA-1 and SHA-256 names.

    6. 
      

    

  

  
~4 min
  • SaySHA-1 is broken for collisions: researchers made two different files with the same SHA-1 in 2017. Git didn't panic, for two reasons. Git's hashing isn't a signature: nobody has found a way to swap content in a repository someone already trusts. And Git added a check that detects the known attack patterns. But the direction is clear, and the project has been moving to SHA-256 for years, carefully, because everything that touches a repository has to understand the new IDs: forges, CI, tools, libraries.
  • TipWhat I read: Git's BreakingChanges page says the default for new repositories will change from sha1 to sha256 in Git 3.0, "There is no planned release date for this breaking version yet", the change waits for the ecosystem ("popular Git libraries, applications and forges"), and "There is no plan to deprecate the sha1 object format at this point in time". The hash-function-transition document describes the compatibility mode (an SHA-256 repository stores a mapping to SHA-1 names) and says SHA-256 repositories can't be read by older Git, and, until the protocol gains SHA-256 support, SHA-256 storage on public-facing servers is "strongly discouraged". Git 2.13's release notes say the collision-detecting SHA-1 by Stevens and Shumow was integrated and made the default. Git 2.29's notes call SHA-256 support experimental, with no interoperability yet.
  • CheckSeveral blog posts give a date for Git 3.0 (April 2027 appears); Git's own page says there isn't one, so the slide follows Git. I didn't verify the status of SHA-256 support on GitHub or other forges: look before telling anyone they can use it for hosted repositories. "Since" row (compatibility mode work) is from the transition document plus Git 2.52's release notes, which list "the beginning of SHA1-SHA256 interoperability work" and describe the compatObjectFormat extension as unfinished.

// CHECKPOINT 1 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. Why does changing an old commit change the ID of every commit after it?
    Hint
    What does each commit contain besides your files?
    Answer
    Each commit includes its parent's ID, and its own ID is the hash of all of that. Change the old one and its ID changes, so the next commit's content changes, so its ID changes, and so on up to the tip. Anyone holding the old tip ID can see that history was rewritten.
    2. 
      
  2. Two people on different continents both commit the same file contents. What do they share, without ever talking?
    Hint
    What is a blob's name computed from?
    Answer
    The same blob ID. The name depends only on the content (and the object type), so identical content gets the same name everywhere. That's what makes deduplication and cheap comparison possible.
    3. 
      
  3. SHA-1 has a known collision attack. Why isn't every Git repository broken, and what should change over time?
    Hint
    What would an attacker need to do to hurt a repository you already trust?
    Answer
    A collision lets someone create two files up front that share an ID. It doesn't let them replace a file in a repository that already exists, and Git detects the known attack patterns. Still, the safer long-term answer is a stronger hash, which is why SHA-256 repositories exist and are planned to become the default for new repositories.
    4. 
    

  

  
5 min
  • ShowPairs talk for 2 minutes, then share. The timer starts by itself.
  • CheckQuestion 3's claim that a collision doesn't let an attacker replace a file in an existing repository is the standard second-preimage versus collision distinction: nobody has published a second-preimage attack on SHA-1. Keep the answer to that.







  
// MERKLE TREES 01
Building a tree from leaves to root

  

    

      

      

      

    

    

      Leaves: one per line (up to 8)
      
      

      
    
        
  • Hash each item to make a leaf. Hash pairs of hashes to make a parent. Repeat to one root.
    • 
        
  • Change any leaf and the hashes on its path to the root change (pink). The rest stay put.
    • 
        
  • The root is a fingerprint of the whole set.
    • 
      

    

  

  
~5 min
  • SayHash every item. Then hash each pair of hashes, and keep going until there's one hash. That's a Merkle tree, and the top hash is the root. Edit one line and notice that only the hashes on the way up change. That property is what's useful: if you know the root, any change anywhere changes it. With five items the tree isn't balanced, and that's fine: the rule is that the left side takes the largest power of two that fits (four here), and the rest goes right.
  • TipThis follows RFC 9162's tree definition (also used by RFC 6962 for Certificate Transparency): a leaf hash is HASH(0x00 || data), an inner node is HASH(0x01 || left || right), and for n entries the left subtree takes the largest power of two smaller than n. Boxes show the first six hex characters of each SHA-256. The empty tree is the hash of the empty string. Tested against RFC 6962's published test-vector roots for 1 to 8 leaves.
  • CheckThe 0x00 and 0x01 prefixes are explained on the domain-separation slide a few minutes from now, so for now just say "there's a byte added to separate leaves from parents".

// MERKLE TREES 02
Inclusion proofs: a handful of hashes

  

    

      

      

      
 path from the entry to the root  the proof: hashes you're given

    

    

      
    
      
    
      
    
      
    
      
    
    
    
  
    
  
    ~6 min
    • SayI hold only the root. You tell me that "cafe.example" is entry 3 of this log. To check, I don't need the log: you send the entry plus the sibling hashes along its path, three here. I hash the entry, combine it with the first sibling, then the next, then the next, and if I get the root I already trust, the entry is in the log. Pick each entry and watch the pink hashes: they're all I needed. For a log of a billion entries that's thirty hashes, a few hundred bytes of hash.
    • AskWhy can't someone hand me a fake entry with the same proof? Answer: they'd need to find a different input that produces the same leaf hash, a second preimage. Press "Swap in a different entry" and see the recomputed path go somewhere else.
    • TipThe verification steps follow RFC 9162 section 2.1.3 (the iterative algorithm over the leaf index and tree size); the demo's log of eight entries is made up, and tested for every position of every tree size from 1 to 40, including rejecting a wrong leaf or a wrong index. The size line uses ceil(log2 n), the bound RFC 9162 gives.

    // MERKLE TREES 03
    Where Merkle trees are used
    
  
    
    
    
      
    Certificate TransparencyEvery publicly trusted TLS certificate is meant to be recorded in public, append-only logs built as Merkle trees. Anyone can check a certificate is logged, and monitors watch for certificates nobody expected.
    
      
    Go's checksum databasesum.golang.org is a transparency log of module hashes. Before it adds a line to go.sum, the go command checks inclusion and consistency proofs, so a proxy or even an author can't hand you different code for the same version.
    
      
    Sigstore's RekorThe public log for signed software releases. Version 2, announced in October 2025, is built on a tile-based log library.
    
      
    GitTrees and commits form a Merkle structure (a "Merkle DAG"): a commit ID covers the tree, its files and the parent commit. Not one single balanced tree, but the same idea.
    
      
    File sync and big downloadsSystems that move large files in pieces (peer-to-peer downloads, sync tools, content-addressed storage) hash each chunk and combine the hashes, so one damaged chunk is found and re-fetched alone.
    
      
    BlockchainsBlocks commit to their transactions with a Merkle root, so light clients can check one transaction with a short proof. Same maths, different context.
    
    
    
    
    Sources: certificate.transparency.dev · Go blog: module mirror and checksum database · Sigstore blog: Rekor v2
    
  
    
  
    ~3 min
    • SaySame trick everywhere: when a lot of data has to be checked by people who don't hold all of it, keep one small root and prove things against it. Notice who benefits: not the log's operator, but the public, who can check the operator without trusting it.
    • TipWhat I read: certificate.transparency.dev (logs are append-only ledgers, leaves are hashes of certificates, the log signs the root as a Signed Tree Head, monitors use consistency proofs); the Go blog post of 29 August 2019 (the checksum database is "built on a Transparent Log (or Merkle tree) of hashes backed by Trillian", the go command checks inclusion and consistency proofs); the Rekor v2 announcement of 10 October 2025 (a tile-backed log built on the Tessera library). RFC 6962 (June 2013) is what Certificate Transparency's deployed logs were built on; RFC 9162 obsoletes it and is itself Experimental.
    • CheckI did not verify the current Certificate Transparency policy of the browsers, or which RFC the largest logs run today (RFC 6962's API versus newer tile-based designs). The file-sync and blockchain cards are general descriptions from background knowledge, not from a source read for this talk: check any specific product's claim before naming it.

    // MERKLE TREES 04
    Why leaves and parents hash differently
    
  
    
    
    
      
      
    Tree A: four leavesa · b · c · d
    
      
    Tree B: two leaves, each the two hashes it replaces, glued togetherH(a)‖H(b) · H(c)‖H(d)
    
      
    
      
    
    
    
    
    
      
      
        
    • Without a marker, a leaf and a parent are both "a hash of some bytes". An attacker can present a parent's two child hashes as if they were data.
      • 
        
    • Then two different sets of data share one root, and a proof for one can pass for the other.
      • 
        
    • The fix is cheap: one different byte in front of leaves and parents. It's called domain separation.
      • 
        
    • The general lesson: when hashing different kinds of thing, label what you're hashing.
      • 
      
    
    
    
  
    
  
    ~4 min
    • SayUncheck the box. Two different datasets, one root. Tree B's leaves are just the intermediate hashes of tree A, glued together. Without separate markers, nothing says "this is a leaf, not a parent", and the structure is ambiguous. This is why RFC 6962 and 9162 put a 0x00 byte before leaves and 0x01 before parents. Tick the box again and the roots differ. The lesson applies to any code that hashes different kinds of data with the same function: label them, or someone will confuse them.
    • TipRFC 9162 says the prefixes provide domain separation for second-preimage resistance (RFC 6962 says leaf hashes use 0x00 and interior node hashes use 0x01, so the two stay distinct). The demo is a defensive illustration only: it shows two toy datasets with one root, and it's tested in Node (the unprefixed trees collide, the prefixed ones don't).

    // MERKLE TREES 05
    Consistency proofs: the log only grew
    
  
    
    
    
      
    
      
    
        
        
        
      
    
      
    
    
    
    
    
      You saved the root when the log had 5 entries
      
    
      
      
    
      
    
    
    
  
    
  
    ~6 min
    • SayAn inclusion proof says an entry is in the log. A consistency proof says something different and just as important: the log you see today contains the log you saw last week, unchanged. You kept the old root. The log gives you a few hashes. You recompute both roots from them, the old one and the new one, and if both match, nothing earlier was altered or removed. Append some entries and ask: it works. Now quietly rewrite entry 2 and ask again: an honest proof can't exist, and the check fails. This is how monitors keep a public log honest without storing all of it.
    • AskWhat does it buy you that signing the root alone doesn't? Answer: a signed root says what the log claims now. Only a consistency proof ties the new claim to the old one, so a log can't show different histories to different people without being caught (given someone compares the roots they saw).
    • TipProofs and verification follow RFC 9162 sections 2.1.4 (consistency proofs, with the verification algorithm that recomputes both roots), tested for every pair of sizes from 1 to 40, including a rewritten old root and a rewritten new root failing. Comparing roots seen by different people is "gossip", which the talk mentions but does not demo.

    // KEEPING DOWNLOADS HONEST 01
    Checksums vs signatures
    
  
    
    
    
      
    The maintainer publishes a file, its SHA-256, and a signature. You got their public key earlier, somewhere else. What happens to the download?
    
      
    
      
    
      
    
    
    
    
    
      
      
      
      
      
      What each one provesChecksum: these bytes match this number. Useful against damage, or when the number came from somewhere the attacker can't touch. Signature: these bytes were approved by the holder of this key. Only as good as how you got the key and how well it's guarded.
      
    
      
  
      
  
      ~6 min
      • SayGo through the five situations. Flaky connection: both checks catch it. A bad mirror: the checksum still catches it, because the number came from the official page. The website itself broken into: the attacker replaces the file and the number, so the checksum passes, and that's the case people forget. The signature fails, because the attacker can't sign without the key. The last one is the honest limit: if the signing key is stolen, both pass. So the next questions are how to avoid long-lived keys, and how to notice a bad signature after the fact. That's the next slide.
      • AskThe download page lists a SHA-256 next to the link. What does that protect against, and what doesn't it? Answer: transfer errors and some bad mirrors. Not a compromised site, since it can change both.
      • TipThe signatures here are real ECDSA over P-256 with the page's own from-scratch implementation (shared/crypto.js), with a key made fresh in your browser; the "stolen key" case just signs the attacker's file with the same key. The signer's public key is assumed to have been obtained earlier through a separate channel.

      // KEEPING DOWNLOADS HONEST 02
      Signed releases and transparency logs
      
  
      
    
      
      
      
      
      
      
      
    
      
    
      
      
      What the verifier checks
      
      
        
        
      • The signature on the artifact's digest is valid for the key in the certificate.
        • 
        
      • The certificate chains to Sigstore's root and was valid when it was logged.
        • 
        
      • The identity in the certificate is the one you expect: this repository, this workflow.
        • 
        
      • The signature is in the public log, with an inclusion proof: the same Merkle trees as before.
        • 
      
      
      
      NO LONG-LIVED KEY to lose, rotate or steal. The trust moves to identity and the log.
      
      
      Sources: Sigstore overview · Rekor v2
      
    
      
  
      
  
      ~5 min
      • SayClick through the six steps. The signer proves who they are to an identity provider, makes a one-off key, gets a certificate valid for about ten minutes that ties that identity to that key, signs, and throws the key away. The signature goes into a public log. Verifiers don't need to know a key in advance: they check the identity in the certificate against what they expect, and the log entry against the log's tree. A stolen key doesn't exist to steal. And because the log is public, a signature made in your project's name is visible, so you can watch for ones you didn't make.
      • TipFrom Sigstore's docs: Fulcio is the certificate authority that checks an OIDC token and issues a short-lived certificate (10 minutes) binding the identity to the key; Rekor is an append-only transparency log of signing events; Cosign is the client; keyless signing uses an ephemeral key. The Rekor v2 post (10 October 2025): a tile-backed log, inclusion proofs returned on upload, entry types for signatures and attestations, cosign 2.6.0 and later support it. This slide's flow is a simplified outline.
      • CheckReal keyless verification has extra details this slide leaves out (trusted roots delivered with TUF, signed timestamps, bundle formats, and Rekor v2 delegating timestamps to a separate timestamp authority). Check Sigstore's current documentation for the exact verification steps before telling people how to run them.

      // KEEPING DOWNLOADS HONEST 03
      Reproducible builds
      
  
      
    
      
      
      Two people build the same source. Will the files hash the same? Switch on the fixes one at a time.
      
      
      
        
        
        
      
      
      
      
      
      
      
      
    
      
    
      
      
      The ideaA build is reproducible when anyone, given the same inputs, can recreate bit-for-bit identical artifacts. Then a hash isn't just something the publisher says: anyone can rebuild and compare.
      
      
        
        
      • The usual causes of drift: timestamps, file order, build paths, locale, random IDs.
        • 
        
      • The fixes are mostly boring and mechanical.
        • 
        
      • It lets independent rebuilders catch a tampered build server.
        • 
      
      
      
      Sources: reproducible-builds.org: definition · SOURCE_DATE_EPOCH
      
    
      
  
      
  
      ~4 min
      • SayThis is a toy "build" that bundles three files. Alice and Ben build the same source and get different hashes, for silly reasons: the time was a second apart, the file system listed the files in a different order, and the build folder's name is baked in. None of it is malicious, but a difference you can't explain looks exactly like tampering. Switch on the fixes and the hashes match. Real build tools have these same three culprits, among others, and the standard way to fix the clock is the SOURCE_DATE_EPOCH environment variable.
      • TipThe definition quoted is reproducible-builds.org's: "any party can recreate bit-by-bit identical copies of all specified artifacts", checked by bit-by-bit comparison, usually with cryptographic hashes. SOURCE_DATE_EPOCH is described there as a standardised environment variable that distributions can set centrally, holding seconds since the Unix epoch. The demo's build, files and paths are invented.

      // KEEPING DOWNLOADS HONEST 04
      Provenance and SLSA levels
      
  
      
    
      
      
      Build track
      
      
      
        
      LevelWhat you get
      
        
          
      L0Nothing: no claims about the build.
      
          
      L1Provenance showing how the package was built.
      
          
      L2Signed provenance, generated by a hosted build platform.
      
          
      L3A hardened build platform.
      
              
      
      
      
      Source track (new in v1.2)
      
      
      
        
          
      L1Use a version control system.
      
          
      L2Preserve change history and generate source provenance.
      
          
      L3Enforce organisational technical controls.
      
          
      L4Require code review.
      
              
      
      
    
      
    
      
      
      Provenance, in one picture
      
      
      
      
        
        
      • Provenance is a signed statement about an artifact's digest: what built it, from which source, how.
        • 
        
      • It's the hash that ties the statement to the file. Change the file and the digest no longer matches.
        • 
        
      • Levels measure how hard the claims are to forge, not whether the software is good.
        • 
      
      
      
      Sources: SLSA v1.2: build track · source requirements
      
    
      
  
      
  
      ~4 min
      • SaySLSA, said "salsa", is a ladder for how much you can trust a build's story. At level 1 there's a statement of how it was built, easy to fake. At level 2 the statement is signed by the build platform. At level 3 the platform itself is hardened so one build can't tamper with another. The picture: the provenance names the artifact by its hash, which is why the whole thing rests on the same fingerprint idea. A level isn't a verdict that the code is safe: it's about how trustworthy the claim of where it came from is.
      • TipFrom slsa.dev, v1.2 (status Approved): Build L1 "Provenance showing how the package was built", L2 "Signed provenance, generated by a hosted build platform", L3 "Hardened build platform". The build page also says L1 provenance "can be used to prevent mistakes but is trivial to bypass or forge". The Source track levels as written on the source-requirements page: L1 use a version control system, L2 preserve change history and generate source provenance, L3 enforce organizational technical controls, L4 require code review. The provenance sketch is a simplified, made-up example in the shape of an in-toto statement; it is not a real artifact.
      • CheckSome secondary sources describe the Source track with three levels; the v1.2 source-requirements page (re-read 11 November 2026) lists four, with "Level 0" only meaning no Source VSA. Re-read slsa.dev before presenting, because levels and wording have changed between versions.

      Lock files and pinning by digest
      
  
      
    
      
      
      
        
        
        
      
      
      
      
      
    
      
    
      
      
        
      
        
    
        
  
        
  
        ~4 min
        • SayEverything in the first column is a label: a tag, a range, a version number. Whoever controls the label can change what it points at. The green lines name exact bytes. The pattern is the same in every ecosystem: a Docker image by its sha256 digest, a GitHub Action by its full commit hash, a Python package with its file hash, an npm package through the lock file's integrity value. Pinning isn't about never updating: it's about making an update a visible change you review, instead of something that happens to you.
        • AskIf you pin everything by hash, who tells you about security fixes? Answer: a tool that opens update pull requests (Dependabot or Renovate style), so the update is a reviewable diff, and your scanners.
        • TipThe checker is a simplified pattern matcher for four formats (Dockerfile FROM lines, workflow uses: lines, pip requirements, npm-style JSON lines). Sources: pip's secure-installs page (a hash per requirement pins an exact file, and one hashed requirement turns hash-checking on for all, so unhashed ones then fail); npm's lock file docs (integrity is an SRI string, sha512 or sha1); Docker's page on digests (tags mutable, digests immutable). Pinning an Action to a full commit hash is GitHub's own advice for third-party actions, which I did not re-read for this talk: check it.

        Pause and discuss
        
  
        
    
        Talk with a neighbour for a couple of minutes, then we share answers.
        
    
          
      
        1. A website lists a file's SHA-256 next to the download link. What does that protect against, and what doesn't it?
          Hint
          Who can edit the page?
          Answer
          It catches accidents (a damaged download) and a bad mirror, since the number came from the official page. It doesn't help if the site itself is compromised: whoever can replace the file can replace the number. A signature checked against a key you got elsewhere, or a log you can check, covers that.
          2. 
      
        2. A Merkle proof for one entry in a log of a million needs about 20 hashes. What does the verifier already need to hold, and why is that enough?
          Hint
          What does the proof get compared to at the end?
          Answer
          Only a trusted root (and the log's size). The verifier hashes the entry, combines it with the proof's hashes up the path, and compares the result with the root. If it matches, the entry must be in the tree, unless someone can find a second input with the same hash.
          3. 
      
        3. Your lockfile pins every dependency by hash. Name one thing that still isn't covered.
          Hint
          The hash says "these are the bytes you got last time". Does it say they're good?
          Answer
          Several: the first time you added the dependency (the hash can pin a bad package just as well), bugs and vulnerabilities in the pinned version, and the build and CI process around it. Pinning makes change deliberate; it doesn't make the content trustworthy.

        // CHOOSING A HASH 01
        Which hash for which job?
        
  
        
    
        
      
        Pick the job:
        
      
        
      
        
      
        
    
        
    
        
      
        The one-page version
        
      
        
        
        JobUse
        
        
          
        Integrity, IDsSHA-256 or better
        
          
        Message authenticationHMAC, or an AEAD
        
          
        PasswordsArgon2id, scrypt, bcrypt
        
          
        Keys from keysHKDF
        
          
        Hash tablesFast non-crypto, keyed if exposed
        
                
      
        
      
        RULE OF THUMB Never invent a construction. Pick the named tool for the job, from a maintained library.
        
    
        
  
        
  
        ~5 min
        • SayFour questions pick the right tool. Is the input a secret? Is there a key? Do you want it fast or slow? Could someone attack it? Click through the jobs. The two mistakes that come up most: using a fast hash for passwords, and hashing a key and a message together to make a MAC. Use a password hash and HMAC instead; both are in your standard library.
        • TipNIST's hash-functions page lists SHA-2 (FIPS 180-4) and SHA-3 (FIPS 202) as approved hash families and says it deprecated SHA-1 in 2011 and published a plan in December 2022 to transition away from it (NIST's December 2022 announcement says by 31 December 2030). Length extension is a property of the SHA-2 construction that HMAC is designed around; I did not re-fetch a primary source for it, but it is standard and in RFC 2104 and in NIST guidance on keyed hashes. The BLAKE3 and SipHash mentions are background knowledge.
        • CheckThe mention of "SHA-256 or better" simplifies a bigger choice: SHA-512, SHA-3 and BLAKE3 are fine for integrity too. If a standards body, a compliance regime or an existing protocol picks the algorithm for you, follow that.
