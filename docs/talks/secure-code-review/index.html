// WHY THIS WORKSHOP

The bug is often right there in the diff

A01Broken Access Control, first in OWASP's Top 10:2025.
A05Injection, fifth. A02 is Security Misconfiguration and A04 Cryptographic Failures.
4rounds today, one for each of those four categories.
  • A diff shows what changed and nothing else, so the first skill is asking what it connects to.
  • Tools find patterns. People find the missing check: the one thing that isn't in the diff at all.
  • The goal is not to catch everything. It's a habit you repeat on every change that touches input, permissions, secrets or config.

Sources: OWASP Top 10:2025 · OWASP Secure Code Review Cheat Sheet · Adam Langley on Apple's bug · Apple, iOS 7.0.6

"goto fail", February 2014 · one line, doubledApple's iOS 7.0.6 advisory says Secure Transport failed to validate the authenticity of a connection. Analyses trace it to a duplicated goto fail; that skipped the signature check. A change this small is easy to read past, and easy to see once someone asks "what does this line skip?"
if ((err = HashUpdate(...)) != 0)
    goto fail;
    goto fail;          // the duplicate: always runs
if ((err = VerifySignature(...)) != 0)   // never reached
    goto fail;
What people do best, per OWASPIts cheat sheet says manual review is best at business-logic flaws, authorization logic, race conditions, cryptographic misuse and design problems, and tools help with triage.

~3 min

  • SayOWASP's Top 10:2025 puts Broken Access Control first, Security Misconfiguration second, Cryptographic Failures fourth and Injection fifth. Those four are today's four rounds. The goto fail story is the shape of every bug we'll meet: a small, local, plausible change whose damage is in what it skips. The code on the slide is a paraphrase to show the shape, not Apple's source.
  • AskWhen did a review last stop a bug for you, and what did the reviewer notice? Often: something that was missing, not something that was wrong.
  • TipSources: top10.owasp.org/2025 lists A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions. OWASP's Secure Code Review Cheat Sheet separates baseline reviews (a whole codebase) from diff-based reviews (a pull request), and for diffs asks about impact on existing controls, new attack vectors, trust boundaries and regressions; it names data-flow tracing from sources to sinks as a technique and manual review as best for business logic, authorization logic, race conditions, cryptographic misuse and architecture-level design flaws. Apple's advisory 2014-02-21-2 for iOS 7.0.6 describes Secure Transport failing to validate the connection's authenticity ("restoring missing validation steps"); the CVE is CVE-2014-1266; the duplicated line and function name (SSLVerifySignedServerKeyExchange) are from Adam Langley's analysis.
  • CheckI did not read Apple's source file itself, so the excerpt is marked as a paraphrase and no line numbers are given. The OWASP page gives no exact release date, so the slide says "Top 10:2025" without one.

// A METHOD 01

Follow the data: sources, sinks and trust boundaries

A source is where outside data enters (a query string, a body, a header). A sink is where it does something (a query, HTML, a shell, a file path, a redirect). Click a variable to follow it.

    ~9 min
    • SayEvery injection, traversal, XSS and redirect bug has the same skeleton: a value from outside travels, unchanged, to somewhere that treats it as more than data. So the whole method is to find where outside data enters, follow it, and ask what happens at each place it lands. A trust boundary is any point where data crosses from something you don't control to something you do: the request, a file upload, a webhook, another service, even a database row that someone else wrote.
    • ShowClick term: it comes from the query string, is copied into like, then into sql, and ends in a query and in the page. Two sinks from one variable. Click page: it is wrapped in Number(), so it is cleaned on the way and reaching the query is fine. Click sort: it reaches the query too, and nothing cleans it, even though it's a column name and parameters can't fix that: it needs an allow-list. Click rows: this is data from the database, not from the request, but it lands in HTML, so ask where it came from. The tracer is a text matcher for one invented snippet, not a real analyser.
    • AskWhich of these variables would a placeholder fix, and which needs a different fix? term and like: placeholders. sort: an allow-list of column names. page: already a number.
    • TipReal tools do this (taint analysis in static analysers like CodeQL and Semgrep), with the same vocabulary: sources, sinks, sanitizers. The OWASP cheat sheet lists data-flow tracing from sources to sinks as a review technique. Reviewers do it by hand with the editor's "find all references".

    // A METHOD 02
    What to read first in a diff
    
  
    
    
      
      
    1. New entry pointsA new route, handler, job, webhook or message consumer is a new front door. Who can call it? What does it return?
      2. 
      
    2. Permission and role changesAnything that adds, removes or moves a check. A deleted line can be the bug.
      3. 
      
    3. Parsing and building thingsQueries, paths, commands, HTML, URLs, deserialisation: places where text turns into something that acts.
      4. 
      
    4. Crypto, tokens and secretsKeys, hashes, random numbers, sessions, anything named token or secret, and anything new in config or tests.
      5. 
      
    5. Config and defaultsNew flags, CORS, debug, timeouts, error handlers. Defaults ship to everyone.
      6. 
      
    6. Everything else, lastRenames, formatting and refactors rarely change who can do what, but check they don't quietly drop a check.
      7. 
    
    
    
    TIP Read the tests first. A test for "someone else's id returns 404" tells you the author thought about it. Its absence tells you where to look.
    
  
    
  
    ~6 min
    • SayYou can't read every line with the same energy, so spend it where permissions and parsing happen. Start with entry points because everything else hangs off them. Look at deleted lines on purpose: removing a check or a validation is the quietest way to introduce a bug, and diff tools make deletions easy to skim. And read the tests: they tell you what the author was afraid of.
    • AskWhat would you open first in a pull request that "just updates the config"? The defaults it changes, and who they apply to.
    • TipThis order follows the diff-based review focus in OWASP's Secure Code Review Cheat Sheet (impact on existing controls, new attack vectors, trust boundaries, regressions) turned into a reading order; the ordering is a suggestion, not a standard. Review small changes: big pull requests hide things.

      • SaySix questions, asked of every change that touches input, permissions, secrets or config. The fourth one is the cheapest high-value habit in this talk: take the thing the code accepts and picture an empty value, an enormous one and a hostile one. The probes on the right are a prompt for that picture, not a test suite.
      • ShowPick "An id in the URL": somebody else's id, an id that doesn't exist, and the same two cases both need to look identical to the caller, or the difference leaks which records exist. Pick "An uploaded file": size, type by content, and never using the name in a path.
      • AskWhich question would have caught the last security bug you had to fix? Often "whose record is it?"
      • TipThe probe values are illustrative prompts, not payload lists, and every one is harmless text. They're there to make you ask about limits, types and ownership. Whether 2147483648 matters depends on the language and the column type.

      How the rounds work
      
  
      
    
      
      
      1 · Flag (about 10 min)In pairs, click the lines of the diff you'd comment on. One of you drives, one challenges. Don't fix yet: find first.
      
      
      2 · Check"Check my flags" tells you how many findings you hit and which flags were noise. It doesn't say where the misses are.
      
      
      3 · Reveal (about 5 min)"Show answers" lists every finding with why it matters, a fix and a model review comment. Score the round.
      
    
      
    
        
      
      • Every diff is invented and deliberately flawed. Some have decoys: lines that look scary and are fine. One diff is clean, because knowing when to approve is part of the job.
        • 
      
      • Flagging everything is the same as flagging nothing. Aim.
        • 
      
      • The scoreboard keeps the tally. There's a badge for finding them all.
        • 
    
      
  
      
  
      ~4 min
      • SayHere's the loop for each round. Pairs flag lines for ten minutes. Press "Check my flags" for a score without spoilers. Then "Show answers" for the full reveal: each finding has a plain explanation, a fix in the same language and a model review comment, so you can compare your wording with a good one. Pairs keep their own tally on the scoreboard slide.

The third tab in rounds 1, 3 and 4 is a bonus.

      // ROUND 1 · 15 MIN · A05 INJECTION
      Data treated as code
      
  
      
  
      ~15 min
      • SayRound one is the classic: text from outside ends up somewhere that treats it as an instruction. Queries, shell commands, HTML and file paths, plus the redirect that sends people elsewhere. Pairs have ten minutes; use the method: where does the input enter, and where does it land?
      • ShowAt the reveal, walk each finding in the same order: what the code does, what that allows, the fix, and the model comment. Notice that all the fixes share a shape: keep data out of code. Placeholders for queries, an argument array instead of a shell string, escaping or an auto-escaping template for HTML, an id instead of a filename, a local-path check for redirects.
      • AskWhich diffs would a linter likely have caught, and which needed you? The query and the shell call have well-known patterns. The path check and the redirect need you to ask what the value is allowed to be.
      • TipReferences: Python's sqlite3 docs say to always use placeholders instead of string formatting to avoid SQL injection. Node's child_process docs say never to pass unsanitized user input to exec, and that execFile does not spawn a shell unless the shell option is enabled. CWE numbers shown in the reveal, checked against cwe.mitre.org on 11 November 2026: 89 (SQL injection), 770 (Allocation of Resources Without Limits or Throttling), 78 (OS command injection), 22 (path traversal), 79 (XSS), 601 (URL Redirection to Untrusted Site, "open redirect"). The exercise's fix for the path finding (resolve then check the prefix) is a common pattern; a robust version also considers symlinks.
      • CheckI didn't re-read Flask's send_from_directory docs fully, so the fixes don't rely on it. The convert command is ImageMagick's; its exact flags don't matter to the exercise.
      • Next"Round 2: authorization."
      

      


      
  
      // ROUND 2 · 15 MIN · A01 BROKEN ACCESS CONTROL
      Authorization
      
  
      
  
      ~15 min
      • SayRound two is about what isn't in the diff. Both diffs check that you're signed in. Neither checks enough. Authentication says who you are; authorization says what you may do, to which record. The question to carry is "whose record is it, and where is that enforced?"
      • ShowThe orders diff has a comment saying TODO: security: click it for the badge. Then the real findings: any signed-in user can read any order and delete any order. In the profile diff, the update applies every field in the request body (mass assignment), and the admin export is "protected" by hiding a link. Hidden isn't blocked. All three fixes put the rule on the server and make "not yours" look the same as "doesn't exist".
      • AskWhere in your codebase would a new endpoint get its ownership check by default, and where only if someone remembers? The answer is the case for central, deny-by-default checks.
      • TipCWE-639 is "Authorization Bypass Through User-Controlled Key" (the order id). The profile finding is mass assignment (CWE-915); the admin route is a missing function-level check (CWE-862). Developer 5 (Building Secure APIs) covers object-level and function-level authorization in more depth. "Blocking", used in the model comments, is a team convention, not part of any standard.
      • Next"Round 3: secrets and crypto."
      

      


      
  
      // ROUND 3 · 15 MIN · A04 CRYPTOGRAPHIC FAILURES
      Secrets and crypto
      
  
      
  
      ~15 min
      • SayRound three: the code works and the tests pass, and the design is wrong. You don't need to be a cryptographer to spot these. You need to know three rules: never write secrets in source, use the tool built for the job (a slow password hash for passwords, a secure random source for tokens, an authenticated mode for encryption), and don't invent your own.
      • ShowIn the first diff the keys are in the code (they live in Git history forever), the password is hashed with fast, unsalted MD5, and the card number is encrypted with a fixed key in a mode that shows patterns. The reset-token diff uses Math.random, never checks expiry or one-time use, and stores the token as-is. At the reveal, check the key phrase in each model comment: "Argon2id", "fresh nonce each time", "constant-time compare".
      • AskIf a secret has been committed, is deleting it in the next commit enough? No. It's in history and in every clone. Rotate it.
      • TipOWASP's Password Storage Cheat Sheet recommends Argon2id first (minimum 19 MiB of memory, 2 iterations, 1 degree of parallelism) and says fast hashes such as SHA-256 are unsuitable because they allow large numbers of guesses. MDN's Math.random() page says it is not cryptographically secure and not to use it for anything related to security; Python's secrets docs say the same of the random module and give token_urlsafe and compare_digest (constant-time compare). The sample "payment key" is obviously fake on purpose so scanners don't flag this deck. ECB's weakness (equal blocks encrypt equally) and the case for AES-GCM are standard background, which I didn't re-read a source for here; check NIST SP 800-38A and 800-38D if you quote them.
      • CheckCWE numbers in the reveal, checked against cwe.mitre.org (CWE 5.0) on 11 November 2026: 798 Use of Hard-coded Credentials, 916 Use of Password Hash With Insufficient Computational Effort, 327 Use of a Broken or Risky Cryptographic Algorithm, 338 Use of Cryptographically Weak PRNG, 640 Weak Password Recovery Mechanism for Forgotten Password (the reset-token lifetime finding; CWE-613 Insufficient Session Expiration, used in an earlier version, is deprecated in CWE 5.0 in favour of 1463 and 1464, which are about sessions), 256 Plaintext Storage of a Password.

      // ROUND 4 · 15 MIN · A02 MISCONFIGURATION · A10 EXCEPTIONAL CONDITIONS
      Configuration and errors
      
  
      
  
      ~15 min
      • SayRound four: the settings and the error paths. Nothing here is a clever bug. It's a default somebody left on, a convenient header, or an error message that says too much. Defaults ship to everyone, so they deserve the same review as logic. The third tab is a clean change: your job is to approve it, and to avoid inventing problems.
      • ShowThe app-setup diff reflects any origin and allows credentials, runs debug on every network interface, and signs sessions with the key "dev". The login handler logs the password and sends the error message and stack trace to the caller. On the clean diff press "Looks good to me": that's the correct answer, and the decoy explanations say why each line is fine.
      • AskWhy can't you just use the * wildcard together with cookies? Browsers refuse it. Echoing back the Origin is the workaround, and it's the bug.
      • TipMDN's CORS guide: for credentialed requests the server must not specify the * wildcard but an explicit origin (the browser blocks the response otherwise), and a dynamic origin from an allow-list should come with Vary: Origin. MDN doesn't discuss reflecting the origin; that warning is general practice. Flask's debugging docs say not to run the development server or the built-in debugger in production, because the debugger allows executing arbitrary Python code from the browser (it is protected by a PIN, which should not be relied on). OWASP's 2025 list has "Mishandling of Exceptional Conditions" as A10 and "Security Logging and Alerting Failures" as A09.
      • CheckCWE numbers checked against cwe.mitre.org (CWE 5.0) on 11 November 2026: 942 Permissive Cross-domain Security Policy with Untrusted Domains, 489 Active Debug Code, 1188 Initialization of a Resource with an Insecure Default, 532 Insertion of Sensitive Information into Log File, 209 Generation of Error Message Containing Sensitive Information. The SECRET_KEY "dev" detail is Flask-specific: it signs the session cookie.

      // CHECKPOINT · 5 MIN
      Share your best review comment
      
  
      
    
      Each pair picks the one comment they're proudest of from today, or one from their own work. Read it to the room.
      
    
        
      
      1. Does your comment say where, what can go wrong and what you'd do instead?
        Hint
        Could the author act on it without asking you a follow-up question?
        Answer
        If the author would have to ask "which line?", "why does that matter?" or "what should I do?", the comment is missing a part. A good one answers all three in a few sentences and says how much it matters.
        2. 
      
      2. Is it about the code or the person?
        Hint
        Try swapping "you" for the name of the function.
        Answer
        Google's review guidance gives the example of "Why did you use threads here?" against a comment about the code's concurrency model: comment on the code, not the developer, and explain your reasoning.
        3. 
      
      3. Which of today's findings would you have to block on, and which would you leave as a note?
        Hint
        Think about who is hurt if it ships as it is.
        Answer
        Anything that lets one user reach another's data or lets outside text act as code blocks the merge. Tidy-ups, optional ideas and for-your-information notes get labels such as Nit, Optional or FYI so the author can tell the difference.
        4. 
    
      
  
      
  
      5 min
      • ShowPairs talk for 2 minutes, then share. The timer starts by itself. Collect two or three comments on the board and look at them together against the next slide's three parts.
      • CheckThe thread example and the "Nit", "Optional" and "FYI" labels are from Google's reviewer guide on writing comments (google.github.io/eng-practices). "Blocking" is a team convention, not Google's label.
      

      



      
  
      // MAKING IT STICK 01
      Write the comment, without the blame
      
  
      
    
      
      The finding: the search query from round 1
      
      
        
        
        
        
        
      
      
      
      
        
        
      
          
          
        
      
      
      
    
      
    
      
      What the author reads
      
      
      
      
      
        
    
        
  
        
  
        ~7 min
        • SayA review comment is a small message to a colleague who can't ask you what you meant. It needs three things to be actionable: where, what can go wrong, and what you'd do. Then two things that make it land: a label that says how hard you're pushing, and aim at the code. Try the person-directed version on the right: it's shorter, it's true, and it makes people defensive instead of fixing the bug.
        • ShowStart with nothing ticked: the comment is "This query needs another look." Tick where, risk and fix and add a label: the author can act without a follow-up. Add "why" and "help" for the full seven. Then switch to "About the person" and read it aloud: nobody has to be rude to be unhelpful.
        • AskWhat's the difference between a Nit and a Blocking comment for the author? One can wait, one can't. Without labels, every comment looks like a demand.
        • TipGoogle's reviewer guide on comments: be kind and courteous; comment on the code, not the developer; explain your reasoning; balance direction with discussion (point out the problem and let the developer decide, or give direct suggestions when that's more useful); call out what you like as well; label severity with "Nit:", "Optional (or Consider):" and "FYI:"; put explanations in the code, not just the review tool. "Blocking" is not in that list: it's a common team convention and an assumption of this demo. The scoring here is mine, a teaching rule of thumb, not a published measure.
        • Next"What should machines review?"
        

        


        
  
        // MAKING IT STICK 02
        Automate the easy parts
        
  
        
    
        So people can review the hard ones. For each item: who should catch it first? A machine on every push, a person in review, or both.
        
    
          
    
          
  
          
  
          ~5 min
          • SayMachines are better at the boring, repeatable and exhaustive: secret formats, known-vulnerable versions, formatting, familiar code patterns. People are better at the missing, the contextual and the social: who should own this, should we keep this data, will this comment land. If you spend review energy on what a formatter could settle, you have less for the authorization check. Use scanners to clear the ground, and treat their silence as "no known pattern", not "safe".
          • ShowChoose for each row, then read the reason. Most are clear. The SQL row is "both": static analysis catches the common shape, and a person checks the wrapper or helper the tool doesn't know.
          • AskWhich of these does your pipeline already do, and which does it only do when someone remembers?
          • TipOWASP's Secure Code Review Cheat Sheet says manual review is a human-led process that complements SAST and DAST, positions tools as aids for triage and pre-review scanning with human judgment validating findings, and lists business logic, authorization logic, race conditions, cryptographic misuse and design flaws as where manual review adds most. The right-hand column's verdicts are a simplification of that: some scanners do check some authorization patterns. Developer 11 (Security Testing in Your Workflow) goes deeper into the tools.
