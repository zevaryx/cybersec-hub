// WHY THIS TALK

APIs are where the data is

Your screens are one client of your API. Anyone with a token and a terminal can be another.

  • The API is the real boundary. Hiding things in the UI hides nothing.
  • Most API breaches are missing checks, not clever cryptography.
  • Make the checks central and default, so a new endpoint can't forget them.

Sources: T-Mobile 8-K · iTnews on ACMA's claim · Infosecurity Magazine · OWASP API Top 10

T-Mobile, 2022–23 · one APIBasic details of about 37 million accounts were pulled through a single API from around 25 November 2022. No card numbers or passwords, it said.
Optus, 2022 · a forgotten endpointAustralia's regulator alleges a weakened access control, fixed on the main site but not on an unused API subdomain. Optus disputes parts of this.
USPS, 2018 · any signed-in userAn API let anyone logged in to usps.com look up other users' account details: about 60 million users, as reported.
OWASP · number one for APIsBroken object-level authorization has led the API Top 10 in 2019 and 2023.

~3 min

  • SayThree real incidents, each with the same shape: an API that answered a request it shouldn't have, for a caller who was allowed to ask something, just not this. None needed a clever exploit. The fix in each was a check on the server.
  • TipT-Mobile: all from its SEC Form 8-K of 19 January 2023 (read on 11 November 2026): identified 5 January, activity stopped within a day, "approximately 37 million" accounts, many without the full data set, and the 8-K says no evidence of a breach of its systems; the filing doesn't say what the flaw in the API was. Optus: these are ACMA's allegations from its Federal Court statement of claim as reported by iTnews on 20 June 2024, not findings; the endpoint went offline on 21 September 2022 per iTnews, and Optus said it was a "previously unknown vulnerability" arising from "a historical coding error" and intends to defend the action. Some commentary says Optus used sequential customer IDs: that claim comes from vendor blogs, not the regulator, so don't say it as fact. USPS: Brian Krebs reported it in November 2018; I read the Infosecurity Magazine write-up, not Krebs's own page, so the count and wording are secondary. Other reports say a researcher had warned USPS a year earlier: not on the slide.

// WHO CAN DO WHAT 01

Authentication is who; authorization is what, to which

QuestionCalledFailure code
Who are you?Authentication401 Unauthorized
May you do this at all?Function-level authorization403 Forbidden
May you do it to this object?Object-level authorization403 or 404

Frameworks hand you the first one. The other two are yours, endpoint by endpoint, forever.

Sources: RFC 9110 §15.5.4 (403 may be hidden behind 404) · RFC 6750 §3.1

Quiz: which status code?

~4 min

  • SayAuthentication answers "who is this?"; authorization answers "may they?". The names of the status codes are famously confusing: 401 is called Unauthorized but means unauthenticated. 403 means "I know who you are, and no".
  • ShowLet people pick answers, then press Check. The "someone else's invoice" row accepts 403 or 404: RFC 9110 says a server that wants to hide that a forbidden resource exists may answer 404 instead. For object-level checks, 404 is usually the better choice because 403 confirms the object exists.
  • TipA 401 should say how to authenticate (a WWW-Authenticate header). For bearer tokens, RFC 6750 says the resource server uses 401 with error="invalid_token" for expired or bad tokens, and 403 with error="insufficient_scope" when the token is valid but lacks the scope. Consistency matters more than the exact choice: whatever you pick, don't let the responses for "no such invoice" and "not yours" differ.

// CHECKPOINT 1 · 5 MIN
Pause and discuss

  

    
Talk with a neighbour for a couple of minutes, then we share answers.

    
    
      
  1. Your UI never shows other users' invoice IDs. Why isn't that protection?
    Hint
    Who else can send a request to your API, and what do IDs leak through?
    Answer
    The API is the boundary, not the page: anyone with a token can call it directly with any ID. IDs also leak through logs, links, emails and screenshots. The fix is a server-side check that this caller may access this object, ideally by scoping the query to the caller.
    2. 
      
  2. A teammate says "that admin route is fine, there's no link to it". What do you say?
    Hint
    How would someone find a URL?
    Answer
    Hiding a link isn't a check: URLs are guessable, appear in client code and old docs, and get shared. Protect the route itself with a rule, and make routes with no rule closed by default.
    3. 
      
  3. Which should a missing token and a token for the wrong user each return, and why do they differ?
    Hint
    Who are you, versus what may you do?
    Answer
    No or bad credentials: 401 (authentication failed). Valid credentials but not allowed: 403, or 404 if you want to avoid confirming the object exists. They differ because they're different questions.

  • ShowTwo clients use key 1: the billing service (which you control) and an old reports cron job nobody remembers. Press "Send a request from each client": both work.     • 
  
  • SayAn API key is a long random password for a program. It's fine for server-to-server calls, but it has no user in it, it usually doesn't expire, and it is trivial to leak, so give it the smallest scope and an owner. "Last used" turns revocation from a gamble into a decision. Hashing the stored key means a database leak doesn't leak working keys; because keys are long and random, a fast hash such as SHA-256 is acceptable here, unlike for human passwords.
  • TipA recognisable prefix (for example a vendor tag) lets secret scanners and your own CI spot leaked keys; many providers do this. Pair this slide with the Git and GitHub Security talk for what to do when a key leaks: revoke first. The keys, clients and dates here are invented.

Sources: RFC 10017 (OAuth 2.0 for browser-based apps, Aug 2026) · RFC 9700 (OAuth security BCP) · RFC 6750

    

    

      Quiz: pick the best fit
      

      

        
        
        
      

      

      
    
        
  • Never put tokens in URLs: they land in logs and referrers.
    • 
        
  • For a browser app, the IETF's advice is a backend that holds the tokens and gives the page a cookie.
    • 
      

    

  

  
~4 min
  • SayThere's no single right answer, but there are wrong fits. Cookies suit your own web app on your own site: the browser stores them and you can mark them HttpOnly so scripts can't read them, at the price of needing CSRF defences. Bearer tokens suit apps and other services acting on a user's behalf: nothing is attached automatically, so there's no CSRF, but whoever holds the token can use it, and a token in script-readable storage can be stolen by any cross-site scripting bug. API keys suit your own servers.
  • ShowWork through the four scenarios. Pick the answer, press Check, and read the one-line reason for each.
  • TipRFC 10017 (OAuth 2.0 for Browser-Based Applications, BCP 212, August 2026) ranks three architectures: a backend-for-frontend (BFF) that acts as the OAuth client and keeps tokens out of the browser is the top recommendation for business and sensitive apps; a token-mediating backend is the middle option; a browser-only client holding all tokens is the least secure. RFC 9700 (OAuth 2.0 Security BCP, January 2025) says clients must not pass access tokens in URI query parameters. JWTs can't be recalled before they expire unless the API checks a denylist, so keep access tokens short-lived.
  • CheckOAuth 2.1 is still an Internet-Draft (draft-17, 31 October 2026, not yet an RFC), so don't cite it as a standard.

Validating a JWT: the signature is the first check, not the only one

    • ShowThe token is a real ES256 JWT, signed in this page with a throwaway P-256 key (the page's own signature code, the same maths as the Crypto 101 talk). Under "Full validation", the Valid token passes all seven checks. Then step through the others: each fails at exactly one check. Switch to "Decode only": everything is accepted, because decoding isn't validating. Then "Naive: trusts the header" (a library that believes the token's own alg field): alg none and the HS256-with-the-public-key token both pass, and the wrong-audience and expired tokens pass too, because it checks only the signature.
    • SayA JWT is a signed claim, nothing more. The signature says "the issuer made this", not "it's for you" or "it's still good". Your server decides the algorithm and the key, never the token: pin the algorithm, take the key from your own configuration, then check issuer, audience, expiry and the token's type. Fail closed on any doubt.
    • TipThe two classic bugs are from Tim McLean's March 2015 post: libraries that accepted alg "none" as validly signed, and libraries that, expecting an RSA signature, treated the public key as an HMAC secret when the header said HS256. RFC 8725 (JWT Best Current Practice, BCP 225, February 2020) lists the rules (verify the algorithm, validate issuer and audience, use explicit typing, don't trust received claims), and RFC 9068 (October 2021) says access-token JWTs carry typ "at+jwt" and that servers must reject alg none and any token whose aud lacks the server. Validation code has bugs too: CVE-2022-21449 ("psychic signatures") made Java 15 to 18 accept an all-zero ECDSA signature as valid for any message, until the April 2022 patch. Keep libraries updated. Don't fetch keys from a URL named inside the token (jku, x5u): that's SSRF with extra steps. The tokens and issuer here are invented, and clock times come from your own browser.

      1. What must you check when your API receives a JWT, besides the signature?
        Hint
        A valid signature says who made it. What else could be wrong with it?
        Answer
        That the algorithm is the one you expect (pinned, never taken from the token), the issuer is yours, the audience is this API, the token hasn't expired (with a small clock allowance), and its type is right. Take keys from your own configuration, not from the token.
        2. 
      
      2. A teammate stores the access token in localStorage "because it's simpler". What's the trade-off?
        Hint
        What can any script on your page read?
        Answer
        Any cross-site scripting bug (or malicious script) on the page can read it and use it elsewhere. An HttpOnly cookie, ideally behind a backend that holds the tokens, keeps it out of script reach, but then you need CSRF defences. No storage choice makes XSS harmless.
        3. 
      
      3. An app has the scope invoices:read. Can it read another customer's invoice?
        Hint
        Is a scope a kind of access, or a pass to every object?
        Answer
        No. A scope limits what the app may do for the user, and the user's own rights still apply: the object-level check runs anyway. Effective access is the intersection of scope and user permission.

      • SayMass assignment, today called broken object property level authorization (API3:2023), is the write-side twin of over-sharing: the client may set properties the user was never meant to touch.       • Ask"Why reject unknown fields instead of ignoring them?" (Checkpoint question 3.)
      • TipThe 2012 GitHub incident is the textbook case: Egor Homakov used Rails' mass assignment to submit a user_id field on the form that adds an SSH public key, pointed it at the Rails organization's account, and pushed a file to prove it; GitHub removed the key and suspended his account, later reinstated (reported by Shiflett and others; GitHub's own post wasn't read). Today's frameworks mostly default to safer behaviour, but the bug returns wherever code binds a whole request body to a model. __proto__ is a classic key in JavaScript: naive merge code can let it change prototypes, and a schema never lets it in. The records and fields are invented.

        API10 Unsafe consumption: validate what upstream services send you as strictly as what clients send you.
        
    
        
  
        
  
        ~3 min
        • SayYou met server-side request forgery in the Web Application Security talk, with a demo of why string checks lose. In APIs it appears wherever a client hands you a URL: webhooks, imports, previews, and issuer or key URLs. The server is inside your network and the client isn't, so the server must not be the client's proxy. Prefer an allow-list of hosts; otherwise parse the URL, resolve the name, reject internal ranges, connect to the address you checked, and refuse redirects. Then put the fetcher on a network that can't reach anything private.
        • TipOWASP's 2023 API list has SSRF as API7 and unsafe consumption of APIs as API10. The pseudocode isn't complete (DNS rebinding means you must connect to the checked address, not resolve again): the full demo is in the earlier talk. Capital One's 2019 incident, discussed there, is the cloud-metadata example; the hardened metadata service (AWS IMDSv2) is the cloud-side defence.

          • Clients get a stable, generic message and a correlation ID. Detail goes to the log.

          • Make "no such user" and "wrong password" look the same.
            • 
        
          • Never log tokens, keys or passwords.
            • 
        
          • Fail closed: an error in the check means no.
            • 
      
          
      
          
    
          
  
          
  
          ~4 min
          • ShowWith "Debug mode left on", run each scenario: the client sees a stack trace, file paths, the SQL text with table names, a framework version, an internal hostname, and a different message for unknown users and wrong passwords (which tells attackers which emails have accounts). Switch to the safe mode: the client gets the same fields every time (RFC 9457's type, title, status, instance) plus a correlation ID, while the server log keeps everything you need to debug, with the Authorization header redacted. Both sign-in failures now look identical.
          • SayError messages are documentation for whoever's probing you. Give clients enough to fix their own request (which field was invalid) and nothing about your internals. Give yourself everything through logs, tied together by a correlation ID the client can quote to support. And when your own check throws an error, deny: an exception in the authorization code must never fall through to "allowed".
          • TipRFC 9457 (Problem Details for HTTP APIs, July 2023, replacing RFC 7807) defines application/problem+json with type, title, status, detail and instance, and its security section warns against exposing implementation details such as stack dumps. OWASP's 2025 Top 10 added "mishandling of exceptional conditions" (A10) for exactly the fail-open and leak-the-details cases. Account enumeration also leaks through timing and the sign-up and reset flows, not only sign-in messages. Every message, path, host and ID here is invented.

          // CHECKPOINT 3 · 5 MIN
          Pause and discuss
          
  
          
    
          Talk with a neighbour for a couple of minutes, then we share answers.
          
    
            
      
          1. Why reject unknown fields instead of ignoring them?
            Hint
            What does the client believe if you answer 200? And what happens when someone adds a column next year?
            Answer
            Ignoring is safe today but silent: the client thinks the field was accepted, and bugs hide. Rejecting is loud, and a new model field can never become writable by accident, because only what the schema lists is accepted. (An allow-list that ignores extras is still far better than copying everything.)
            2. 
      
          2. One customer's script retries in a tight loop and everyone else gets 429s. What went wrong?
            Hint
            Whose bucket was it?
            Answer
            The limit was shared. Limit per key, user or tenant, so one noisy client uses up its own budget, not everyone's. Add tighter limits on costly endpoints, and return Retry-After so well-behaved clients back off.
            3. 
      
          3. A 500 response shows the SQL query and a file path. Name two problems.
            Hint
            What can an attacker learn, and what can your team still do?
            Answer
            It reveals internals (table names, versions, paths) that help attackers, and it may include user data. Return a generic problem response with a correlation ID instead, and keep the full detail in the server log, where your team can still find it.
