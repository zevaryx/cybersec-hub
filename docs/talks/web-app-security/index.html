// WHY THIS TALK

Old bug classes, real breaches

Most web breaches come from a few well-known kinds of bug. Each one has a standard defence, and your framework probably ships it already.

  • Keep data as data: never let input become code.
  • Check who's asking on every request, on the server.
  • Make the safe way the default way: framework features, CI checks, review habits.

Sources: CISA AA23-158A · SEC 2021-102 · US DOJ · The Register · CNBC

MOVEit Transfer, 2023 · injectionA SQL injection in a file-transfer product was exploited from 27 May 2023 to plant a web shell and steal data from its database.
First American, 2019 · access controlChanging digits in a document link showed other people's files: over 800 million document images, dating back to 2003.
Capital One, 2019 · server-side requestsA misconfigured web application firewall let outside commands reach a server, which handed over cloud credentials. Data on over 100 million people in the US was copied.
British Airways, 2018 · scriptsA modified script on the payment pages copied card details to the attackers. The UK regulator fined BA £20m (429,612 people affected).

~4 min

  • SayFour breaches, four of today's topics: injection, access control, server-side requests, and scripts running in your page. None needed a new technique. Each was a known bug class with a known defence that wasn't in place.
  • TipMOVEit: CVE-2023-34362, exploited by the CL0P group, per the CISA/FBI advisory. First American: reported by a journalist in May 2019; the SEC's 2021 order (a $487,616 penalty) found security staff had known of the flaw for months. Capital One: the DOJ says the attacker scanned for servers whose web application firewall misconfigurations let outside commands run, and the criminal complaint says "a firewall misconfiguration permitted commands to reach and be executed by that server", and the first command obtained credentials; many analyses describe it as a server-side request to the cloud's metadata service, which the complaint itself doesn't spell out. The OCC fined the bank $80m in 2020. British Airways: RiskIQ found a modified copy of the Modernizr library sending payment data to a look-alike domain for about two weeks (21 August to 5 September 2018); the ICO's figure is 429,612 people, and its fine was £20m in October 2020.

// DATA VS CODE 01

Injection: user data treated as code

… WHERE name = 'alice' … WHERE name = 'x' OR '1'='1'

Top: the data stays in its slot. Bottom: a quote in the data closed the slot, and the rest became code.

Every injection bug is the same bug: text from outside is glued into something an interpreter will run.

THE FIX Keep data in a separate channel: parameters, auto-escaping, argument arrays. Validating input helps, but it isn't the fix.

InterpreterSeparate channel
SQLParameterised queries, ORM query builders
HTMLTemplates that escape by default
ShellAn argument array, no shell at all
File pathsIDs mapped to paths, or resolve and check the folder
TemplatesNever build a template from user text
NoSQL, LDAPThe driver's query objects, not strings

See OWASP Injection Prevention and OS Command Injection Defence

~4 min

  • SaySQL, HTML, a shell command, a file path, a template: each is a little language, and each has a way to pass data without it ever being read as code. If you remember one sentence from part 1, make it this: don't glue strings together for an interpreter.
  • TipInput validation is still worth doing, as an allow-list of what a field should look like (a number, a date, one of five values). But it can't be the fix: names contain apostrophes, comments contain angle brackets, and the right escaping depends on where the data ends up, which the validator doesn't know.

    // DATA VS CODE 04
    Content Security Policy: the safety net
    
  
    
    
    
      
    
        
        
        
        
      
    
      
    
      
    
    
    
    
    
      
      
        
    • Prefer a nonce-based policy with 'strict-dynamic', object-src 'none' and base-uri 'none'.
      • 
        
    • Host allow-lists are easy to get around: most of the policies one large study examined could be bypassed.
      • 
        
    • Roll out with Content-Security-Policy-Report-Only first, then enforce.
      • 
        
    • It's a safety net. Encoding is still the fix: CSP doesn't stop injected HTML that needs no script.
      • 
      
    
      
    Sources: web.dev: Strict CSP · Weichselbaum et al., CCS 2016 · CSP Level 3
    
      
    
    
    
  
    
  
    ~7 min
    • ShowStep through the four policies and watch the table. No policy: everything runs. 'unsafe-inline' undoes most of the benefit. A host allow-list stops inline script, but not a script from an allowed host that can be made to run attacker code (a JSONP endpoint, an old library on a CDN). The strict nonce policy stops all the script attacks; the fake form still gets through.
    • SayCSP tells the browser which scripts it may run. With a nonce, only script tags carrying this response's random value run; injected markup can't know the value. 'strict-dynamic' lets your trusted scripts load their own dependencies, so you don't maintain host lists. base-uri 'none' matters with nonces: an injected base tag could otherwise point your trusted relative script URLs at another server.
    • TipThe 2016 Google study (Weichselbaum, Spagnuolo, Lekies, Janc) found 94.72% of distinct policies could be bypassed, and 14 of the 15 most commonly allow-listed script hosts had unsafe endpoints. CSP Level 3 is still a W3C Working Draft but its core directives are supported across major browsers. frame-ancestors (clickjacking) comes back in part 3.

    // WHO'S ALLOWED 03
    Sessions and cookies: set the flags
    
  
    
    
    
      
    
        
        
        
      
    
      
    
        
        
        
      
    
      
    
      
      
      
      
    
      
    
      
      
        
        
      • HttpOnly: scripts (including injected ones) can't read it.
        • 
        
      • Secure: never sent over plain HTTP.
        • 
        
      • SameSite=Lax or Strict: not sent on most cross-site requests.
        • 
        
      • The __Host- prefix makes the browser enforce Secure, no Domain and Path=/.
        • 
        
      • Issue a new session ID at sign-in; expire sessions on the server, idle and absolute; sign-out ends the server session.
        • 
        
      • Keep session tokens out of localStorage: any script in the page can read it.
        • 
      
      
      
      Sources: MDN Set-Cookie · OWASP Session Management
      
    
      
  
      
  
      ~6 min
      • ShowStart with the bare cookie: every line of the list is a warning. Tick HttpOnly and Secure, set SameSite to Lax, and watch them clear. Then rename it __Host-session: try adding Domain and watch the browser reject it. SameSite=None without Secure is rejected too.
      • SayThe session cookie is the user, as far as your server is concerned. Three flags and a prefix shut most of the ways it leaks: read by injected script, sent over plain HTTP, sent along with requests another site started, or shared with a subdomain you forgot about. Sign-in is better with passkeys or a second factor, but whatever the method, it ends in one of these cookies.
      • TipMDN: setting Domain "makes the cookie available to that domain and all its subdomains"; leaving it out makes a host-only cookie, which is stricter. HttpOnly cookies are still sent with fetch() from the page, so it limits theft, not misuse by injected script: XSS is still game over for that session while it runs.

      // WHO'S ALLOWED 04
      CSRF, and how SameSite changed it
      
  
      
    
      
      
      You're signed in to bank.example. Another page tries to make your browser send POST /transfer.
      
      
      
        
        
      
      
      
      
        
        
        
      
      
      
        
    
        
    
        
      
        
      
          
        
        • Use your framework's CSRF protection for anything that changes state.
          • 
        
        • GET never changes state.
          • 
        
        • Set SameSite yourself: only Chromium browsers default to Lax.
          • 
        
        • "Same-site" means the same registrable domain: sibling subdomains count as same-site.
          • 
        
        • Fetch Metadata (Sec-Fetch-Site) or an Origin check is a cheap extra layer.
          • 
      
        
      
        Sources: Chromium SameSite updates · Mozilla bug 1617609 · web.dev Fetch Metadata · OWASP CSRF
        
    
        
  
        
  
        ~6 min
        • ShowStart with the default: a self-submitting form on evil.example, cookie without SameSite, in Chrome. The cookie isn't sent, so it fails. Switch to "in Firefox": it's sent and the transfer goes through. Switch to a sibling subdomain with Lax or Strict: still same-site, so the cookie goes. Then tick the CSRF token: blocked in every case. The Sec-Fetch-Site check blocks it too.
        • SayCSRF is the browser helpfully attaching your cookie to a request someone else's page started. SameSite cookies cut it down a lot, which is why it fell down the rankings. But the default only applies in some browsers, Lax still allows top-level GET navigations, and a subdomain you don't fully control counts as the same site. Keep the token or an origin check.
        • TipChrome began treating unmarked cookies as Lax in 2020 (Chrome 80 onward, rolled out gradually), with a two-minute exception for top-level POSTs right after a cookie is set. Mozilla closed its Lax-by-default bug as WONTFIX; a 2025 comment says Firefox uses None when no SameSite is set and has no plans to change. Safari's behaviour isn't covered by a primary source here: test it rather than assume. Sec-Fetch-Site is sent by Chrome, Edge, Firefox and Safari 16.4+; accept requests that lack it.

        // WHO'S ALLOWED 05
        Server-side request forgery: when your server fetches URLs
        
  
        
    
        
      
        "Paste an image URL and we'll fetch it for your profile." The server fetches from inside your network.
        
      
        
        
      
        
      
        
        
        
        
        
        
        
        
        
        
      
        
      
        
        
        Naive: block "localhost" and "169.254.169.254"
          
        
          Robust: parse, resolve, check the IP, pin it
            
      
            
      
            
    
            
    
            
      
              
        
            • Best: an allow-list of hosts you expect.
              • 
        
            • Otherwise: allow only http(s); resolve the name; block loopback, private, link-local and metadata ranges; connect to the IP you checked.
              • 
        
            • Don't follow redirects, or check every hop.
              • 
        
            • Fetch from a network that can't reach internal services.
              • 
        
            • In the cloud, require the hardened metadata service (AWS: IMDSv2).
              • 
      
            
      
            Sources: OWASP SSRF Prevention · AWS: IMDSv2 · OCC 2020-101
            
    
            
  
            
  
            ~7 min
            • Showcat.png passes both checkers. The metadata address is the one cloud servers use to get their own credentials: both catch the obvious spelling. Then LOCALHOST in capitals, the decimal 2130706433 and the user@host trick: the naive string check misses them all, because URL parsers turn them into 127.0.0.1 and 10.0.0.5. The internal name, the redirect and DNS rebinding look fine as text; only resolving, checking the IP, connecting to that IP and refusing redirects catches them.
            • SaySSRF turns your server into the attacker's proxy, with your server's network position and permissions. Block-lists of strings always lose to the many ways of writing an address. Decide on the IP, after parsing and resolving, or better, only talk to hosts you expected.
            • TipOWASP's 2025 list folds SSRF into Broken Access Control (A01). AWS introduced IMDSv2 in November 2019: a session token fetched with a PUT, which most SSRF bugs, open firewalls and reverse proxies can't send. 169.254.169.254 is the metadata address on AWS, Azure and Google Cloud. All hosts and addresses in the demo are made up or documentation ranges; nothing is fetched.

            1. A user changes /invoices/1041 to /invoices/1042 and sees someone else's invoice. What's the fix?
              Hint
              Where should the rule live, and what should the query include?
              Answer
              Check on the server, for every request, that this user may access this object: fetch it scoped to the user (owner_id = current user) and return 404 otherwise. Hiding links or using random IDs doesn't fix it. Add a test that user A can't read user B's invoice.

              Hint
              Think about GET handlers, sibling subdomains and other browsers.
              Answer
              Yes, keep it. Lax still sends cookies on top-level GET navigations (so state-changing GETs are exposed), sibling subdomains count as same-site, and defaults differ between browsers. A framework token or a Sec-Fetch-Site/Origin check is cheap.

              Hint
              What can your server reach that the user can't?
              Answer
              Any two of: http(s) only; resolve the host and block private, loopback, link-local and metadata addresses; connect to the IP you checked; don't follow redirects (or re-check each); fetch from an isolated network; require IMDSv2 in the cloud.

                // MAKING IT ROUTINE 04
                Tools in the pipeline, and their limits
                
  
                
    
                
      
                Which tool is most likely to catch each bug?
                
      
                
      
                
        
        
        
      
                
      
                
    
                
    
                
      
                
        
                Secret scanning
                Known key formats in commits and pushes. Cheap, fast, few false alarms.
                
        
                Dependency scanning (SCA)
                Your lock file against advisory databases.
                
        
                SAST
                Reads your code for risky patterns. Sees every path, guesses at intent, raises false alarms.
                
        
                DAST
                Pokes a running app from outside. Finds real behaviour, only on the pages it reaches.
                
        
                Review and tests
                The only one that knows who should see what.
                
      
                
    
                
  
                
  
                ~6 min
                • ShowLet the room call out an answer for each row, set the dropdowns, then check. Some rows accept two answers.
                • SayTools are great at patterns and terrible at intent. A scanner can see you built SQL from a string; it can't know that Bob shouldn't see Alice's invoice. So put the cheap, quiet tools (secret scanning, dependency checks) where they block a merge, run the noisier ones where someone triages them, and keep access control in tests and review. A clean scan means "nothing these tools know how to find".

                // CHECKPOINT 3 · 5 MIN
                Pause and discuss
                
  
                
    
                Talk with a neighbour for a couple of minutes, then we share answers.
                
    
                  
      
                1. Why isn't a Content Security Policy enough on its own?
                  Hint
                  What does it control, and what does injected HTML do without script?
                  Answer
                  It's a safety net that limits which scripts run. It doesn't fix the injection: fake forms and other script-free HTML still work, allow-list policies are often bypassable, and one 'unsafe-inline' undoes most of it. Output encoding is the fix; CSP limits the damage when one slips.
                  2. 
      
                2. Your front-end bundle contains an API key. When is that fine?
                  Hint
                  What does the provider call the key?
                  Answer
                  Only when the provider designs it to be public (a publishable key, or a browser key restricted to your site). Secret keys, passwords and private keys belong on the server; if one shipped, revoke and replace it.
                  3. 
      
                3. Every scanner in your pipeline is green. Are you secure?
                  Hint
                  What can't a tool know about your app?
                  Answer
                  Not necessarily. Tools find patterns and known issues; they miss logic bugs, especially access control. Keep review and tests for "who may do what", and treat green as "nothing these tools know how to find".
