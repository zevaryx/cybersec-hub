// HOW FUZZERS THINK 01

The inputs you'd never think to test

Write the tests you can imagine. A fuzzer writes the ones you can't.

  • Where it started: in the late 1980s a stormy-night dial-up session scrambled a researcher's commands with line noise, and the noise crashed programs. The 1990 paper that came from it fed random characters to almost 90 Unix utilities and crashed more than 24% of them.
  • What it finds: the bugs hiding in the places your tests never go. Parsers, decoders, protocol handlers, anything that reads bytes it doesn't control.
  • What it costs: a small harness, some CPU time, and the habit of looking at what it finds.
Fuzzing, in one sentenceRun your code over and over on machine-made inputs, keep the ones that reach new code, and watch for crashes, hangs and sanitizer reports.
The goal hereFinding and fixing bugs in your own code before release. A crash becomes: reproduce it, shrink it, fix it, keep the input as a regression test.
It doesn't replace the restUnit tests say what should work. A fuzzer asks what happens on everything else. See Security Testing in Your Workflow for where each tool fits.

~2 min

  • SayThe idea is old. In the late 1980s a researcher was logged in over a dial-up line during a rainstorm; the line noise scrambled what he typed, and it crashed programs. That made the team ask what would happen if they fed random characters to the standard Unix utilities on purpose. In their 1990 paper, testing almost 90 utilities on seven versions of Unix, they crashed more than 24%. Modern fuzzers are far cleverer, but the question is the same: what happens on input nobody planned for?
  • CheckThe storm story, "almost 90 utilities", "seven versions of UNIX" and "more than 24%" are from the paper itself (Miller, Fredriksen and So, CACM December 1990; read in the Wisconsin technical-report copy, and the three figures re-checked against the published text on 11 November 2026). That copy is dated 1989 and its summary says 25 to 33%; the published CACM version (December 1990) says "more than 24%". I use the 24% from the introduction. I didn't read the published version itself.

// HOW FUZZERS THINK 02

Random, mutation, coverage: why guessing fails

  1. Random input. New text every time. Fast, and hopeless past the first check.
  2. Mutation. Edit an input that already works. Better, but it never learns where to aim.
  3. Coverage guidance. Keep any input that reaches new code and mutate that. It climbs the format one check at a time.

Random guessing

–tries, on average–

Coverage-guided

–tries, roughly–

A toy model: 95 printable characters, inputs about 10 long. Random must hit every check at once; guided finds each check on its own, because a correct guess reaches new code and gets kept. REC2:FUZZ is nine checks.

~3 min

  • SayOur toy parser wants a record that starts REC2: and then a field starting FUZZ. That's nine characters that must all be right. A random guesser needs all nine at once: about 95 to the ninth power tries, which is hundreds of quadrillions. A coverage-guided fuzzer gets a signal after each correct step: when it finds R, the code takes a new branch, so that input is kept and mutated further. Slide the number up: random grows by a factor of 95 per check; guided grows in a straight line.
  • ShowDrag the slider. At nine checks the random column is about 10 to the 17th tries; guided is a few thousand. Push it to 12 and watch the random time pass the age of the universe.
  • Ask(Checkpoint question, preview) Why does coverage guidance find deep bugs that random input never reaches? Answer: coverage feedback turns one impossible guess into a chain of small, feasible ones.
  • CheckThis is my own simplified model, not a measurement: it ignores length, assumes each check takes about 95 guesses at a known position, and real fuzzers differ a lot. The time column uses the speed you pick. The "age of the universe" line uses 13.8 billion years.

        // CHECKPOINT 1 · 5 MIN
        Pause and discuss
        
  
        
    
        Talk with a neighbour for a couple of minutes, then we share answers.
        
    
          
      
        1. Why does coverage guidance find deep bugs that random input never reaches?
          Hint
          What does the fuzzer learn when an input reaches new code?
          Answer
          Random input has to get every check right at once, and the odds multiply with each one. Coverage feedback turns that into a sequence: an input that passes the first check reaches new code, so it's kept and mutated, and the next check only has to be guessed on top of it. One impossible guess becomes a chain of small ones.
          2. 
      
        2. What makes a good fuzz target in your codebase?
          Hint
          Think about where untrusted bytes enter, and what a harness needs to be fast.
          Answer
          A function that takes bytes (or something you can build from bytes) from outside your trust boundary: a parser, decoder, deserialiser or protocol handler. It should be fast, deterministic, and free of network, disk and global state. If it isn't, fuzz the part of it that parses, with the rest stubbed.
          3. 
      
        3. Why do fuzzers usually run together with a sanitizer?
          Hint
          What does a silent memory error look like from outside?
          Answer
          A fuzzer only notices what looks like a failure: a crash, hang or timeout. Many memory bugs corrupt memory and carry on. A sanitizer turns the first bad access into a loud failure with a report, so the fuzzer can save the input and you can see what went wrong.

              • CheckGo's engine minimises a failing input and writes it to testdata/fuzz (go.dev); libFuzzer writes crash-<sha1> files (LLVM) and its -minimize_crash option shrinks them (I ran it). Whether to dedupe by stack, by function or by sanitizer report depends on your tooling: the toy's grouping is deliberately simple.

              // RUNNING IT FOR REAL 03
              Tools and programmes you can use today
              
  
              
    
              
      
              libFuzzer · AFL++ · HonggfuzzThe main engines. libFuzzer ships with clang. AFL++ is a community fork that gathers improvements to AFL, which hasn't been updated since 2017.
              
      
              Go, Rust, PythonNative Go fuzzing since Go 1.18. cargo-fuzz for Rust (libFuzzer, nightly compiler). Atheris for Python (libFuzzer-based). Hypothesis for property tests.
              
      
              OSS-FuzzGoogle's free continuous fuzzing for open-source projects. Its README says it had found over 13,000 vulnerabilities and 50,000 bugs across about 1,000 projects as of May 2025.
              
      
              CIFuzzA GitHub Action that runs OSS-Fuzz projects' fuzz targets on pull requests. Default 10 minutes.
              
      
              ClusterFuzzLiteFuzzing in your own CI: pull-request fuzzing, longer batch runs, crash downloads and coverage reports. GitHub Actions, GitLab, Cloud Build, Prow. C, C++, Java, Go, Python, Rust, Swift.
              
      
              Where to beginOne parser. One harness. Run it over lunch with a sanitizer. Add it to CI when it's quiet.
              
    
              
  
              
  
              ~4 min
              • SayYou don't build any of this yourself. Engines: libFuzzer, AFL++, Honggfuzz. Language-native: Go has it in the standard toolchain; Rust and Python use libFuzzer underneath. If your project is open source, OSS-Fuzz will run your fuzzers for free once they're integrated. For private code, ClusterFuzzLite gives you a pull-request mode and a batch mode on your own CI. Start with one target.
              • CheckRead on 11 November 2026: OSS-Fuzz README (engines libFuzzer, AFL++, Honggfuzz; the 13,000 and 50,000 figures are "as of May 2025" and the README may have updated since; languages it lists include Java/JVM and JavaScript); ClusterFuzzLite's home page (modes, CI systems, languages); the CIFuzz page; aflplus.plus (AFL++ is a fork of AFL, AFL last updated in November 2017 on that page); go.dev (Go 1.18); the rust-fuzz book (nightly); Atheris's README (based on libFuzzer). Hypothesis's home page. Not read: Honggfuzz's own page, and any commercial service's pricing or availability, which the deck doesn't mention. Google's OSS-Fuzz-Gen, which asked language models to write harnesses, shows as archived and no longer maintained on its repository page; the deck doesn't rely on it.

              // RUNNING IT FOR REAL 04
              Measuring progress: coverage over time
              
  
              
    
              
      
      
                
      
                
    
                
    
                
      
                What to watchCoverage rising means the fuzzer is learning. A plateau means it's stuck, or done.
                
      
                When it goes flatIs the harness reaching the code at all? Add seeds and a dictionary. Check for a checksum or length field it can't guess. Try a structure-aware mutator. Look at the coverage report for code that never ran.
                
      
                Coverage isn't correctnessHigh coverage means the code ran, not that bugs were found. It's a progress signal, not a finish line.
                
      
                
    
                
  
                
  
                ~4 min
                • SayFour runs of 20,000 tries on the toy parser, drawn on one chart: random text, mutation only, coverage-guided with coverage feedback alone, and coverage-guided with comparison tracing. Random is the flat line: it barely gets off the floor. Mutation climbs a little and stops. Guided keeps climbing, and the comparison-tracing run gets there first. In real life you'd watch the same curve per target: if it goes flat, ask why before assuming you're finished.
                • ShowPress Draw the curves, then Another run: the shapes stay, the details change.
                • Ask(Checkpoint question 3) A target's coverage has been flat for a week. What do you check? Answer: whether the harness reaches the code, whether seeds or a dictionary are missing, whether something blocks progress (a checksum, a length), and whether the code that never ran needs a different harness.
                • CheckThe toy curves are drawn from real runs of this page's own fuzzer on its own invented parser. Real tools (libFuzzer's cov: and ft: counts, coverage reports in ClusterFuzzLite) measure real code. libFuzzer's log fields are from its docs.

                // CHECKPOINT 2 · 5 MIN
                Pause and discuss
                
  
                
    
                Talk with a neighbour for a couple of minutes, then we share answers.
                
    
                  
      
                1. What would you run on every pull request, and what overnight?
                  Hint
                  Think about how long each takes, and what each can find.
                  Answer
                  On every pull request: replay the saved corpus (and past crash files) so nothing regresses, then fuzz the changed targets for a few minutes. Overnight or continuously: longer runs that grow the corpus and reach the deep bugs short runs miss.
                  2. 
      
                2. A crash file arrives. What happens to it, step by step?
                  Hint
                  Four verbs.
                  Answer
                  Reproduce it, shrink it, fix the cause, keep the shrunken input as a regression test that runs in every build. Group duplicates first so you fix one bug once.
                  3. 
      
                3. Coverage on one target has been flat for a week. What do you check?
                  Hint
                  Is the fuzzer stuck, or is the harness the problem?
                  Answer
                  Whether the harness actually reaches the code you care about, whether seeds or a dictionary would help, whether a checksum or length field is blocking it, whether a structure-aware approach fits, and what the coverage report says never ran.
                  4.
