// WHY THIS TALK

The code you didn't write, and the machine that ships it

98%of audited commercial codebases contained open-source components (Black Duck, 2026).
1,180open-source components in the average application in that report.
500+npm packages hit by the self-spreading Shai-Hulud worm in September 2025 (CISA).
  • Every dependency is a stranger's code running with your permissions, and every update is a new delivery from them.
  • The build pipeline is the one place that can write to production, so it's the place worth attacking.
  • The goal isn't "trust nothing". It's fewer, pinned, reviewed, verified, with small blast radius when one fails.

Sources: Black Duck OSSRA 2026 · CISA on npm · CISA on tj-actions · TanStack postmortem

tj-actions/changed-files, March 2025 · a build step that leaked secretsCISA: a popular GitHub Action was modified between 12 and 15 March, and secrets from workflow runs, such as access keys and tokens, could be exposed (CVE-2025-30066). Fixed in 46.0.1.
Shai-Hulud, September 2025 · a worm made of maintainersMalware stole developers' credentials, then used them to log in to npm as those developers and publish tainted versions of their other packages. CISA counted over 500.
TanStack, May 2026 · the pipeline was the way inOn 11 May, 84 malicious versions of 42 packages were published in six minutes. TanStack's postmortem traces it to a pull-request workflow running fork code, a poisoned build cache, and a publishing token taken from the runner's memory.

      // YOUR DEPENDENCY TREE 02

      Known vulnerabilities: find, triage, fix

      Finding them

      • Let the platform watch. GitHub's Dependabot alerts, GitLab and others compare your lock files with advisory databases. OSV-Scanner and npm audit or pip-audit do it on demand.
      • Check pull requests before merge: GitHub's dependency review shows which vulnerabilities a change would add.
      • Let a bot open the updates, so fixes arrive as small pull requests, not a yearly project.

      Triage in four questions

      1. Is the vulnerable code actually used by us, and is it reachable?
      2. Is it known to be exploited? (CISA's KEV catalogue; the EPSS score)
      3. Is there a fixed version, and what does the update break?
      4. If we can't fix today: what do we do instead? (Override, disable the feature, add a filter, tell people.)
      A useful defaultSecurity updates should go through your normal fast lane and be exempt from any waiting period. Routine version bumps can wait a few days. Dependabot's cooldown, for example, applies to version updates and not to security updates.
      The dependency you can't updateSometimes the fix needs a major upgrade, or the project is abandoned. Write down the decision and a date to revisit: an exception with no expiry is a permanent hole.
      Updates are a habit, not a projectSmall, frequent, reviewed updates are easier to read and roll back than a year's worth at once.

      # a vulnerability in a package you don't use is noise. A vulnerability in one you can't see is the problem.

      ~3 min

      • SayFinding known vulnerabilities is the solved part: databases and tools exist, and most are free. The hard part is deciding and then doing. Four questions get you through most alerts. Link this to the vulnerability management talk for ranking by exploitation and exposure.
      • TipDependabot's reference says the cooldown option "is only available for version updates, not security updates", and that its default cooldown doesn't apply to security updates. The reference also lists a default of 3 days when default-days is left out; check it before you describe a default. Renovate has an equivalent minimumReleaseAge option (not read in detail). Tools to name: Dependabot, Renovate, OSV-Scanner, pip-audit, npm audit, GitHub dependency review.
      • CheckThis slide is practices and tool names, not statistics. The 3-day Dependabot default ("If not specified, Dependabot applies a default cooldown of 3 days") and the pnpm default of 1440 minutes were confirmed against the current docs on 11 November 2026.

      // YOUR DEPENDENCY TREE 03

      Packages that are bad on purpose: six ways in

      1 · Look-alike namesA package whose name is one slip away from a popular one, waiting for a typo or a copied command. Defence: copy names from the project's own page; use a lock file.
      2 · Dependency confusionA public package with the same name as your private one, and a higher version number. In 2021 Alex Birsan reached more than 35 companies this way, with permission. Defence: scoped names, one trusted registry, locked hashes.
      3 · Hijacked accountsA maintainer's credentials are stolen and a bad version is published under their name, as Shai-Hulud did at scale in 2025. Defence: wait a few days, use provenance, ask maintainers for phishing-resistant MFA.
      4 · Install-time scriptsCode that runs the moment a package is installed, before you've imported anything. npm 12 (July 2026) turned dependency install scripts off by default. Defence: allow-list the few that need one.
      5 · The build is the way inThe release pipeline is tricked into publishing, as in the TanStack case. Defence: harden the pipeline (part 3), and scope publishing trust to one workflow and branch.
      6 · A patient insiderA new maintainer earns trust over time, then adds something hidden, as with xz Utils in 2024. Defence: no single control; diversity, review and monitoring, and humility.

      # different doors, same idea: you ran something nobody on your team read.

      ~5 min

      • SayWalk the six quickly; each has a one-line defence and the rest of the talk fills them in. Be clear that these are not rare: registries remove malicious packages every day. Two of the six (5 and 6) are not about the package you installed at all.
      • TipDependency confusion: Alex Birsan's February 2021 research reached the internal builds of more than 35 companies by publishing public packages with the names of internal ones and higher version numbers, with permission through bug bounty programs and agreements; coverage reported bounties above $130,000. npm 12: GitHub's July 2026 changelog says allowScripts defaults to off, so preinstall, install and postinstall scripts and implicit node-gyp builds don't run for dependencies unless allowed, and git and remote-URL dependencies are off by default too (--allow-git and --allow-remote default to none); you prepare with npm approve-scripts --allow-scripts-pending. pnpm gates dependency build scripts in its own way (unlisted packages are unreviewed and, by default, installation fails). xz Utils: Andres Freund's 29 March 2024 post on oss-security (CVE-2024-3094, versions 5.6.0 and 5.6.1), where part of the backdoor existed only in release tarballs and not in the git source.
      • CheckBirsan's own write-up returned a 403 here, so the 35-company and $130,000 figures rest on secondary coverage of it. The npm 12 details were confirmed on 11 November 2026 against GitHub's 8 July 2026 changelog and the npm v12 config reference (allow-git and allow-remote "none" as of npm 12; allow-scripts empty by default). The phrase "a patient insider" describes xz Utils as widely reported; the maintainer's identity and motives were never established in the sources I read, so don't speculate.

      // CHECKPOINT 1 · 4 MIN

      Pause and discuss

      Talk with a neighbour for a couple of minutes, then we share answers.

      1. A popular package's maintainer account is hijacked and a bad version is published at 09:00. How could that reach your production app by tonight?

        Hint

        Which of your tools install the newest version that matches a range, and which one merges updates automatically?

        Answer

        Any build without a lock file, or with a bot that merges new versions straight away, pulls it in on its next run, and the image or artifact keeps it after the package is removed. A lock file, a waiting period for routine updates, reviewing update pull requests, and turning off dependency install scripts each cut a link in that chain.

      2. Your internal package is called acme-billing. What could go wrong if the public registry has one by the same name?

        Hint

        What does your package manager do when two registries both have the name?

        Answer

        If the tool searches both and picks the highest version, an outsider's version 99.0.0 wins. Use a scope you own, route internal names to your registry only, and install from a lock file with hashes.

      3. The scanner reports a High vulnerability in a package three levels down. Name two ways to deal with it that don't involve waiting for the maintainer.

        Hint

        You can change what version everything uses, or change how it's used.

        Answer

        Force a fixed version with an override or resolution (and test it), update the direct dependency that brings it in, replace the package, or disable or filter the vulnerable feature. Record the decision with an expiry.

      4 min

      • ShowPairs talk for 2 minutes, then share. The timer starts by itself.

      // KEEPING IT UNDER CONTROL 01

      Lock files, and the value of waiting a few days

      Your manifest says date-fmt ^1.2.0. Day 12: a bad 1.3.1 is published. Day 14: the registry removes it. Move the day:

      What the lock file checks 
      
      
      
      
        
        
      • Commit the lock file and install from it in CI (npm ci, uv sync --locked).
        • 
        
      • It doesn't decide what's good: it makes builds repeatable and changes visible.
        • 
        
      • A short wait on routine updates skips the days a bad release is freshest.
        • 
      
      
      
      
    
      
  
      
  
      ~5 min
      • ShowEach row is a different way of installing, over 21 days; red cells are days when it would hand you the bad version. Start at day 12. "No lock file" takes whatever is newest, so for two days it's bad, and anything built on those days keeps it after the registry removes it. "Lock file" never moves. "Update bot (no waiting)" updates to 1.3.1 on day 12 and stays on it until the fix on day 16. "Update bot with a 3-day wait" only proposes versions that are three days old and still there, so it never saw 1.3.1. Then press the integrity button: the lock file records a hash of the file, and a changed byte is refused. (The demo uses SHA-256; npm records SHA-512 and the idea is the same.)
      • SayTwo separate protections. Locking makes builds reproducible and changes visible. Waiting gives the community and the registry time to find and pull a bad release; in this toy the registry takes two days, which is optimistic for some cases and pessimistic for others. It isn't a guarantee, and it should never delay a security fix.
      • AskIf a lock file is committed but your CI runs npm install instead of npm ci, what do you actually have? Answer: a lock file that can be rewritten during the build; use the command that installs exactly what's locked and fails if it disagrees with the manifest.
      • TipRelease-age settings that exist today, from their docs: npm min-release-age (a number of days; the CLI docs for v11 list it with a default of none), pnpm minimumReleaseAge (minutes; the docs list a default of 1440, one day, with minimumReleaseAgeExclude for exceptions), and Dependabot's cooldown. Socket's February 2026 write-up also lists Yarn (npmMinimalAgeGate) and Bun (minimumReleaseAge). The registry timeline in the demo is invented.
      • CheckDefaults and names change often; check the current docs for the tool your audience uses. The pnpm default of 1440 comes from the current docs page, which I could read; I did not confirm which version introduced it. Whether npm's min-release-age applies the same way to security fixes is not something I verified.

            // THE PIPELINE 03
            A tag can move. A commit hash can't.
            
  
            
    
            
      Your workflow says…
      
            
        
        
        
      
            
      The action's repository (someone else's)
      
            
      
            
        
        
        
      
            
    
            
    
            
      
            Tonight's build runs:
            
      
            
      
            
      
              
        
            • Pin third-party actions to a full commit hash, with a comment for the version.
              • 
        
            • Let a bot update the pin in a pull request you can read.
              • 
        
            • You can require pinning in the repository or organisation policy.
              • 
      
            
      
            
    
            
  
            
  
            ~4 min
            • ShowWith the tag selected, press "Maintainer ships a fix": the tag moves to a newer commit and your build runs it, which is the convenient, intended behaviour. Reset, then press "Someone with push access repoints the tag": same mechanism, but now the build runs a commit that sends the environment to a made-up address. The tag moved and nobody was asked. Switch the workflow to the full hash and repeat: the build still runs the commit you reviewed, and the update arrives as a pull request. @main is the same problem, faster.
            • SayA version tag is a label that whoever controls the repository can move. A full 40-character commit hash names exact content, and changing it is not feasible. That's why GitHub's secure-use reference says pinning to a full-length commit SHA is the way to use an action as an immutable release (and mentions that an attacker would need a SHA-1 collision to get around it). The price is that you now own updating: let Dependabot or Renovate propose the new hash and read it.
            • AskIf your pipeline uses a third-party action by tag, who decides when your build changes?
            • TipSince 15 August 2025 an organisation or repository admin can require actions to be pinned to a full-length commit SHA in the Actions policy, and a workflow that uses an unpinned action fails; the same policy supports blocking specific actions with a ! prefix (GitHub changelog). The tj-actions case (CISA: affected versions 12 to 15 March 2025): workflows that referenced the action by version picked up malicious code. Short hashes are rejected by the policy (per a third-party test); use all 40 characters. Pins don't cover what an action itself downloads, so also prefer actions you can read and that are small.
            • CheckThe commits and their hashes in the demo are generated here. I didn't confirm, from StepSecurity or GitHub, the exact mechanism by which tj-actions' version tags were changed, so the slide only says what CISA says. Per third-party tests, a reusable workflow may be called by tag but the actions inside it still need a full SHA; local actions and docker:// steps are out of scope.

            // THE PIPELINE 04
            Short-lived credentials instead of stored keys
            
  
            
    
            
      
            
        
            A stored keyCreated once, copied into CI settings, valid until someone remembers to rotate it. Any step that can read it can take it.
            
        
            An identity tokenThe job proves who it is, the cloud checks the claims against a trust policy, and issues a credential that lasts about an hour.
            
      
            
      
            # a deploy job asks for an identity, only here
deploy:
  permissions:
    id-token: write
    contents: read
  environment: production
            
      
              
        
            • Give only the deploy job the right to request an identity.
              • 
        
            • The trust policy is the lock. Name the repository and the branch, tag or environment, not just the organisation.
              • 
      
            
    
            
    
            
      
            When the trust is narrow, but the run isn't cleanIn the TanStack case the binding was already scoped to one repository, one workflow file and one branch. The malware ran inside a genuine release run on main (via a poisoned cache), so it could mint a valid publishing token anyway. Narrow trust limits what a stolen run can do; it doesn't make the run itself safe.
            
      
            Publishing packages the same waynpm's trusted publishing (OIDC) replaces long-lived publish tokens, and it generates provenance for you. npm is also retiring 2FA-bypass tokens: early August 2026 for sensitive account actions, around January 2027 for direct publishing.
            
      
            # fewer secrets to steal beats better places to keep them. The token demo is in the secrets management talk.
            
    
            
  
            
  
            ~2 min
            • SayThis is a short slide on purpose: the full mechanism, with a signed token and a trust policy you can break, is in the secrets management talk's short-lived credentials demo. Here the point is where to apply it in a pipeline: cloud deploys, registry publishing, and anything else that currently reads a long-lived key from CI settings. Two sharp edges: a trust policy that names only the repository trusts every workflow in it; and even a narrow one trusts every step of that workflow's run, as TanStack found.
            • TipGitHub's secure-use reference: OIDC lets workflows authenticate to cloud providers so you can stop storing credentials as long-lived secrets, and recommends short-lived, well-scoped tokens; the cloud checks conditions you set on the token's claims. TanStack's own postmortem: the publishes were "authenticated via OIDC trusted-publisher binding for TanStack/router release.yml@refs/heads/main"; both malicious publishes came from runs of release.yml on main (a re-run, then a push), where malware restored from the poisoned Actions cache minted a token via id-token: write and POSTed to the registry directly; lesson learned: "once configured, any code path in the workflow can mint a publish-capable token". Endor Labs' write-up says the trust was granted at repository level rather than a branch and workflow file, which contradicts the postmortem, so the slide follows the postmortem. npm's July 2026 changelog: 2FA-bypass granular tokens stop skipping 2FA for sensitive account actions in early August 2026, and lose direct publishing around January 2027; move automated publishing to trusted publishing or to staged publishing with human approval. Also from October 2026, npm expires unvalidated trusted-publishing configurations 48 hours after creation (GitHub changelog "Unvalidated npm trusted publishing configurations now expire", 2 October 2026; the 48-hour figure is from secondary coverage, as the changelog body didn't load).
            • CheckThe 48-hour expiry figure is from secondary coverage of the changelog, so it is only in these notes. Dates for the 2FA-bypass change are approximate in GitHub's own wording ("early August", "around January").

            // THE PIPELINE 05
            Untrusted text in a pipeline step
            
  
            
    
            
      
            A workflow greets each new issue. Anyone can open an issue, so the title is untrusted.
            
      
            
        
        
      
            
      
            
      
            
        
      
            
      
            
        
        
        
      
            
    
            
    
            
      The script the runner builds
      
            
      Commands the shell would start (nothing here is run)
      
              
      
              
      
              
    
              
  
              
  
              ~4 min
              • ShowWith "Pasted into the script", a normal title starts one command. Press the second sample (a quote, a semicolon, an echo): the quote closes the greeting early, and the shell sees a second command that the workflow's author never wrote. The third sample shows a command substitution doing the same. Switch to "Passed as an environment variable" with the same titles: still one command, because the text is data in a variable and never becomes part of the script. Nothing here runs anything; the page only splits text into commands to show what a shell would do.
              • SayThis is injection again, in a new place: template expressions are replaced with their values before the shell ever sees the script. A harmless echo in the demo could be anything in real life, running with the job's token and secrets. The fix is the same as for SQL: keep data out of code. The same applies to branch names, commit messages, pull request titles and bodies, and anything from a fork.
              • AskWhere else does text from outside your team end up in something that gets executed?
              • TipGitHub's secure-use reference gives the intermediate-environment-variable approach as the preferred way to handle untrusted input in inline scripts (its example uses a pull request title), and also suggests a JavaScript action that receives the context value as an argument. The same page says to avoid pull_request_target unless it's needed, to use workflow_run for privilege separation, and not to explicitly check out untrusted fork code in those workflows. Since 18 June 2026, actions/checkout v7 refuses by default to check out fork pull request code in pull_request_target workflows (opt-out input: allow-unsafe-pr-checkout); backports to older supported major versions (not v1) were enforced from 20 July 2026, but SHA or patch pins don't get it automatically. GitHub's 2 November 2026 changelog says that from 2 December 2026 pull_request_target is blocked by default for public repositories on Free, Team and Enterprise Cloud unless an Actions event policy allows it (brownouts: 9 and 16 November, 16:00 to 18:00 UTC; private and internal repositories aren't affected). Scorecard's Dangerous-Workflow check looks for these patterns.
              • CheckThe December date and brownouts are from GitHub's own changelog but are moving: earlier coverage said 2 November before it was moved, and a later search summary mentioned the same dates. Re-read before you present. The checkout v7 changelog does not block shell steps that fetch fork code with git or gh, or other events such as issue_comment, so the protection isn't complete.

              // CHECKPOINT 2 · 5 MIN
              Pause and discuss
              
  
              
    
              Talk with a neighbour for a couple of minutes, then we share answers.
              
    
                
      
              1. Why pin a third-party CI action to a commit hash instead of a version tag?
                Hint
                Who can move a tag, and what happens to your next build when they do?
                Answer
                A tag is a movable label controlled by the action's owner (or anyone who takes over that account), so your next build silently runs whatever it points to. A full commit hash names exact content. Let a bot propose updates so you read each change.
                2. 
      
              2. A workflow runs tests on pull requests from forks and also has the cloud deploy key in a repository secret. What would you change first?
                Hint
                Think about which job needs the secret, and who can trigger the workflow.
                Answer
                Move the deploy credential out of reach: use an environment with required reviewers (or short-lived identity for the deploy job only), set the default token to read-only, and make sure fork-triggered workflows never run with secrets or check out untrusted code in a privileged workflow.
                3. 
      
              3. A workflow step contains echo "${{ github.event.pull_request.title }}". What's wrong, and what's the fix?
                Hint
                When is the expression replaced, and by what?
                Answer
                The title is pasted into the script text before the shell runs it, so a crafted title can add commands. Pass it through an environment variable and read it as "$TITLE", so it stays data.

              // PROVING WHAT YOU BUILT 01
              Signing a release, and a log that remembers
              
  
              
    
              
      The release
      
              
      
              
        
        
        
        
      
              
      The toy transparency log (a hash chain; real logs use Merkle trees)
      
              
    
              
    
              
      What a consumer checks before trusting it
      
                
      
                
      
                  
        
                • A signature proves this signer approved these exact bytes.
                  • 
        
                • It does not prove the code is safe, or that the signer is who you think, unless you check the identity.
                  • 
        
                • With keyless signing the identity is a workflow or a person, and the log lets owners notice misuse.
                  • 
      
                
      
                
    
                
  
                
  
                ~4 min
                • ShowThe release is a small text file signed with this page's own ECDSA P-256, and logged in a toy append-only chain. "Untouched" passes all three checks. "One byte changed" fails the hash check: the file is no longer what was signed. "Signed by a different key" fails the signature check: the right file, but not signed by the signer we expect. "Never logged" fails the log check: a signature nobody can see isn't something the owner could ever notice being misused.
                • SaySigstore is the common way to do this without managing keys: cosign signs with a short-lived certificate tied to an identity, Fulcio is the certificate authority that issues it after checking an OIDC identity, and Rekor is a public append-only log of what was signed. Verification checks the signature, that the identity is the one you expect, the certificate chain, and proof the entry is in the log. The consumer's job is the second one: you must decide whose identity you expect.
                • AskWhat does a signature on a release prove, and what doesn't it prove? Answer: it ties exact bytes to a signer's identity; it doesn't say the code is good, or that the signer's account wasn't taken over.
                • TipFrom Sigstore's overview: signatures use ephemeral keys, so there's no long-lived key to manage; the log stores the artifact's digest, signature and certificate; verification performs four checks (signature, expected identity, certificate against the root of trust, inclusion in Rekor). npm packages can carry provenance: publish with --provenance from a supported cloud CI with id-token: write (or with trusted publishing, which does it automatically) and verify installed packages with npm audit signatures. npm's docs say provenance "does not guarantee the package has no malicious code".
                • CheckThe log in the demo is a hash chain, not Rekor's real structure, and the keys are made up for the demo and generated in the page. I summarised Sigstore's overview page and npm's provenance docs; I didn't check other ecosystems' signing (for example PyPI's attestations).

                // PROVING WHAT YOU BUILT 02
                Provenance and SLSA: where did this come from?
                
  
                
    
                
      
                
      The signed statement from the build
      
                
      
                
    
                
    
                
      Our deploy policy checks
      
                  
      
                  
      
                  
      
                  SLSA build levelWhat it adds
                  
        
                  L1Provenance exists
                  
        
                  L2Hosted platform signs it
                  
        
                  L3Hardened, isolated builds
                  
      
                  
      
                  
    
                  
  
                  
  
                  ~4 min
                  • ShowProvenance is a signed statement from the build system: which file, which builder, which repository, which ref. Pick scenarios and watch the policy checks. "A normal release" passes. A swapped file fails on the hash; an edited statement fails on the signature; one signed with another key fails because we don't trust that signer; a build in someone else's repository, or from a pull request branch, passes the signature but fails our policy. The last scenario passes everything: a malicious change that was merged and then built correctly.
                  • SayProvenance answers "how and where was this built", which lets you reject anything built somewhere else. It doesn't answer "is the code any good". Reported analyses of the May 2026 TanStack compromise found the malicious packages carried valid SLSA Build Level 3 provenance (StepSecurity, as reported), because they really were published by the project's own pipeline. That is not a failure of provenance; it's what it does and doesn't promise.
                  • AskWhat does your policy verify when you deploy: a signature, a hash, a source, or nothing?
                  • TipSLSA's Build track (spec v1.2, build-track-basics): L0 no guarantees; L1 provenance exists; L2 a hosted platform generates and signs it, and consumers validate it; L3 a hardened platform keeps runs from influencing each other and keeps signing secrets away from user-defined build steps. GitHub's artifact attestations: "Artifact attestations alone provide SLSA v1.0 Build Level 2"; Level 3 needs a reusable workflow; and "Generating attestations alone doesn't provide any security benefit": consumers verify them (gh attestation verify). Attestations "are not a guarantee that an artifact is secure".
                  • CheckEndor Labs' write-up confirms the malicious versions carried valid SLSA provenance attestations from the legitimate tanstack/router repository; the "Build Level 3" wording is from The Hacker News' report of StepSecurity, and counts differ between vendors (84 versions of 42 packages in the first wave; 160+ across the wider campaign). The level summaries match SLSA v1.2's build-track-basics page (read 11 November 2026). The scenarios, repository names and build output in the demo are invented.

                    3.

                    Hint

                    Answer
                    Controls before the build: reviewed changes, protected branches, a pipeline that can't be tricked into running untrusted code, narrowly scoped publishing trust. After the release: a waiting period before consumers adopt it, scanning and monitoring, and an SBOM to find out quickly who has it.

                    Hint

                    Answer

                  // PROVING WHAT YOU BUILT 04
                  Everyday habits, beyond the incidents
                  
  
                  
    
                  
      
                  For your dependencies
                  
      
                    
        
                  • Add fewer dependencies. Before you add one, ask what it costs to keep.
                    • 
        
                  • Commit the lock file and install from it in CI.
                    • 
        
                  • Wait a few days on routine updates, never on security fixes.
                    • 
        
                  • Read the update's shape: new scripts, new publishers, new dependencies.
                    • 
        
                  • Copy install commands from the project's own page.
                    • 
        
                  • Own your names, and route internal names to your own registry.
                    • 
      
                  
    
                  
    
                  
      
                  For your pipeline
                  
      
                    
        
                  • Default tokens read-only; grant more to the one job that needs it.
                    • 
        
                  • Pin third-party steps by hash, and let a bot propose updates.
                    • 
        
                  • Use short-lived identities instead of stored keys, scoped to repo and branch.
                    • 
        
                  • Treat input as data, never as script.
                    • 
        
                  • Review workflow-file changes like production code.
                    • 
        
                  • Keep an SBOM and verify what you deploy.
                    • 
      
                  
      
                  
    
                  
  
                  
  
                  ~3 min
                  • SayNone of these is dramatic, which is why they work. They are the same habits that would have blunted most of the incidents in the intro, and they hold up for incidents nobody has had yet.
