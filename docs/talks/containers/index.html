// WHY THIS TALK

Containers are convenient, and defaults are generous

10,456public Docker Hub images pushed in November 2025 contained at least one exposed secret (Flare).
42%of those images held five or more sensitive values each.
3runc container-escape bugs disclosed on 5 November 2025.
  • A container shares the host's kernel. Its walls are settings, and the defaults favour convenience.
  • Most real problems are ordinary: a secret in a layer, a root user, a privileged flag, a flat network. They are all ours to fix.
  • So the plan is simple: smaller images, fewer rights, and a smaller blast radius when something goes wrong.

Sources: Flare, Docker Hub secrets research · Sysdig on the runc bugs · Kubernetes network policies · Kubernetes Secrets

// BUILDING IMAGES 01

What a container is, and what it shares

A container is a normal process with a restricted view of the machine. For each item, is it its own or shared with the host?

    • Containers are processes plus limits: namespaces change what a process can see, cgroups limit what it can use, capabilities and seccomp limit what it can ask the kernel to do.
    • A virtual machine has its own kernel. A container doesn't, so the kernel and the runtime are part of your attack surface.
    • That's why the rest of the talk is about giving the process less: fewer files, fewer rights, fewer paths out.
    "Isolated" is a description, not a guaranteeDocker's own security page says containers are quite secure by default, especially when processes run as non-privileged users. The words "especially when" are doing a lot of work.

    ~4 min

    • ShowLet people answer before you click: for each row pick Own or Shared, and the answer appears. Two surprises usually land: CPU and memory are shared unless you set limits, and root inside a container is UID 0 on the host too.
    • SayA container is not a small VM. Think of it as a process wearing blinkers. The blinkers (namespaces) change what it sees; the leash (cgroups) limits what it uses; the rulebook (capabilities, seccomp) limits what it can ask the kernel to do. All of it is configuration, which means all of it can be loosened by accident.
    • TipDocker's engine security docs: user namespaces (which can map the container's root to a non-root host user) are supported but not enabled by default; root inside a container has far fewer privileges than host root, because Docker starts containers with a restricted capability list. Kubernetes and containerd follow similar defaults but differ in detail.
    • CheckWhether user namespaces are available and enabled on your own platform. Managed Kubernetes services differ.

    // BUILDING IMAGES 02

    Start small: pick the smallest base that works

    What is inside the floor your app stands on?

    • Everything in the image is something to patch and, if someone gets in, something they can use.
    • Small bases cut both. Their cost is debugging comfort: use a debug tag or an ephemeral debug container instead of putting a shell in production.
    • Prefer maintained minimal images over hand-made ones, and check how often they are rebuilt.

    Sizes are from the distroless README's own comparison; yours will differ with the exact tag.

    ~4 min

    • ShowClick through the four. Debian has everything, which is the comfort and the cost. Alpine is tiny and has a shell and a package manager. Distroless static has no shell and no package manager: that's the point. scratch is literally empty.
    • SayPeople pick a big base so that debugging is easy and the build "just works". Then production inherits every tool an intruder might want. Go for the smallest thing your program can actually run on, and build the habit of debugging from outside the container.
    • AskWhen did your team last remove something from a base image rather than add something?
    • TipDistroless README: images contain only an application and its runtime dependencies, with no package managers or shells; the smallest, static, is around 2 MiB, against about 5 MiB for alpine and 124 MiB for debian; tags include nonroot and debug (adds a busybox shell); all images are signed with cosign keyless. Alpine uses musl instead of glibc; a few programs behave differently. Docker's best-practice guide: choose a minimal base image that matches your requirements.
    • CheckThe table is a simplified comparison, and the contents of each image vary by tag: check the exact tag you use. Chainguard, Docker and others also publish hardened minimal catalogues: look at them, and at how fast they patch, rather than picking by logo.

    // BUILDING IMAGES 03

    A tag is a label. A digest is a fingerprint.

    Your Dockerfile says FROM registry.example.com/shop/api:1.4. The publisher fixes something and pushes again under the same tag.

    BY TAG · shop/api:1.4 today resolves to
    BY DIGEST · your pinned line resolves to

    • A tag is a pointer the publisher can move. The same Dockerfile can build different images on different days.
    • A digest is the SHA-256 of the image manifest: change a byte and it changes. Pinning it gives repeatable builds, and defeats a swap at the registry.
    • The catch: a pinned digest never updates itself. Pair it with a bot (Dependabot, Renovate) that opens a pull request, so the update is reviewed and rebuilt, not silent.
    FROM registry.example.com/shop/api:1.4@sha256:3f9a…

    Keep the tag for humans and the digest for the machine.

    ~4 min

    • ShowPush the tag once: the "by tag" box changes and the pinned one doesn't. The digests are real SHA-256 values computed in your browser from a made-up manifest. Then let the bot move the pin: the update arrives on purpose.
    • SayPinning trades silent updates for repeatability. That is a good trade only if something is watching for updates, because an image pinned in 2024 and never touched is a collection of unpatched bugs with a certificate of authenticity.
    • AskWho would notice if your base image changed overnight? Who would notice if it never changed for a year?
    • TipDocker's build best practices: to fully secure your supply chain integrity, pin the image version to a specific digest; the trade-off is that you opt out of automatic security fixes, so use something like Dependabot to update pinned digests. The manifest in the demo is invented; real manifests list layer digests and config.
    • CheckWhich update bots handle digest pins for the Dockerfiles you use. Both Dependabot and Renovate advertise Docker support; confirm digest handling and the pull-request cadence in your set-up.

            Answer

                • SayThe Pod Security Standards are three ready-made policies: privileged (anything goes), baseline (blocks the known dangerous things) and restricted (current hardening best practice). A namespace label turns one on: pod-security.kubernetes.io/enforce: restricted. Use warn and audit first to see what would break. Four lines in a container's securityContext get you most of the way: non-root, no privilege escalation, drop all capabilities and the runtime's default seccomp profile.
                • TipKubernetes's Pod Security Standards page: baseline disallows privileged containers, host namespaces, hostPath volumes, host ports, capabilities outside an allowlist and an Unconfined seccomp profile (plus AppArmor, SELinux and /proc rules); restricted adds: volumes limited to configMap, csi, downwardAPI, emptyDir, ephemeral, persistentVolumeClaim, projected and secret; allowPrivilegeEscalation: false; runAsNonRoot: true and no runAsUser: 0; seccomp RuntimeDefault or Localhost; and drop ALL capabilities, adding back only NET_BIND_SERVICE. Pod Security Admission is stable since 1.25, configured with namespace labels pod-security.kubernetes.io/<mode>: <level>, with modes enforce, audit and warn; for Deployments and Jobs only audit and warn apply, and enforce applies to the resulting Pods. It replaced PodSecurityPolicy, removed in 1.25. A pod with no seccomp profile runs Unconfined unless the kubelet is set to default to RuntimeDefault (--seccomp-default, stable since 1.27 but still a per-node setting).

                Limits: the leaky pod and its neighbours
                
  
                
    
                
      
                A node has 8 GiB. Four pods use 5 GiB. A fifth, a worker with a memory leak, grows by half a GiB every step. Set its memory limit and run it.
                
      
                
        
        
        
        
      
                
      
      
                cyan = four healthy pods · pink = the worker · red = over capacity · 8 GiB node
                
    
                
    
                
      
                
      
                
      
                  
        
                • Requests are what the scheduler reserves; limits are the ceiling. A memory limit means an out-of-memory kill, a CPU limit means throttling.
                  • 
        
                • Set both. Without limits, one mistake becomes everyone's outage.
                  • 
      
                
      
                
    
                
  
                
  
                ~3 min
                • ShowRun with no limit: the node runs out of memory and the message says a neighbour may be the victim. Then 1 GiB: only the leaky worker is killed.                 • SayThis is a security topic because availability is part of security, and because a compromised pod mining coins looks exactly like a leaky one. Limits turn "the node falls over" into "one pod restarts and an alert fires".
                • TipKubernetes docs (managing resources for containers): the kube-scheduler uses requests to place a Pod; a CPU limit is a hard limit the kernel enforces by throttling; a memory limit is enforced reactively: the container may be terminated when the kernel detects memory pressure; if you set a limit but no request, the limit is copied as the request. Notice that no single setting is enough: the picture changes only when you do all three.
                  • SayYou can't prevent every compromise. You can decide what a compromise is worth. This is the "defence in depth" slide: each setting assumes the previous one failed. Practical order: restricted settings in the namespace, a default-deny network policy per namespace (then allow exactly what's needed, including DNS), and a dedicated service account with only the permissions the pod needs, with the token not mounted if it doesn't call the API.
                  • AskIf your web pod was compromised today, which of the seven targets would be open? How would you find out without running an attack?
                  • TipKubernetes docs: with no NetworkPolicy, pods are non-isolated and all traffic is allowed in both directions; a NetworkPolicy has no effect unless the cluster's network plugin enforces it (the API server accepts the object either way, so test enforcement); policies are additive. A pod with no service account specified gets the default account in its namespace, and its token is mounted automatically unless automountServiceAccountToken: false is set on the account or the pod (the pod's setting wins). Cloud metadata endpoints and their protections vary by provider; where a provider lets you limit pod access to node credentials, do so.
                  • CheckThis is a model of reachability, not a scan: real results depend on your network plugin, your roles and your cloud. The statement about the default account having next to no rights holds for a clean cluster; verify yours for stray role bindings. Bound, time-limited service-account tokens are the modern default (I did not re-read the version details), and the demo doesn't depend on them.
                  • Next"One more thing people think is protected: Kubernetes Secrets."

                    • ShowType any value: base64 is just a different alphabet, and the second line decodes it instantly (it is not a cipher). Then change the three settings and watch the list of who can read it. Turning on encryption at rest only closes the first row. The rows that remain are about who has API rights, and who can create a pod.
                    • SayKubernetes's own documentation is blunt: Secrets are stored unencrypted in etcd by default; anyone with API access can retrieve or modify a Secret, so can anyone with access to etcd, and anyone authorised to create a Pod in a namespace can read any Secret in that namespace, including indirectly through a Deployment. The four steps it recommends: enable encryption at rest, least-privilege RBAC, restrict Secret access to specific containers, and consider external secret stores. Then link back to the secrets-management talk: the best secret is the one a workload never stores; short-lived credentials come from an identity, not a file.
                    • AskWho on your team can create a pod in the production namespace? Does that match who you would trust with every secret in it?
                    • TipQuotes and the four steps are from the Kubernetes Secrets concept page. The reader list is a model: exactly which rows apply depends on your cluster. An external secret store (for example one synced by an operator or mounted with a CSI driver) moves the master copy and the audit trail, but the value still reaches the pod, and in some set-ups it is turned back into a Kubernetes Secret.
                    • CheckWhether encryption at rest on your cluster uses a KMS provider or only a local key, and whether your managed service enables it by default.

                        // CHECKPOINT 2 · 5 MIN
                        Pause and discuss
                        
  
                        
    
                        Talk with a neighbour for a couple of minutes, then we share answers.
                        
    
                          
      
                        1. A scan of your image reports 300 findings. Where do you start?
                          Hint
                          Where is the package, can it be fixed, and how severe is it?
                          Answer
                          Narrow to what ships in the final image, has a fix, and is high or critical. Rebuild on a fresh base first, since that clears many at once. Then deal with what's left by reachability, and set up a regular rebuild so the pile doesn't regrow.
                          2. 
      
                        2. A Kubernetes Secret's value is base64. Is it encrypted? Who can read it?
                          Hint
                          Think: etcd, the API, and who can create pods.
                          Answer
                          No. Base64 is an encoding anyone can reverse. By default it's stored unencrypted in etcd; anyone with API access to Secrets can read it, and so can anyone allowed to create a pod in the namespace. Encrypt at rest, use least-privilege RBAC, limit pod creation, and prefer short-lived credentials from an identity.
                          3. 
      
                        3. A pod is compromised. Name three settings that decide how far the attacker gets.
                          Hint
                          The pod, the network and the account.
                          Answer
                          Its security context (non-root, no privilege escalation, dropped capabilities, no host access), network policies (default deny), and its service account (minimal rights, and no token if it doesn't need one). Resource limits and patched nodes and runtimes also matter.
