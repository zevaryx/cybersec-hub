Cloud Security Fundamentals

Cloud breaches are rarely clever. They're public buckets, over-powered keys and missing logs. Who secures what, and the handful of settings that matter most.

// WHY THIS TALK

Cloud breaches are rarely clever

None of these needed a cloud provider to be hacked. Each needed one setting, one credential, or one missing copy.

  • The provider runs the building, the hardware and the services. How you configure them is yours.
  • Clouds make it easy to change things fast. That includes making things public, and deleting them.
  • The good news: the fixes are mostly settings you can turn on this week.
Snowflake customers, 2024Logins stolen by infostealer malware, some dating to 2020, still worked: the accounts had no MFA. Mandiant found no breach of Snowflake itself; about 165 organisations were notified.
Capital One, 2019A misconfigured firewall let an attacker fetch the server's own cloud credentials, which could read storage. About 100 million people in the US and 6 million in Canada were affected.
Code Spaces, 2014An attacker in the AWS console deleted servers, data and backups, which lived in the same account. The company shut down.

Sources: Mandiant · Capital One · Network World

~3 min

  • SayThree different failures: a login without MFA, a server whose credentials could be fetched by an outsider, and backups an attacker could reach with the same access. We'll fix each of them today.
  • TipCapital One: the metadata service detail is part 3. Code Spaces: separate accounts are next.
  • Next"First question: whose job is what?"

// WHO SECURES WHAT 01

Shared responsibility, as a stack

You Shared: the provider builds it, you configure it Provider

  • The provider secures the cloud itself: buildings, hardware, the hypervisor, the services.
  • You secure what you put in it, and the settings. The more managed the service, the less you patch.
  • Two rows never move: your data and who can get to it. They're yours even in SaaS.
  • Providers fail too. Microsoft lost a signing key in 2023; a US review board called it a "cascade of security failures". That's why you still log and limit.

Source: CSRB review of the 2023 Exchange Online intrusion

~6 min

  • ShowClick through the four models. On your own servers, everything is yours. Each step to the right hands more rows to the provider, but data and access never move.
  • SaySnowflake was SaaS. The provider ran everything below the login. The customers owned the login, and that's where it failed.
  • Ask"Which of your services are which?" Most organisations have all four.
  • Next"The next boundary is one you draw yourself: accounts."

// WHO SECURES WHAT 02

Accounts are walls. Use more of them

Organisationguardrails apply to everything below
Securityaudit logs, read-only for everyone else
Productioncustomer data, few people, no experiments
Staginglooks like prod, holds no real data
Developmenttry things here
Backupscopies production can write but not delete

AWS accounts in an Organization · Azure subscriptions under management groups · Google Cloud projects in folders under an organization.

  • An account (or subscription, or project) is the strongest wall a cloud gives you. A leaked key in Development can't touch Production.
  • Backups belong somewhere else. Code Spaces' backups died with the same login that ran production.
  • Logs belong somewhere else too, so an intruder can't erase their tracks.
  • Organisation-wide guardrails (AWS service control policies, Azure Policy, Google organization policies) say what nobody below may do, admins included.

~5 min

  • SayOne account for everything means one mistake reaches everything. Separate accounts cost almost nothing and turn "we lost everything" into "we lost dev".
  • TipGuardrails come back in the policy simulator: the organisation's "deny" beats even an admin's "allow".
  • Next"Checkpoint."

// CHECKPOINT 1 · 5 MIN

Pause and discuss

Talk with a neighbour for a couple of minutes, then we share answers.

  1. In a managed database service, who patches the database engine, and who controls who can connect?

    Hint

    Which rows of the stack moved to the provider?

    Answer

    The provider patches the engine and the operating system under it. You decide who can connect: network rules, database users and their permissions.

  2. Why keep backups in a separate account from production?

    Hint

    What can a stolen production admin login reach?

    Answer

    So one stolen login, or one mistake, can't delete both. Production can write backups but not delete them; nobody's everyday account can.

  3. Snowflake wasn't hacked, but its customers were. Whose job was the fix?

    Hint

    Which rows stay yours, even in SaaS?

    Answer

    The customers': accounts and access are always yours. Requiring MFA and rotating old logins would have stopped it. (Providers can help with safer defaults: Snowflake made MFA the default for new accounts from October 2024.)

// IDENTITY IS THE PERIMETER 01

Users, roles and policies

// a policy: who may do what, to which thing, when
{
  "Effect":    "Allow",
  "Action":    ["s3:GetObject"],
  "Resource":  "arn:aws:s3:::acme-reports/*",
  "Condition": { "aws:SecureTransport": "true" }
}
A userA person or program with its own long-term login. For people, prefer SSO into roles.
A roleA set of permissions anyone allowed can step into, for a short time. No password, no permanent key.
  • Least privilege: the actions this job needs, on the resources it needs, nothing else.
  • "Action": "*" and "Resource": "*" are smells. Every one should have a reason written next to it.
  • Don't write policies from scratch: start from what the job actually used. AWS IAM Access Analyzer can generate a policy from the activity log; Google's IAM recommender flags unused permissions.
  • Give permissions to groups and roles, not to individuals, so changes happen in one place.

Same idea everywhere: AWS IAM policies, Azure role assignments (RBAC), Google Cloud IAM bindings.

~5 min

  • SayRead the policy aloud: allow, get objects, from this bucket, only over HTTPS. Every cloud permission is some version of this sentence.
  • TipThe recommenders are the easiest win in the talk: they show which granted permissions haven't been used in 90 days.
  • Next"When several policies apply, which one wins? Let's try it."

// IDENTITY IS THE PERIMETER 02

Policy simulator: explicit deny wins

    ~7 min

    • Showdev-role reading prod-bucket: allowed by ProdRead. Untick HTTPS: the bucket's own policy denies it, and deny beats allow. Switch to old-admin key and DeleteBucket on prod-bucket: "*" allows it, the organisation's guardrail denies it. Then the intern on iam:CreateUser.
    • SayThree rules: anything not allowed is denied; an allow in the identity's or the resource's policy can grant it; an explicit deny anywhere ends the discussion. This is AWS's order; Azure and Google work the same way for deny assignments and deny policies.
    • Tipci-deploy has ec2:* on everything. Ask: does a deploy job need to terminate servers?

    // IDENTITY IS THE PERIMETER 03

    Roles, not keys

    Long-lived access keyWorks until someone deletes it, from anywhere in the worldLives in config files, laptops, CI settings and chat logsOften older than the person who made it remembersUsually attached to more than it needs
    Short-lived role credentialsExpire on their own, usually within an hourIssued on demand to something that proved who it isNothing to store, so nothing to leak from storageEach session is logged with who assumed the role

    Who gets them, and how

    • People: sign in through SSO and step into a role (AWS IAM Identity Center, Microsoft Entra ID, Google Workspace or Cloud Identity).
    • Servers and functions: instance roles, managed identities, attached service accounts. The platform hands out credentials; your code never sees a key file.
    • CI/CD: OpenID Connect federation. GitHub Actions, GitLab and others prove which repository and branch is running, and get credentials for that job only.
    • Other clouds and on-premises: workload identity federation instead of exported keys.

    Google now blocks new service account keys by default in organizations created since 3 May 2024, and automatically disables keys it finds exposed in public places. Source

    ~6 min

    • SayA key is a password that never expires and often has admin rights. A role is a visitor's badge that stops working at the end of the day.
    • Ask"How many access keys does your account have, and how old is the oldest?" Most consoles can answer that in one screen.
    • Next"Let's leak one of each and compare."

    // IDENTITY IS THE PERIMETER 04

    Blast radius: leak a key, leak a role

    ~5 min

    • ShowFifteen minutes in, both are dangerous: but look at what each can reach. Then drag the slider past an hour: the role's credentials expire on their own; the key just keeps going. Drag to the end.
    • SayTwo things shrink the damage: scope (what it can touch) and lifetime (how long it works). Roles win on both.
    • Next"Humans still log in, though. Protect those logins hardest."

    // IDENTITY IS THE PERIMETER 05

    MFA for humans, root first

    • The root or owner account can do anything, including closing the account. Give it a phishing-resistant MFA (a security key or passkey), no access keys, and use it almost never.
    • Everyone else: SSO with MFA, then roles. No shared admin logins.
    • Break-glass: one or two emergency accounts, kept offline, alarmed when used, tested twice a year.
    • Automation shouldn't use human accounts at all. Use workload identities: they're built for it.

    SEE ALSO Identity and Access Management for MFA strength, push fatigue and break-glass in detail.

    The providers now insist

    AWSMFA required for root users: management accounts from May 2024, standalone accounts from June 2024, and all account types by June 2025. Member accounts can have no root password at all, with centralized root access.
    Microsoft AzureMFA required to sign in to the Azure portal from October 2024, and for create, update and delete through the CLI, PowerShell, SDKs and IaC tools from 1 October 2025 (tenants could postpone to 1 July 2026). Managed identities and service principals aren't affected.

    Sources: AWS · Microsoft Learn

    ~5 min

    • SayWhen the providers start forcing a setting on everyone, that's a sign of how often its absence went wrong. Turn it on before they make you.
    • TipA script that breaks because of Azure's MFA requirement was running as a person. Move it to a managed identity or service principal: that's the real fix, not an exemption.
    • Next"Checkpoint."

    // CHECKPOINT 2 · 5 MIN

    Pause and discuss

    Talk with a neighbour for a couple of minutes, then we share answers.

    1. Why are short-lived role credentials safer than an access key stored in a config file?

      Hint

      Think scope and lifetime.

      Answer

      They expire on their own, so a leak has a deadline; there's nothing stored to leak in the first place; and each session is tied to who assumed the role in the logs.

    2. One policy allows an action and another explicitly denies it. What happens, and why is that useful?

      Hint

      Who usually writes the deny?

      Answer

      It's denied. That lets a central team set guardrails (like "nobody deletes production buckets") that no team's allow can override, however broad.

    3. Your nightly script stopped working when MFA became mandatory. What's the right fix?

      Hint

      Who was the script pretending to be?

      Answer

      Stop running it as a person. Give it a workload identity (managed identity, service principal or role) with only the permissions it needs.

    5 min

    • ShowPairs talk for 2 minutes, then share. The timer starts by itself.

    // MISCONFIGURATIONS 01

    Public storage: block it for the whole account

    • "Public" should be a decision someone made on purpose, for a website or a download, not a side effect.
    • Turn on block public access at the account level, so one bucket's policy can't undo it. Put real public files behind a CDN instead.
    • Since April 2023, new S3 buckets block public access and disable ACLs by default. Older buckets didn't change. Check them.
    • Google enforces uniform bucket-level access in organizations created since May 2024; Azure has a per-account "allow blob anonymous access" switch. Turn it off.

    Sources: AWS · Google Cloud

    ~5 min

    • ShowSet the bucket policy to "Anyone can read" with the block on: still private. Untick the block: the whole bucket is open. Tick the ACL instead: one file leaks. Turn the block back on: both closed.
    • SayDefaults protect new things. Your oldest buckets are the ones to check, because they were made before the defaults changed.
    • Next"Storage isn't the only thing you can open to the world. Ports too."

    // MISCONFIGURATIONS 02

    Open ports: who can reach what

    PortForAllowed from

    • Scanners sweep the whole internet all day. masscan's authors say it can cover every IPv4 address in under five minutes, so "nobody knows the address" isn't protection.
    • Only the front door should face the internet: usually 443, through a load balancer.
    • Admin access (SSH, RDP) through the provider's session tools (AWS Systems Manager, Azure Bastion, Google IAP) or a VPN, not an open port.
    • Databases: private subnets, reachable only from the app's security group.

    Source: masscan README

    ~5 min

    • ShowStart with everything open to 0.0.0.0/0. Change SSH to "nobody" (we use session tools) and the database to "web servers only". The exposure count drops to one: the front door.
    • SayAllow rules that point at another security group, not at IP ranges, follow your servers as they come and go.
    • Next"Encryption: usually one setting. The interesting question is who holds the key."

    // MISCONFIGURATIONS 03

    Encryption is one setting. Keys are the decision

    At rest

    • Since January 2023, S3 encrypts every new object by default with AES-256. Disks, databases and snapshots usually need one setting, often an account-wide default.
    • Turn on encryption by default for disks in every region, so nobody has to remember.

    In transit

    • TLS everywhere, including inside your network. Refuse plain HTTP in the policy itself (the aws:SecureTransport condition from the simulator).

    Source: AWS S3 default encryption FAQ

    Who holds the key?

    Provider-managed keysOn by default, nothing to manage. Protects against a stolen disk, not against someone with your permissions.
    Customer-managed keys in a key serviceAWS KMS, Azure Key Vault, Google Cloud KMS. You choose who may use the key, and every use is logged.
    Your own hardware or external keysFor strict regulation. More control, more ways to lose your own data.

    Encryption at rest doesn't stop a user who's allowed to read. It moves the question back to identity: who can use the key? Crypto 101 explains the AES underneath.

    ~4 min

    • SayEncryption at rest is table stakes and mostly automatic now. What it buys you depends on who can use the key: with a customer-managed key, revoking key access cuts off the data even if a bucket policy is wrong.
    • Next"Now the one that caught Capital One: the metadata service."

    // MISCONFIGURATIONS 04

    The metadata service, and fetching URLs for users

    Our app has a "link preview" feature: give it a URL, and the server fetches it.

    
    
    
    
    
      
      
        
    • Every cloud server can ask 169.254.169.254 about itself, including for its role's credentials.
      • 
        
    • If your server fetches URLs for users, a user can point it there. That's server-side request forgery (SSRF), and it's how Capital One's credentials were taken.
      • 
        
    • IMDSv2 needs a token from a PUT request first. A simple fetch can't get one. Since March 2024 you can make it the default for every new instance in an account; Amazon Linux 2023 turns off v1 itself.
      • 
        
    • Also: validate and allow-list the destinations your fetcher may reach, and keep the role small.
      • 
      
    
      
    Sources: AWS · EC2 docs · Krebs on Capital One
    
    
    
  
    
  
    ~6 min
    • ShowPreview example.com: fine. Click the metadata preset: the server fetches its own role name, then the credentials. Tick IMDSv2: the same request gets 401. Untick it and tick "refuse private addresses" instead: blocked earlier. Use both.
    • SayAzure and Google have metadata services too, and both require a special header, which helps against the simplest version of this. The habit is the same: never let users choose where your server connects without a list.
    • Next"How do you catch all this before it ships? Check the code that builds it."

        1. Why block public access at the account level, instead of checking each bucket?
          Hint
          Who makes the next bucket, and when?
          Answer
          Because it covers buckets that don't exist yet and settings someone changes by mistake. Exceptions become deliberate, reviewed decisions.
          2. 
      
        2. Why does requiring IMDSv2 stop the link-preview attack?
          Hint
          What does the attacker control in the request?
          Answer
          The attacker only controls the URL of a GET request. IMDSv2 wants a token from a PUT request with a special header first, which a simple fetch can't make.
          3. 
      
        3. Your policy checker passes. Is the infrastructure secure?
          Hint
          What can't a list of known mistakes see?
          Answer
          Not necessarily. It catches known-bad settings; it can't tell whether a role is too broad for this job, or whether data should exist at all. That's what review is for.

        The billing alert: an intrusion detector you already pay for

        // GUARDRAILS 03
        Habits that keep a cloud tidy
        
  
        
    
        
      
        Everything has an ownerTag every resource with a team and a purpose. "Whose is this?" should never need a meeting.
        
      
        Change it in codeConsole clicks are for exploring. Real changes go through a reviewed diff you can roll back.
        
      
        Delete what you don't useUnused servers, keys and buckets don't get patched or watched. They just wait.
        
      
        Review on a calendarOnce a quarter: who has admin, which keys are over 90 days old, what's public, what costs money for no reason.
        
      
        Practise restoringA backup you've never restored is a hope. Restore something real, on purpose, twice a year.
        
      
        Write the runbook first"A key leaked", "the bill spiked", "root signed in": write down who does what before it happens.
        
      
        Read the defaults changelogProviders keep making safer defaults, but only for new things. Once a year, bring old things up to date.
        
      
        Start small, then widenNew services start with no access and get more when someone needs it. Taking access away later is much harder.
